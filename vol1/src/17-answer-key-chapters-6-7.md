# Answer Key: Chapters 6–7

## Chapter 6 — Choosing and Optimizing a Model

**Q6.1 — D.** Claude Haiku 5.5 is the only model in the current lineup with tiered pricing, and the threshold is 100,000 prompt tokens. Crossing it moves the entire request to the higher rate — roughly a 5x jump on both input and output — which matches the observed cost change far better than the 40% length increase would suggest. A fails because 140K is well inside the 1M context window and no automatic model substitution exists. C is wrong because long prompts do not disable caching; caching still applies, and cache reads even count toward the threshold.

**Q6.2 — A.** For pre-4.6 models on the Claude API, the bare string is an alias pointing at the most recent dated snapshot, so it can move when a new snapshot ships. B is the tempting answer because it is *almost* true now: dateless IDs from 4.6 onward genuinely are pinned snapshots, not aliases. But Sonnet 4.5 predates that change, so the alias semantics still apply and the dated form is the pinned form.

**Q6.3 — C.** Claude 4.7 and later support only adaptive thinking; `type: "enabled"` returns a 400 error. The migration is to drop `budget_tokens`, set `thinking: {"type": "adaptive"}`, and steer depth with `output_config.effort`. B is the most tempting wrong answer because it looks like a minimal additive change, but leaving `type: "enabled"` in place is precisely what the API rejects — the modes are mutually exclusive, not composable.

**Q6.4 — D.** Agent cost is dominated by turn count, because every turn re-sends the accumulated conversation as input. A model that converges in 8 turns rather than 26 processes far fewer total tokens, and a 35% failure rate adds retry cost on top. The nominal per-token ratio is only one factor in cost per completed task. A is wrong in magnitude — the cache discount helps but does not close a 40x gap on its own, and it applies to both models.

**Q6.5 — D.** No human is waiting on an overnight enrichment job, which is exactly the Batch API’s use case: a flat 50% discount on input and output with no change to model behavior or output quality. A and C both trade quality for cost. B helps only if the prompts share a long cacheable prefix and the job’s request pattern keeps hitting within the TTL, and even then it cannot match an unconditional 50% reduction across the whole job.

**Q6.6 — B.** An escalation router is only cheaper while most traffic terminates on the cheap path. If the escalation rate has drifted upward, most requests now pay for a Haiku call *plus* an Opus call, which is strictly worse than Opus alone. This is why escalation rate must be instrumented as a first-class metric. D is plausible — an over-strict validator does inflate escalation — but it is one possible cause of the rate rising, so measuring the rate is the correct first step.

**Q6.7 — C.** Output tokens cost 5x input across the lineup, and thinking tokens are billed as output. Costing an entire conversation at the input rate therefore understates by a large factor, especially on a model that reasons before answering. A, B, and D are all real modifiers, but 1.25x, 1.1x, and 1.1x respectively cannot compound to a 4x gap; only the input/output asymmetry is large enough.

**Q6.8 — A.** Lowering effort reduces or eliminates thinking, which is the dominant latency contributor on a request with a small prompt and short output. On a task like autocomplete, extended reasoning rarely improves the answer, so the quality risk is low. C is the trap: the Batch API’s discount is real but it trades latency away by design, with results available up to 24 hours later — the opposite of what a latency-sensitive endpoint needs. D would also raise a TypeError on current SDKs.

**Q6.9 — A.** The resolved effort value is rendered into the prompt, so changing it between requests invalidates cache breakpoints. Mixing effort levels per request in a cached conversation therefore guarantees misses. The documented practice is to keep effort constant for the life of a cached conversation and use the per-message effort beta where a one-off change is genuinely needed. B is invented; there is no effort ceiling on caching.

**Q6.10 — C.** Anthropic’s documented guidance for Fable 5.1 is explicitly measurement-gated: use it when evaluations on Opus 5.5 at higher effort still fall short. A is the reflex this guidance exists to prevent — importance is not a technical criterion, and Fable is both the most expensive and the slowest model. B is factually wrong: all four current models share the same 1M-token context window.

**Q6.11 — A.** On Opus 4.5 and all models 4.6 and later, thinking blocks from prior assistant turns are preserved in context and billed as input on subsequent turns. Over a long run, early reasoning keeps being paid for. B is wrong because tool definitions are cacheable and sit at the top of the cache hierarchy. C misreads the usage fields: `input_tokens` counts only uncached tokens after the last breakpoint, so there is no double counting.

**Q6.12 — B.** Opus 5.5 defaults to `medium` effort while Opus 5 defaults to `high`, so an otherwise identical request reasons less after the swap. Omitting `effort` means accepting each model’s own default, which is why a bare string change can alter behavior. A is wrong — Opus 5.5 is the newer and documented recommended default — and the lesson is that migration requires re-tuning effort and re-running evals, not just editing a string.

**Q6.13 — C.** `temperature`, `top_p`, and `top_k` are deprecated on Claude 4.7 and later; the Python SDK from v1.0 removes them, so the call fails before a request is sent. Determinism now comes from prompting, output format constraints, and programmatic validation. B is the tempting answer because `output_config` is where `effort` lives, but relocating a removed parameter does not restore it. A would work briefly and leaves the code unable to run on current models.

**Q6.14 — B.** The direct cause is that nobody knew the tool existed or which model it called, so a 60-day deprecation notice passed unnoticed. The Console’s per-API-key, per-model usage CSV exists precisely to find these forgotten callers. A is wrong as a *direct* cause of a hard outage: an alias moving produces quality drift, not total failure, whereas a retired model returns errors on every request.

**Q6.15 — B.** This matches the chapter’s two central recommendations: route by request category so each workload runs on the cheapest tier that passes its evaluations, and measure cost per successful task per category rather than per token. A is close but over-rotates by forcing open-ended multi-step analysis onto Haiku first, where the escalation rate will be high enough to cost more than routing it directly. C degrades the one category that genuinely needs reasoning.

## Chapter 7 — Agents and Workflows

**Q7.1 — A.** Every step is known before the input arrives: classify, then run the matching extractor. That is the definition of a workflow, and implementing it as predefined code paths gives bounded cost, predictable latency, and per-step testability that an agent loop cannot. B is a real secondary concern but it is a symptom; the primary objection is that model-directed control flow buys flexibility the task does not need.

**Q7.2 — C.** When `stop_reason` is `max_tokens`, generation was cut off mid-stream, so a trailing `tool_use` block can carry truncated `input` JSON that nonetheless parses into plausible-looking arguments. Such a call must never execute. B is the tempting answer because schema validation is genuinely important, but truncated arguments can be schema-valid while being semantically wrong, so validation alone does not catch this class of bug.

**Q7.3 — A.** Cost scales with total tokens processed, not turn count, and a large tool output early in a run becomes part of the input on every subsequent turn — paid for repeatedly. The fix is truncating or paginating large tool outputs at the dispatch boundary. B contradicts the evidence: the run used 11 turns, so the cap was never the binding constraint.

**Q7.4 — A.** A non-fork subagent starts with no parent conversation history and no parent tool results. The only content that crosses the boundary is the prompt string the parent passes, so file paths, error messages, and prior decisions must be written into it explicitly. Under-briefing causes exactly the observed symptoms: re-derived context and worse answers. B is wrong because the model is configurable per subagent and defaults do not explain re-reading files the parent already read.

**Q7.5 — C.** Compaction is lossy by design, so instructions that live only in the opening message may not survive the summary. Persistent rules belong somewhere re-injected on every request, which in the SDK means CLAUDE.md. A is the tempting answer because it appears to remove the problem, but a run long enough to need compaction will eventually hit any threshold, and disabling it only moves the failure to the context limit.

**Q7.6 — A.** Three consecutive failures from one tool indicate a broken environment rather than a bad approach, so further turns are pure cost. Tracking per-tool consecutive failures and terminating is the structural fix, and distinguishing permanent failures such as a 401 from retryable ones prevents pointless retries. B actively makes things worse: hiding the error leaves Claude unable to understand why its calls are not working.

**Q7.7 — D.** Gate the operations that are expensive to undo and let reversible work run unattended. A is the trap: approving every call produces approval fatigue, which trains operators to click through reflexively and manufactures the appearance of oversight without the substance. C comes too late — by then the pull request already exists.

**Q7.8 — B.** Three independent checks with no data dependency between them is the textbook case for sectioning: run them concurrently and aggregate, so latency becomes the slowest branch rather than the sum. A is wrong because chaining would make them sequential, which is the current problem. C addresses output quality through iteration, not latency, and would add round trips.

**Q7.9 — C.** The subtasks cannot be enumerated in advance — which files need changing is discovered during the run — which is exactly the condition that calls for orchestrator-workers. A fails because you cannot write one step per file without knowing the files. D is the tempting distractor: voting runs the *same* task repeatedly for confidence, and does nothing to discover an unknown set of subtasks.

**Q7.10 — D.** A cost cap can only be evaluated once a response arrives, because the cost comes from the usage returned with it. The response that crosses the cap still completes and bills, and subagents already running can add spend before they stop. Overshoot of roughly one response’s cost is expected behavior, so caps need headroom. A is wrong: subagent spend does count toward the total.

**Q7.11 — B.** Clearing changes the prompt prefix, which invalidates the cache from that point. `clear_at_least` exists to guarantee each activation frees enough context to justify the cache write it forces. Without it, a low trigger produces frequent small clears that cost cache writes while freeing little. C overstates the effect: `keep` preserves the most recent tool uses by default.

**Q7.12 — C.** Oscillation is usually a progress-tracking failure: the agent has no durable record of what it has already tried, so it rediscovers the same dead end. Task state held outside the conversation, plus detection of repeated identical calls, attacks the cause. A is the tempting answer and is strictly harmful — more turns means more cost spent on the same loop, with no mechanism that would break it.

**Q7.13 — D.** An agent that reads, edits, and runs tests needs exactly what the Agent SDK ships: hardened `Read`/`Edit`/`Bash` implementations, a permission system with scoped rules and modes, and hooks for validating calls before they run. Writing and securing a correct file-edit and shell-execution layer yourself is substantial work. C is false — the tool runner supports `max_iterations` — and A is false as well, since the runner handles parallel tool calls.

**Q7.14 — B.** A free-text parameter invites invention; a closed `enum` in the input schema removes the opportunity, and dispatch-layer validation catches anything that slips through, reporting it as `is_error` so Claude can correct. A is the tempting answer and does help somewhat, but the schema is the authoritative constraint the model is given for each tool, and system-prompt instructions are weaker and more easily lost to compaction.

**Q7.15 — B.** An unattended agent against production needs defense in depth: all three budget caps, per-tool failure termination, schema validation before execution, approval gates on irreversible actions, task state outside the conversation so progress survives compaction, and per-turn usage logging so cost and failure modes are visible. C inverts the correct reasoning — the *absence* of a human is why `bypassPermissions` is inappropriate outside isolated environments, and a cost cap alone does not prevent destructive actions.
