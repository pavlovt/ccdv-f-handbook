## Applications and Integration

**M1 — A.** *(Applications and Integration)* The Messages API holds no conversation state: the full history must be sent on every request, so history that lives only in one replica’s memory is lost whenever the load balancer routes a follow-up elsewhere. With three replicas and round-robin routing, roughly two requests in three land on a replica that never saw the earlier turns, which matches the reported two-in-three failure rate exactly. B inverts the actual architecture — there is no server-side conversation state to overwrite. C is tempting because context exhaustion also loses early turns, but exceeding the window surfaces as an error or a truncation stop reason, not as a clean 1-in-3 pattern, and a short support chat is nowhere near the limit. D names a real required header, but `anthropic-version` governs request and response shape, not history interpretation.

**M2 — C.** *(Applications and Integration)* A long non-streaming generation holds one connection open with no traffic on it, and intermediaries drop idle connections, which is why the failure presents as a reset with no HTTP response and clusters on the longest outputs. Streaming keeps the connection active and the Batches API removes the open connection entirely by letting you poll. A would reduce the symptom by truncating legitimate long outputs, which breaks the feature rather than fixing the transport problem. B is the right reflex for transient errors but wrong here: the failure is deterministic for large contracts, so retries reproduce it, as the question states. D is a non sequitur — `temperature` does not control length, and a lower temperature does not shorten a long structured summary.

**M3 — C.** *(Applications and Integration)* The SDKs raise typed exceptions, so branching on the exception class lets you retry only what can succeed — connection errors, 5xx responses, and 429s that carry a `retry-after` — and skip the 400/401/403/404/413 class that will fail identically forever. Capturing the `request-id` from the failed response is the specific piece of evidence support needs, which is the second half of the problem. A makes the first problem worse by spending more time on unretryable failures. B is partly right but names the same blind retry-everything behaviour that caused the bug. D misattributes the fix: batches isolate failures per request but still surface errors to you, and they are wrong for a path that needs a synchronous answer.

**M4 — D.** *(Applications and Integration)* The manual is a large, static prefix reused across hundreds of requests, which is exactly the shape prompt caching is designed for, and the extended TTL matters because a morning burst of questions can have gaps longer than the default lifetime between them. A is counterproductive: prefilling does not reduce input cost, and moving the manual into the messages array gives up the natural position for a stable prefix. B is tempting because the batch discount is real and the work is bursty, but these questions are interactive — an analyst is waiting — so asynchronous processing changes the product. C sounds like retrieval but is not: sending 180 separate blocks still sends every page unless you also build retrieval, and splitting a cacheable prefix into many blocks does nothing by itself.

**M5 — B, D.** *(Applications and Integration)* A cache hit requires a byte-identical prefix, and the cache hierarchy runs tools, then system, then messages, so a change at an earlier level invalidates everything after it — an image appearing and disappearing invalidates from the system level onward, and unstable key ordering in tool definitions invalidates the tool level and everything below. A describes a real condition (prompts below the minimum are not cached) but the failure mode is wrong: no error is returned, and the question states non-zero creation tokens, which means writes are happening. C is a real isolation boundary, but two workspaces would show a stable split rather than near-universal misses, and the question gives no sign of a second workspace. E is fabricated; usage fields are reported on streaming and non-streaming responses alike.

**M6 — A.** *(Applications and Integration)* This is the canonical batch workload: very high volume, no interactive consumer, and a deadline hours away, so the Batches API gives a substantial discount and removes the need to manage concurrency and rate limits yourself. Matching results by `custom_id` is required because batch results are not returned in submission order. B works but is the expensive version of the same thing: you pay full price, build a concurrency controller, and then handle the 429s you deliberately provoked. C destroys the per-ticket boundary — one long request means one failure takes 500 tickets with it, and cross-contamination between concatenated tickets degrades classification. D confuses streaming with throughput; streaming changes when the first token of one response arrives and does nothing for 40,000 of them.

**M7 — B.** *(Applications and Integration)* Two independent facts explain the two symptoms: requests that do not complete within the processing window expire and produce no successful result, which is the missing scores, and batch result ordering is not guaranteed, which is the misattributed scores. A gets ordering backwards — it is explicitly not guaranteed. C invents an automatic retry batch that does not exist; expired requests are yours to resubmit. D is wrong on both halves: you are not billed for expired requests, and sorting by a creation timestamp would not fix an ordering problem that `custom_id` is designed to solve.

**M8 — C.** *(Applications and Integration)* Structured outputs use constrained decoding, so the response text is valid JSON conforming to the schema — this removes the parse-failure class rather than retrying past it, and the schema’s `required` list also settles the missing-field problem. A helps a little but is a heuristic: prefilling suppresses preamble without guaranteeing well-formed or complete JSON, and it is in any case incompatible with JSON outputs. B is a genuine and widely used pattern, and it gets you structured arguments, but without strict schema validation the conformance is natural rather than guaranteed, and the question asks for the final *response* to be JSON rather than a tool call. D reduces the failure rate without changing its nature; best-effort formatting is what already failed 1.5% of the time.

**M9 — D.** *(Applications and Integration)* Constrained decoding guarantees conformance for a response that finishes, but a response cut off at the token limit can be incomplete JSON, and a refusal comes back with HTTP 200 and output that need not match the schema — so both must be handled in application code. A is the trap: neither case is an HTTP error, so an error handler never sees them. B describes a real schema-complexity concern but would surface as a 400 at request time, not as intermittently malformed output on otherwise successful responses. C invents a cache-expiry failure mode; grammar caching affects first-use latency, not output validity.

**M10 — A.** *(Applications and Integration)* Scanned pages have no extractable text, and image citations are not supported, so citations cannot be produced for this document no matter how it is sent — that is the answer to the question as asked. **M11 — C, E.** *(Applications and Integration)* Both answers give you a citation that identifies the originating chunk: one document block per chunk yields a `document_index` per citation, and a custom-content document with one block per chunk yields `content_block_location` with block indices and skips sentence chunking, which suits short retrieved passages. **M12 — B.** *(Applications and Integration)* Tool input is streamed as partial JSON fragments, which are not individually parseable — you accumulate them and parse once the block closes. **M13 — C.** *(Applications and Integration)* The usage reported on a `message_delta` event is cumulative, so each event carries the running total; summing them adds the same tokens repeatedly, which inflates the metric exactly as described. Take the final value instead. A names a true fact about thinking token billing but no double count occurs, and it would not produce a total “far higher” the way summing a cumulative counter does. B is the wrong direction — cache reads are input tokens, and adding them would further inflate rather than reconcile an output overcount. **M14 — D.** *(Applications and Integration)* Search results carry opaque encrypted content that must be returned unchanged on later turns; dropping or altering it fails the request with a 400, which is precisely what reconstructing the assistant turn from a partial database copy does. The general rule is to send the assistant’s content blocks back exactly as received. A is backwards — citations are always on for web search and are not something you enable on a later turn. B inverts the requirement: the tool definition must be kept in the `tools` array on continuation, not dropped. C confuses server tools with client tools; you never return a `tool_result` for a server tool’s id.

**M15 — A.** *(Applications and Integration)* A server tool call with no matching result is the documented shape when a server tool and a client tool are requested in the same parallel group: the server call is deferred so you can run the client tool first. Both of the engineer’s planned changes break the continuation — omitting the server tool from `tools` is a 400, and appending a text block after `tool_result` blocks when a server tool is involved is also a 400. B misreads the unfinished call as a failure. C is wrong about the outcome (the request fails rather than succeeding) even though disabling parallel tool use is a legitimate way to avoid the situation in future. D confuses the two stop reasons: a pending client tool call returns the tool-use stop reason, never the pause stop reason.

**M16 — B, D, F.** *(Applications and Integration)* Caching a static prefix bills the repeated tokens at the much lower read rate. Clearing the oldest tool results removes input tokens from the prefix altogether, and a minimum-clear threshold makes sure each clear frees enough to be worth the cache invalidation it causes. And on most models cache reads do not count toward the input-token-per-minute limit, which answers the rate-limit half of the question. A is a real cost lever but reduces *output* tokens, which the question explicitly excludes. C reduces truncation-driven retries, which is good practice but not an input-token reduction, and it was ruled out by the question’s framing. E inverts the pricing: the longer TTL costs *more* per token written, and you choose it for hit rate, not price.

**M17 — B.** *(Applications and Integration)* Files are scoped to the workspace, not to an end user or session, so a `file_id` taken from a client request is a direct cross-tenant read: the server must own the user-to-file mapping, and a workspace per tenant gives a boundary that is actually enforced rather than assumed. A is security through obscurity — unguessability is not an authorization control, and IDs leak through logs, caches, and support tooling. C mitigates duration without mitigating access; an attacker only needs the window to be open once. D invents a scoping distinction between block types that does not exist.

**M18 — C.** *(Applications and Integration)* An error delivered inside the event stream arrives after a 200 response has already been returned, so ordinary HTTP-level retry handling does not apply — the correct response is to treat the partial generation as lost, back off, and either retry or resume from the last complete text block. A invents separate capacity pools for streaming and non-streaming traffic. B is the behaviour described in the question, which is what is causing the repeat failures. D presents the symptom as a reason to shed the feature and is wrong about batches, which can also experience errors; it would also convert an interactive chat into an asynchronous one.

## Model Selection and Optimization

**M19 — D.** *(Model Selection and Optimization)* High volume, narrow task, short input, single-label output, and 2.4 points of accuracy headroom above the requirement describe the textbook case for the efficiency-first path: evaluate a smaller model on the existing held-out set and adopt it if it clears the bar. A is a common misconception — `max_tokens` is a ceiling, and you are billed for tokens produced, so lowering it saves nothing here. B is worth doing and will help, but caching a short system prompt on short requests is a marginal saving compared with moving four million daily requests down a model tier. C would halve the bill and is a good idea if the classification can run offline, but the question does not say it can, and it leaves the oversized model in place.

**M20 — A.** *(Model Selection and Optimization)* Effort governs how many output tokens the model spends across thinking, tool calls, and prose, so lowering it from the default is the most direct latency lever that does not change models — and well-specified refactoring tasks are exactly the workload the lower levels are recommended for, subject to confirming on evals. B confuses a ceiling with a cause: the responses are not hitting the token limit, so lowering it truncates good answers rather than speeding them up. C is backwards — streaming improves *perceived* latency by delivering the first tokens sooner and is the thing you would add, not remove. D is a category error: batching increases latency and is for workloads with no waiting user.

**M21 — B.** *(Model Selection and Optimization)* Effort and model choice both reduce cost, but by different mechanisms and with different risks: effort trades thoroughness within one model’s capability envelope, while a model change moves the envelope itself — which makes effort the cheaper experiment to run first, with evals deciding either way. A collapses a real distinction and leads teams to make the larger change first. C is wrong on scope: effort applies to all output tokens, including text and tool arguments, not only to whether thinking blocks appear. D asserts an ordering that your own evals and traffic mix decide, and it is not generally true.

**M22 — A, C.** *(Model Selection and Optimization)* Both are the standard ways to keep most tokens on a cheap model while preserving quality where it matters: an orchestrator on a strong model delegating bulk work to cheap workers, and a cheap executor escalating only the cases it flags as uncertain. B increases cost rather than reducing it — caching lowers the price of repeated *input*, and the highest effort level drives up output spend on every request. D doubles the cost of every request and then selects on length, which is not a quality signal. E bounds per-request cost by truncating responses, which produces incomplete summaries rather than cheaper good ones.

**M23 — C.** *(Model Selection and Optimization)* Forcing a tool and disabling thinking are precisely the integration patterns called out as potentially behaving differently or being rejected on newer models, so the migration starts with the breaking-change notes, then re-runs the eval set, then re-tunes the prompt for the new model rather than assuming months of tuning transfers. A misapplies the versioning promise, which covers the stability of the API contract across API versions, not behavioural equivalence between models. B invents a compensating relationship between temperature and model generation. D is expensive, slow, and selects on a single weak metric instead of the team’s own task performance.

**M24 — D.** *(Model Selection and Optimization)* The guidance is explicit that a larger set with slightly noisier automated grading beats a small set of carefully hand-graded cases, because the small set cannot detect the differences you care about and cannot be rerun on every change. A is the plan as stated. B overcorrects: human grading is slow and expensive and worth avoiding at scale, but it remains the right tool for validating an automated grader. C substitutes a length proxy for quality, which is exactly the kind of metric that produces verbose, worse summaries. D’s claim about cross-model comparison is false — comparing models on your own evals is the recommended practice.

**M25 — A.** *(Model Selection and Optimization)* You are billed for the tokens actually produced, and the output-token rate limit is evaluated as tokens are generated rather than reserved from `max_tokens`, so the colleague is wrong on both points. The real hazard of a very large value is a long-running non-streaming request being dropped mid-generation, which is why that path should stream. B states the pre-reservation belief, which is the single most common misconception in this area. C and D each concede half of that misconception, which is why they are the most tempting wrong answers — but neither half is true.

**M26 — B.** *(Model Selection and Optimization)* Newer model generations can ship a different tokenizer that produces materially more tokens for the same text, which raises cost per request and consumes more of the context window even though nothing in the prompt changed — so token counts must be re-measured against the model you are actually calling. A invents a surcharge on tool definitions. C is false and would in any case reduce cost if it were true, not raise it. D inverts the rule: system-added tokens may appear in counts but are not billed, so they cannot explain an invoice increase.

**M27 — C.** *(Model Selection and Optimization)* Caching changes what a long prefix *costs*, not how large it is, so it cannot prevent a failure caused by the prefix growing — only reducing the content does that, which is what clearing the oldest tool results achieves, at the price of invalidating the cache when it fires. That tradeoff is exactly why a minimum-clear threshold exists. A is the seductive version of the caching answer and ignores that the context window is a hard limit. B asserts an equivalence that is false in both directions. D is defeatist and wrong: the whole point of server-side clearing is to extend a session past this point without discarding it.

## Agents and Workflows

**M28 — D.** *(Agents and Workflows)* When the categories are stable and the steps are the same every time, a routing workflow plus a templated generation step produces the same output with better predictability, lower cost, lower latency, and a far simpler audit trail — agentic flexibility earns its cost only when the sequence of steps cannot be known in advance. A is false: tool calls appear in the response and can be logged. B invents a dependency on batch processing. C is wrong on mechanics — tool choice can be constrained to a single tool, which is in fact one way to implement routing.

**M29 — A.** *(Agents and Workflows)* The pause stop reason means a server-tool loop hit its iteration limit mid-turn; the continuation is to append the returned assistant content to the message list and call again with the same tools, which resumes the work instead of discarding it. That is precisely what the buggy loop fails to do, hence the “starts over” complaint. B treats it as a transient capacity problem, which it is not, and resending the original message is the behaviour being complained about. C misreads a mid-turn pause as completion. D confuses it with hitting the output ceiling, which is a different stop reason with a different remedy.

**M30 — B.** *(Agents and Workflows)* Appending your own text immediately after tool results is a documented cause of empty responses: it teaches the model that the turn ends there. The second half matters too — the recovery is a fresh continuation prompt in a new user message, not resending the empty response, which compounds the pattern. A misdiagnoses the mechanism and proposes moving the text to a place where it would be applied on every turn. C is the reflex answer, but the question states the response is a couple of tokens with the natural-end stop reason, which is not truncation. D invents a cache-miss symptom; a cache miss costs money, it does not empty a response.

**M31 — B, C.** *(Agents and Workflows)* Both the cost problem and the selection problem come from loading too many definitions at once. A tool search tool with deferred loading keeps only a handful of tools in context and discovers the rest on demand; disabling the tools this agent does not need shrinks the candidate set directly. A spends more tokens reasoning over a set that is too large to reason over well, which treats the symptom. D limits calls per turn without reducing the number of choices or the fixed input cost. E is actively harmful: prose in a system prompt is not a callable tool definition, and caching it only makes the wrong thing cheaper.

**M32 — C.** *(Agents and Workflows)* The distinction is where the decomposition comes from: in parallelization your code fixes the subtasks in advance, while in orchestrator-workers the model decides at runtime how to break the task apart based on the input. A invents an API dependency for one pattern. B is wrong — both patterns can use one model or several, and mixing tiers is an optimization, not a definition. D misstates both: parallelization is defined by independence, and orchestrator-worker subtasks are frequently run concurrently.

**M33 — D.** *(Agents and Workflows)* A clear written rubric that reviewers apply consistently is the precondition for the evaluator-optimizer loop: one call drafts, another grades against the rubric and returns specific feedback, and the loop runs until it passes — which is the pattern most often cited for exactly this translation-quality problem. A addresses genre variation, which is not the reported failure. B splits the work into passes that do not map to the problem; flatness is not a granularity issue. C produces diversity and then collapses it by majority, which selects for the most typical output — the opposite of what a stylistic lift needs.

**M34 — C, D, F.** *(Agents and Workflows)* All three are real mechanisms, accurately described: clearing the oldest tool results with a placeholder so the model knows content was removed; a memory tool so the agent can persist findings before clearing takes them; and clearing earlier thinking blocks while keeping the most recent turns, which on some models preserves cache hits. A misuses a cache pre-warming technique as a history-compaction one — and that technique is in any case incompatible with the thinking configurations these agents use. B asserts a relationship between sampling temperature and tool-call count that does not exist. F in its original form is the dangerous belief that the API will quietly manage the window for you; exceeding it is surfaced, not silently absorbed.

**M35 — A.** *(Agents and Safety-adjacent Workflows — scored under Agents and Workflows)* This is indirect prompt injection, and the answer layers the three controls that actually apply: deliver third-party content in tool results labelled with their source, state in the system prompt that such content is data whose embedded instructions are to be reported rather than followed, and apply least privilege so the destructive action cannot complete without an explicit confirmation. B removes the capability entirely, which is a legitimate last resort but is not available when cancelling is a product requirement, and a prompt instruction alone is the control that already failed. C is the single worst placement: the system prompt is where untrusted content gains the most authority. D adds reasoning and after-the-fact logging, neither of which prevents the action.

## Prompt and Context Engineering

**M36 — B.** *(Prompt and Context Engineering)* For long inputs the guidance is specific: put the documents at the top, put the query at the end, and wrap each document in tags with its source metadata so the model can attribute and separate them. The reported inconsistency on multi-document questions is the exact symptom this ordering addresses. A optimizes the wrong thing; instruction placement is not the dominant factor at 60,000 tokens. C wastes context and introduces repetition the model must reconcile. D destroys the cross-document reasoning the questions require.

**M37 — C.** *(Prompt and Context Engineering)* Asking the model to quote the relevant passages first and then answer from those quotes is the standard long-context grounding technique: it forces an explicit relevance selection step before synthesis, which is what stops irrelevant documents bleeding into the answer. A changes variance, not relevance — a deterministic answer can be deterministically wrong. B is an instruction with no mechanism behind it; exhortations to be accurate do not create a selection step. D shortens the answer without changing which documents it draws on.

**M38 — D.** *(Prompt and Context Engineering)* Prefilling the start of the assistant turn puts the response inside the target format from the first token, so there is no position in which a preamble can appear — the most direct fix for a right-content-wrong-shape problem when structured outputs are not in use. A stops generation at a literal string, which is brittle, and it does nothing about the other phrasings the preamble can take. B puts a response-formatting instruction somewhere it only applies to tool input. C may improve conformance slightly but is a large change for a problem a single prefill solves, and more examples have never been a reliable cure for preamble.

**M39 — D, E.** *(Prompt and Context Engineering)* Boundary-case inconsistency is what targeted examples are for — show the intended label on precisely the cases that are ambiguous — and tagging the prompt’s parts keeps instructions, definitions, examples, and input from bleeding into each other, which is a common cause of unstable classification. A removes the guidance that makes the task well defined. B adds output and latency on every request without improving the hard cases, and long explanations on easy cases can talk the model out of correct answers. C raises variance, which is the opposite of consistency.

**M40 — A.** *(Prompt and Context Engineering)* A breakpoint written on a block that changes every request can never be hit, because a hit requires a byte-identical prefix up to and including that block. The breakpoint belongs on the last block that is identical across requests — here, the end of the session-stable document set — with additional breakpoints on the static tool and instruction prefixes. B blames the lifetime, which does not matter when no reusable entry is being written in the first place. C invents a restriction: breakpoints are valid in tools, system, and messages alike. D invents an ordering rule; prefixes are built tools, then system, then messages, and breakpoints are placed on whichever blocks are stable.

**M41 — B.** *(Prompt and Context Engineering)* The failure is a design problem, not a wording problem: two rules genuinely conflict, so the fix is to resolve the conflict explicitly, structure the rules so each one’s scope is unambiguous, and keep an eval case for the situation so the regression cannot return silently. A relies on a folk belief about instruction position and leaves both contradictory rules in the prompt. C puts operational policy in a tool description, where it applies only when that tool is considered. D asks the model to resolve, at runtime and inconsistently, a contradiction that a human can resolve once.

## Tools and MCPs

**M42 — C.** *(Tools and MCPs)* Two things are wrong with the plan: the connector reaches remote servers over HTTP and cannot attach to a local STDIO server at all, and the authorization token is an access token your application is responsible for obtaining and refreshing, not a static key you paste once. A gets the transport requirement backwards — co-location does not make STDIO reachable. B invents a capability split in which STDIO servers expose resources but not tools. D describes a re-declaration step the connector does not require, and it would not make the transport problem disappear.

**M43 — D.** *(Tools and MCPs)* Disabling the nine write tools on the toolset means the model never sees them, which is a configuration boundary rather than a request the model can be talked out of honouring — and it is the recommended pattern for building a read-only assistant over a server that also exposes destructive operations. B disables tool calling entirely, so the reporting assistant cannot read anything either. **M44 — B, D.** *(Tools and MCPs)* Returning the failure to the model as an error-marked tool result keeps the loop alive and gives the model enough information to fix its input or take another path, and improving the tool and parameter descriptions — optionally with strict schema validation — reduces the rate of bad-input failures at the source. **M45 — A.** *(Tools and MCPs)* The distinction is know-how versus capability: a Skill packages instructions, reference files, and local scripts that load progressively as the task needs them, while an MCP server supplies a connection to an external system. **M46 — B.** *(Tools and MCPs)* The allowed-domain and blocked-domain lists are mutually exclusive, and supplying both returns a 400 — which is the bug here. ## Security and Safety

**M47 — C.** *(Security and Safety)* Placing third-party content in the system prompt positions it as authoritative instruction rather than as data to be examined, which is the structural mistake behind most indirect prompt injection. Untrusted content belongs in tool results, labelled with its source, under a stated policy that such content cannot override the system prompt or the user’s request. A invents a differential token limit between the two. B is factually wrong — system content is cacheable — and in any case describes a cost issue, not the security finding. D reframes a serious security problem as a retention nuance.

**M48 — B, D.** *(Security and Safety)* A lightweight screening model in front of the main conversation, with a schema-constrained verdict and a refusal from the screen itself treated as a harmful verdict, is the recommended first layer; an explicit boundaries-and-refusal-wording system prompt is the recommended second. A proposes self-consistency checking, which is neither a documented control nor reliable — the same model talked into a bad answer tends to be talked into it twice. C argues against defence in depth, which is the whole premise of hardening. E hands an attacker a feedback channel telling them which classifier fired, which helps them iterate.

**M49 — D.** *(Security and Safety)* Your instruction placed inside a tool result sits in the same untrusted region as the attacker’s, so it may be discounted along with it — and putting your own instructions there is explicitly discouraged. The policy belongs in the system prompt as a standing rule, or in a user turn that follows the tool result. A attributes the problem to markup when it is about trust region. B assumes length fixes a placement problem. D endorses the position the question is asking you to reject.

**M50 — A.** *(Security and Safety)* When the design question is blast radius, the answer is least privilege plus containment plus an out-of-band confirmation on the damaging action: scope the credentials narrowly, sandbox tool execution, and require a confirmation the injected content cannot supply — so a successful injection cannot complete the transfer by itself. B improves reasoning, which an adversary is specifically trying to subvert, and reasoning quality is not a containment boundary. C shortens the time to detection but the money has already moved. D is wrong on mechanism: the transfer tool is yours regardless of how it is exposed, and routing it through a server does not put it beyond the reach of an instruction the model follows.

## Claude Code

**M51 — B.** *(Claude Code)* Managed settings are the top of the precedence stack, so a deny rule deployed there cannot be overridden by a developer’s own settings files; developers can still add allow rules for their own projects in their local settings; and a deny rule beats a matching allow rule however specific that allow rule is. That is all three guarantees. A has no enforcement — a shared project file is editable by anyone who can commit. C mistakes an allowlist for a denylist: broad allow rules elsewhere can still permit the command, and an allow rule cannot carve the restriction into place. D is wrong on both counts: ask rules are overridable by precedence like any other setting, and an ask rule prompts rather than blocks.

**M52 — C.** *(Claude Code)* Hooks run as shell commands at lifecycle events and are enforced by the tool rather than by the model: a hook before a tool runs can deny a matching call and return a reason, and a hook after a tool completes can run the formatter. That is exactly the “without relying on the model reading an instruction file” requirement. A relies on the model honouring context, which is guidance and not enforcement. B misuses ask rules, which prompt a human and cannot run a formatter. D confuses a non-interactive invocation mode and a tool allowlist with a post-edit action.

## Eval, Testing, and Debugging

**M53 — D.** *(Eval, Testing, and Debugging)* With two days and a vague failure, the right build is a larger set drawn from real traffic — deliberately including irrelevant, overlong, and ambiguous input — graded automatically: code checks for anything mechanically verifiable, and a model-based grader with an explicit rubric and a constrained verdict for the subjective part, spot-checked against human judgment before it is trusted. A is the small-hand-graded-set trap: it cannot catch a 1-in-20 failure and cannot be rerun on every change. B tests liveness, not behaviour, and would have passed throughout the regression. C substitutes a length proxy for the quality being measured, and monitoring detects the next regression rather than preventing it.

Then apply two corrections to that reading:

**Weight by domain size.** Applications and Integration is 18 questions and a third of the real exam, and Model Selection and Optimization is another nine. Scoring 12 of 18 on the first section is a serious problem even if your total looks acceptable; missing the single Eval question tells you almost nothing. Any section where you scored below 60% deserves attention, but a weak large section deserves it first.

**Check *why* you missed each one.** Separate your misses into three piles: items where you did not know the fact, items where you knew the fact but picked the wrong answer anyway, and items you ran out of time on. The first pile is a reading problem. The second is the one that matters most, because it means the distractors are working on you — and the real exam’s scenario questions are built out of plausible-but-wrong advice. The third means you need to practise pacing: 2 minutes 15 seconds per question, and no single question is worth five.

And once more: this mock is a third-party instrument. It is calibrated against the published domain weights and the real exam’s format, not against its item bank. Use it to find holes, not to predict a number.
