# Answer Key: Volume II Chapters 1–2

## Chapter 1 — Integration Architecture in Production

**V1.1 — A.** Break-even hit rate is (*w* − 1) / (*w* − *r*). On Sonnet 5.5 the five-minute multipliers (1.25 write, 0.05 read) give 20.8%, and the one-hour multipliers (2.00 write, 0.05 read) give 51.3%; 35% clears the first and 88% clears the second, so both configurations beat no caching. Comparing them directly, expected cost per request in units of the uncached price is 0.35 × 0.05 + 0.65 × 1.25 = 0.830 for the five-minute setting and 0.88 × 0.05 + 0.12 × 2.00 = 0.284 for the one-hour setting. The one-hour configuration is therefore roughly a third of the cost, which eliminates C, and nothing here falls below break-even, which eliminates B and D.

**V1.2 — B.** OTPM is evaluated in real time as tokens are produced and counts only tokens actually generated, so `max_tokens` does not factor into it at all and raising it carries no rate-limit penalty. Lowering it from 64,000 to 4,096 therefore relieves nothing and merely truncates legitimate responses. A is the common misconception — reservation from `max_tokens` — and C invents a streaming-specific variant of the same error. D is wrong in the other direction: ITPM is estimated at request start from the *input*, then reconciled against actual input during the request, and `max_tokens` plays no part in it.

**V1.3 — D.** Haiku 5.5 is priced by prompt length, and the documented rule is that prompt length counts all input tokens including cache reads and writes, with each request priced on its own. A 180,500-token prompt is above the 100,000-token threshold, so the entire request pays the higher tier: reads at \$0.05/MTok and uncached input at \$0.50/MTok. A applies the under-threshold rates, C forgets that reads keep their own 0.1× relationship to the stepped-up base rate, and B inverts the threshold rule by exempting cache reads from the length calculation.

**V1.4 — C.** A cache entry becomes available for reading only once the first response has begun, so a simultaneous fan-out against a cold prefix produces one write per request. On a 150,000-token prefix that is 60 writes instead of one write and 59 reads — the documented reason to send one request, wait for its response to start, and only then release the rest, or to pre-warm with `max_tokens: 0`. A assumes the entry is available the instant the first request is accepted, B confuses write behaviour with the 20-position lookback that governs where a breakpoint searches, and D credits the platform with a serialisation it does not perform.

**V1.5 — A and C.** Invalidation cascades in the order tools, then system, then messages, so any change to the `tools` array — including a reordering, since matching is byte-exact — invalidates the system-level breakpoint and everything after it. Changing `output_config.format` also invalidates the thread’s prompt cache, because an extra system prompt describing the format is injected into the prompt. B is the normal append-only growth pattern that caching is designed for and leaves the system prefix intact. D and E do not affect the rendered prompt: `max_tokens` is a generation ceiling, and `metadata.user_id` is opaque metadata used for abuse detection.

**V1.6 — A.** Cache writes count toward ITPM and cache reads generally do not, so on a 100% hit rate each request draws only its 2,000-token uncached tail from the input bucket. Ten million ITPM divided by 2,000 is about 5,000 requests per minute. B is correct arithmetic on the wrong basis — it uses the full 402,000-token prompt — and D compounds that with the false premise that the start-of-request estimate ignores the cache. C overstates the exemption: the tail is small but not free, so the limit is finite.

**V1.7 — B.** `metadata.user_id` is documented as an opaque external identifier, capped at 512 characters, that Anthropic may use for abuse detection, and the docs explicitly warn against putting names, e-mail addresses or phone numbers in it. It is not a dimension in the Usage or Cost reports, which group by workspace, API key, model, service tier, context window, data residency and speed. A claims a grouping that does not exist, C recommends exactly the personal data the field must not carry, and D confuses an abuse-detection field with workspace-level billing attribution.

**V1.8 — C.** Within a batch, requests run concurrently and in arbitrary order, so cache hits are best-effort; the documented pattern is to send one request carrying the shared prefix with a one-hour breakpoint, wait for it to complete, and only then submit the batch. A and B both fan out against a cold prefix and risk paying thousands of writes, with B merely paying the more expensive 2× write multiplier while doing so. D is impossible: `max_tokens: 0` is explicitly rejected inside Message Batches, which is precisely why the warm-up request must be an ordinary one.

**V1.9 — A.** With a write at 1.25× and an Opus 5.5 read at 0.05×, two requests cost 1.25 + 0.05 = 1.30 units against 2.00 uncached, a saving of 35%. This is the algebraic content of the documented summary that a five-minute write pays off after a single read: the break-even request count is (*w* − *r*) / (1 − *r*) + 1 ≈ 2.26, and two requests already clear it. C describes the one-request case, where a write with no read is a flat 25% penalty; B and D simply misstate the arithmetic.

**V1.10 — B and D.** `max_tokens: 0` is rejected together with `output_config.format`, as well as with streaming, extended thinking, and `tool_choice` of `tool` or `any` — which is why schema-constrained workloads need a pre-warm request that omits the format. Fast mode is also documented as unavailable with the Batch API. The others all stack: caching works with batches at the full 50% discount, the 1.1× data-residency multiplier applies to cache writes and reads as well as ordinary tokens, and structured output is explicitly supported with streaming.

**V1.11 — D.** The API enforces limits with a token bucket whose capacity is replenished continuously rather than reset at interval boundaries, so 60 RPM behaves much like one request per second. A client that permits its whole minutely allowance at the top of each minute presents a burst the server rejects, then idles while the bucket refills — exactly the observed pattern. A is contradicted by the idle capacity later in each minute, C does not explain the periodicity aligned to the minute boundary, and B inverts cause and effect: ignoring `retry-after` wastes attempts but does not cause the platform to lower your configured limit.

**V1.12 — C.** A spend-cap 429 carries error type `rate_limit_error` but sets `error.details.error_code` to `enforced_spend_limit_reached`, never includes `retry-after`, and keeps failing until access resumes at the start of the next month or the tier is raised. Branching on that field before entering backoff is essential, because the SDK’s automatic retries will otherwise consume attempts on a request that cannot succeed. A and B both retry a condition that is deterministic for the rest of the billing period, and D misclassifies a billing state as a capacity failure, which would also take down unrelated traffic sharing the breaker.

**V1.13 — B.** Cache matching is prefix-based and you have four breakpoints with a 20-position lookback, so the productive layout orders content from most stable to least — global prefix, tenant prefix, session documents — and reserves the fourth breakpoint for a sliding history window, which is where the remaining uncached growth lives. A collapses the global and tenant layers into one, so every tenant pays its own write for the shared global prefix and nothing is reused across tenants. C abandons the two most stable and largest layers entirely, and D leaves the single most reusable block uncached.

**V1.14 — D.** The undifferentiated `anthropic-ratelimit-tokens-*` triple reports whichever limit is currently most restrictive: workspace values when a workspace limit is binding, and otherwise the combined input-plus-output total. A describes only the second of those two cases. C is wrong because remaining token counts are rounded to the nearest thousand, so they are a floor for reservation purposes rather than an exact figure, and B is wrong because the rate-limit headers are returned on ordinary successful responses, which is what makes header-driven limiting possible at all.

**V1.15 — A and C.** `overloaded_error` is a transient capacity failure and is retryable with exponential backoff, but the retries must run inside the existing concurrency budget so that a retry wave does not become a self-inflicted thundering herd. `invalid_request_error` is deterministic: the body must be fixed before resending, so those items are surfaced as permanent failures. B retries permanent failures and abandons the concurrency bound at once. D trips a capacity breaker on a code bug, which would take down unrelated features. E conflates a throughput observation with a limit and permanently cripples the fan-out.

**V1.16 — C.** Without caching, 45 requests each pay 200,000 tokens at \$2/MTok, or \$18.00. With a one-hour write and 45 hits, billable-equivalent input is 200,000 × 2.0 + 45 × 200,000 × 0.05 = 400,000 + 450,000 = 850,000 tokens, which is \$1.70, and the batch discount halves that to \$0.85. The ratio is 18.00 / 0.85 ≈ 21×, of which roughly 10.6× comes from caching and 2× from batching. A would be the batch discount alone with a little caching, B omits the batch discount, and D mistakes the request count for the saving.

**V1.17 — B.** Effort is rendered into the prompt, so two requests that differ in effort have different prefixes and cannot share a cache entry. Sonnet 5.5 defaults to `high` on the Claude API, so an omitted `effort` is not equivalent to the batch path’s explicit `"medium"` — the fix is to set it explicitly and identically on both paths. A denies the premise that effort is prompt-affecting, while C and D invent isolation boundaries that do not exist: caches are scoped per organization and workspace, not per submission mode or per streaming setting.

**V1.18 — A.** The one-hour write multiplier of 2.00× puts break-even at a 51.3% hit rate, so extended TTL needs a *majority* of requests to land on the entry. A nightly harness running 2,000 prompts against a fixed 90,000-token rubric over 40 minutes will hit on essentially all of them, and the 40-minute span is exactly the case the five-minute default cannot cover. B is a 20% hit rate, well below the one-hour threshold though above the five-minute one. C has no shared prefix to cache, and D has a prefix that changes every request, so neither can hit at any TTL.

**V1.19 — C and D.** Workspaces and API keys are the two real billing dimensions: the Cost API groups by `workspace_id`, and the Usage API filters and groups by `api_key_id` as well as workspace, model, service tier and context window. One workspace per tenant and one key per feature therefore gives authoritative per-tenant cost and per-feature usage with no bookkeeping of your own. A is wrong because `metadata.user_id` is an abuse-detection field and not a reporting dimension. B abuses a generation-control parameter, and E misuses the API version header; neither appears in any usage or cost breakdown.

**V1.20 — B and D.** The `diagnostics` object is the opt-in: the API stores a fingerprint only for requests that include it, which is why a missing fingerprint is reported rather than inferred. `cache_missed_input_tokens` is derived from byte lengths before tokenization, so it indicates the magnitude of lost prefix and can differ from, or exceed, `usage.input_tokens`. A is wrong because `previous_message_not_found` means no comparison was possible, not that the request changed. C is wrong because only the earliest divergence is reported, so later ones can hide behind it. E contradicts the documented best-effort guarantee that diagnostics never blocks or fails the request.

## Chapter 2 — Failure, Correctness, and Recovery

**V2.1 — A.** The Messages API has no idempotency key, so a retry is an entirely new request as far as the platform is concerned. A client-side timeout near the ten-minute non-streaming ceiling is exactly the condition under which the original most likely *did* complete server-side, with the response body simply never arriving — so the model generated twice, you are billed twice, and the tool loop’s payment side effect runs twice. B is exactly the assumption that causes the duplicate, since a client-side timeout says nothing about whether the server completed the work. C claims a deduplication behaviour that does not exist, and D invents a 409 for in-flight requests; `conflict_error` concerns resource state, not concurrent message creation.

**V2.2 — B.** `model_context_window_exceeded` is a stop reason on a successful 200 response, indicating that generation filled the model’s context window rather than your own ceiling. Raising `max_tokens` cannot help, because the binding constraint is not yours; the recoveries are compaction, context editing such as clearing old tool results or thinking blocks, trimming history, or surfacing the truncation. A is the single most common misdiagnosis, C retries an entirely deterministic condition, and D reduces output volume without addressing the fact that the window is already full of input.

**V2.3 — D.** The spend-cap 429 is distinguished by `error.details.error_code` of `enforced_spend_limit_reached`, carries no `retry-after`, and continues to fail until access resumes at 00:00 UTC on the first of the next month or the usage tier is raised. It is therefore permanent for the current billing period and must be excluded from the retry path before any backoff logic runs. A retries a condition that cannot succeed, C treats a billing state as a rate-shaping problem, and B both retries and misuses a capacity breaker; the cap is organization-wide, so another model offers no relief.

**V2.4 — A and C.** A 429 is a quota you exceeded, with a refill rate that is often stated exactly in `retry-after` and a bucket that belongs to your organization alone, so there is no cross-client contention to decorrelate and the header should be honoured precisely. A 529 is broadcast to every client at once, which makes full jitter essential to avoid synchronised retry waves, rarely carries a header, and needs a longer synthetic base because recovery is measured in seconds. B and D invert the correct responses: 529 is the overload signal that should trip a breaker and shed load, while 429 is the signal that should lower the sustained target rate. E discards legitimate retries on both.

**V2.5 — C.** The absence of `message_stop` is the only reliable indicator that a stream did not complete, and with 6,000 characters already received the work is worth preserving. On Claude 4.6 and later the documented resumption shape is a *user* message quoting the tail and asking the model to continue, because prefilling the assistant turn returns a 400 on current models — which is exactly why D is wrong. A treats a partial as complete and will silently ship truncated output, and B discards paid-for work that is recoverable from a text block.

**V2.6 — C.** Tool use and thinking blocks cannot be partially recovered; resumption is possible only from the most recent complete text block. Accumulated `input_json_delta` fragments are a partial JSON string that is meant to be parsed at `content_block_stop`, and 80% of a JSON document is not a document. A would execute a tool with invented arguments, which is the worst available outcome. B asks the model to continue a structure it cannot resume, and D fabricates a `tool_result` for a `tool_use` block whose id and arguments you do not reliably have.

**V2.7 — B.** A refusal arrives as `stop_reason: "refusal"` on an HTTP 200 response, you are billed for the tokens, and the refusal text may not conform to the schema even when `output_config.format` is set — it is one of the documented exceptions to the compliance guarantee. `stop_details` carries the policy category, and the documented recovery is to retry on a fallback model or rephrase, noting that Haiku 5.5 has no server-side fallback so the retry must live in your client. A and D misclassify it as an error or a rate-limit state, and C asserts a guarantee the docs explicitly qualify.

**V2.8 — C and D.** Repair is appropriate only when the correct value is computable without guessing. An enum returned as `"In Progress"` where exactly one schema member matches under case folding has one unambiguous target, and enum casing drift is a documented failure mode with no error and no special stop reason, so normalising it is safe. Trailing whitespace is likewise a total, unambiguous transformation. A is a semantic violation whose correct value is unknown — and note that numeric bounds are not in the supported schema subset, so it is yours to check. B and E both require inventing data.

**V2.9 — C.** The official SDKs retry transient failures twice by default, so each of your three attempts can become three requests, for a worst case of nine. This is the usual reason a retry-budget calculation is wrong by a factor of three, and the fix is to set `max_retries=0` when you own the policy layer. A counts only your own attempts, D would be the result if the SDK retried once, and B corresponds to no combination of the two layers.

**V2.10 — D.** When `stop_reason` is `max_tokens` and the final block is an incomplete `tool_use`, the documented recovery is to retry with a higher `max_tokens`: the partial tool arguments are unusable, and no continuation can repair them. A is the correct recovery for a truncated *text* response but not for a truncated tool call, because the partial block cannot be replayed as valid assistant content. C executes a tool on fabricated input, and B removes the tool from consideration entirely, changing the request’s meaning rather than recovering it.

**V2.11 — B.** `pause_turn` means a server-tool loop reached its iteration limit, ten by default, and the documented continuation is to send the assistant’s content back unchanged so Claude can carry on. The necessary safeguard is a cap on continuations, because a pathological loop will otherwise continue indefinitely at full price. A discards the work already done by resending the original request, C addresses a ceiling that is not the constraint, and D treats a normal continuation signal as a policy refusal.

**V2.12 — A and B.** An effort drop reduces the number of output tokens across the whole response — text, tool calls and thinking alike — so the median output tokens for a fixed prompt distribution falls sharply with no deploy, and the reasoning share of output tokens, visible as `gen_ai.usage.reasoning.output_tokens`, collapses. Both move without any error being raised. C is precisely the blind spot: the error rate is unchanged because nothing failed. D detects prefix instability, which is unrelated, and E is a capacity metric that an effort drop would if anything improve.

**V2.13 — A.** Latency improving with no deploy is a symptom, not good news: the usual cause is that responses got shorter, which happens when a model’s default effort level changes or a router moved traffic to a different model. Comparing the model ID distribution against output-token medians per feature identifies both in one query, and it is exactly how the quiet-summariser regression in the case studies was found. B acts on the symptom and removes the headroom you will need when the regression is fixed, C addresses truncation that the unchanged `max_tokens` rate rules out, and D is how a regression reaches customers for eleven days.

**V2.14 — A.** If the input alone exceeds the context window, the API returns HTTP 400 `invalid_request_error` before generation begins, on every model. If input plus `max_tokens` exceeds the window, Claude 4.5 and newer accept the request and signal the constraint afterwards as `stop_reason: "model_context_window_exceeded"` on a 200 response. The status code therefore separates the two cleanly. B requires knowing the window and still cannot distinguish the two cases at the boundary, C is irrelevant to either, and D does not change which ceiling was binding.

**V2.15 — D.** Deduplication depends entirely on the operation ID being byte-identical between a call and its retry, so any per-request value inside the hashed body — an interpolated timestamp, a freshly generated UUID, a non-deterministically serialised tool schema — silently defeats the whole design while appearing to work. This is the same prefix-stability discipline that prompt caching requires, which is a convenient alignment rather than a coincidence. A is not a practical concern for SHA-256, C is trivially solved by truncating the digest, and B is harmless: `max_tokens` is stable across a retry of the same logical call.

**V2.16 — B and D.** The rule is that the log record describes the request and never its contents, which excludes the system prompt text and any tool result payloads along with prompts, completions and tool arguments. What remains is more than enough: the `request-id` header is the only identifier Anthropic can look up and must be logged unconditionally, the full `usage` object drives cost and cache-efficiency analysis, and the error `type` is the stable classification key — unlike the message string, which is prose and will change. Content fingerprints give you cache-miss forensics without storing anything reversible.

**V2.17 — B.** The `usage` values carried on `message_delta` events are cumulative, not incremental, so the correct accumulation is to take the last value observed. Summing them inflates the count by roughly the number of delta events, which is one of the three classic causes of a ledger that disagrees with the Cost API. C is wrong because `message_start` carries a `Message` with empty content and incomplete accounting, and D is arithmetically meaningless for a monotonically increasing series.

**V2.18 — C.** Changing the subject model and the judge model in one release makes the result unattributable: a score movement could come from either, or from both in opposite directions. The discipline is to pin the judge across evaluations and vary one thing at a time; a golden set is only a regression detector if the measuring instrument holds still. A asserts one of the two possible explanations as if it were established, B rejects a standard and effective technique, and D confuses the execution mode with the measurement — a batch is the right place to run a golden set, being half price and not latency-sensitive.

**V2.19 — B and D.** A refusal is returned with HTTP 200 and is billed, so monitoring that keys on status codes alone never sees it. An error delivered as an SSE `error` event arrives after a 200 and after headers were sent, which is why the docs note that standard retry handling does not apply to mid-stream errors and your consumer must inspect event types. A, C and E are all ordinary non-2xx responses: 413 for an oversized request, 529 for overload on a non-streaming call, and 400 for an unsupported schema feature, each visible to status-code monitoring.

**V2.20 — A.** The design error is the failure classification, not the threshold: a breaker that counts deterministic 400 responses as capacity failures lets a malformed tool schema in one code path take down every feature sharing the model. The signal a breaker should respond to is capacity loss — 529, 500, timeouts, connection resets — while 4xx is a deterministic bug and 429 is a scheduling instruction that belongs in the limiter. B treats a correct trip as a tuning problem. C is partly useful as defence in depth but does not fix the misclassification, and D removes the recovery path without addressing the cause.
