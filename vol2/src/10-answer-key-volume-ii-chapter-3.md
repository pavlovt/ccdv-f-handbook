# Answer Key: Volume II Chapter 3

**V3.1 — A.** Cost the prefix symbolically with base input rate `p`. At 80% hit with 5-minute entries: reads `0.8 × 6,000 = 4,800` at 0.1x gives `480p`, writes `0.2 × 6,000 = 1,200` at 1.25x gives `1,500p`, total `1,980p` per request. At 97% hit with one-hour entries: reads `5,820` at 0.1x gives `582p`, writes `180` at 2x gives `360p`, total `942p`. Cost falls by 52% despite the write multiplier rising from 1.25x to 2x, because write volume dropped by 85% and writes are 12.5x the per-token rate of reads. The lesson generalises: on a large reusable prefix, hit rate dominates TTL multiplier, which is why the one-hour TTL is the default recommendation for batch and for long-lived sessions.

**V3.2 — B.** Prompt length for Haiku 5.5 tiering is the sum of all input categories — fresh, cache writes and cache reads alike. The request was `94,000 + 4,000 = 98,000` tokens, inside tier 1; adding 8,000 cached tokens makes it 106,000 and the whole request reprices at the \>100K tier. Every category’s rate multiplies by 5: input \$0.10→\$0.50, output \$0.50→\$2.50, reads \$0.01→\$0.05. The old bill was roughly `94,000×0.01 + 4,000×0.10 + 2,000×0.50` per MTok = \$0.00234; the new one is roughly `102,000×0.05 + 4,000×0.50 + 2,000×2.50` = \$0.0121, a 5.2x increase caused entirely by a “free” cached block. C is wrong because tiering is not marginal — it reprices the entire request.

**V3.3 — D.** The discordant pairs are what carry information: 31 where the candidate alone is right, 14 where the incumbent alone is right, 45 informative items. McNemar’s statistic with continuity correction is `(|31 − 14| − 1)² / (31 + 14) = 16² / 45 = 256/45 = 5.69`, which exceeds the 3.841 critical value at α = 0.05. The 455 agreements genuinely carry no signal and correctly drop out of the test. A misapplies the independent-sample sizing of \~370 per arm; paired designs are far more efficient precisely because they discard the agreements, which is why you should always run both models over the same frozen item set.

**V3.4 — A.** Break-even is where the cascade’s total equals the expensive stage alone: `c_cheap + overhead + p·c_exp = c_exp`, so `p* = 1 − (c_cheap + overhead)/c_exp`. Substituting: `p* = 1 − (0.00040 + 0.00002)/0.00250 = 1 − 0.00042/0.00250 = 1 − 0.168 = 0.832`, about 83%. C inverts the quantity — 16.8% is the cost ratio, not the break-even fraction. Note how generous the real limit is: a cascade designed to escalate 20% of traffic is operating at roughly a quarter of its economic ceiling, so when a cascade disappoints, the cause is nearly always gate quality or tail latency rather than the cost ratio.

**V3.5 — C.** A join that waits for all subcalls finishes at the maximum of the draws, so the aggregate succeeds within the single-call p99 only if every leaf does: `0.99¹⁵ = 0.860`, meaning about 14% of aggregate requests exceed 7.5 s. A is the classic error — parallelism bounds you by the slowest leaf, not the typical one, and `0.5¹⁵ ≈ 3 × 10⁻⁵` means the aggregate essentially never achieves the single-call median. D is wrong because hedging the slowest leaf with a duplicate request is one of the few effective tail-latency levers available: duplicating the slowest few percent costs a few percent more tokens and can cut aggregate p99 materially. The architectural consequence is that fan-out timeouts must be sized from aggregate p99, never from leaf p50.

**V3.6 — B.** Opus 5.5 defaults to `medium` effort, whereas Opus 5 defaults to `high`. A request that omits `output_config` therefore silently drops one effort level across a model change, and the resulting quality dip gets misattributed to the new model. The fix is to set `output_config: {"effort": ...}` explicitly on every production request and then run a fresh effort sweep rather than carrying settings over. D is false — `thinking: {"type": "adaptive"}` is the supported form on current models; it is the legacy `{"type": "enabled", "budget_tokens": N}` that returns 400 on 4.7+. C is false because a dateless 4.6+ ID is a fixed snapshot, not a floating alias.

**V3.7 — A and D.** Top-tier models carry deeper cache-read discounts — 0.025x on Fable 5.1 and 0.05x on Opus 5.5 and Sonnet 5.5 versus the general 0.1x — so in a workload where reads are the dominant token category the effective price ratio between tiers compresses well below the headline ratio (A). A 30-turn session over a 200,000-token corpus is read-dominated by construction, which shifts spend away from fresh input where the full headline ratio does apply (D). B is a true statement about current pricing but applies identically to both candidates, so it does not change their *relative* affordability. C is false: write multipliers are uniform at 1.25x and 2x across models. E is false: the Batch discount is a flat 50% everywhere.

**V3.8 — C.** Both prompts exceed 100K, so Haiku bills at tier 2. Haiku per attempt: `130,000 × 0.50/10⁶ + 3,000 × 2.50/10⁶ = $0.0650 + $0.0075 = $0.0725`. With a 30% pass rate, expected attempts `1/0.30 = 3.33`, so expected cost per accepted output is `3.33 × $0.0725 = $0.2417`. Sonnet: `130,000 × 2.00/10⁶ + 3,000 × 10.00/10⁶ = $0.2600 + $0.0300 = $0.2900`. Haiku still wins, but by only 1.2x — and since tier-2 Haiku is exactly 4x cheaper per token, the crossover sits at a 25% pass rate, meaning a few points of validator degradation would flip the decision while also adding latency and complexity.

**V3.9 — A.** Each chunk is `50,000 + 55,000 = 105,000` tokens, over the threshold, so all six pay tier-2 rates: `6 × 105,000 × 0.50/10⁶ = $0.3150` of input. The single monolithic request is also tier 2 but bills the corpus once: `300,000 × 0.50/10⁶ = $0.1500`. Chunking is therefore roughly 2.1x *more* expensive on input, because the 55,000-token overhead is paid six times and every chunk lands in the expensive rate class. This is the chunking trap: the fan-out looks like an optimisation and is a regression. Compressing the reference to under 50,000 tokens so each chunk stays in tier 1 would be worth far more than any other change available here.

**V3.10 — D.** Compute both. Real-time at 96%: `4,800 × 0.01 + 200 × 0.125 + 400 × 0.10 + 80 × 0.50` per MTok = `$0.000048 + $0.000025 + $0.00004 + $0.00004 = $0.000153`. Batch at 55%: `2,750 × 0.01 + 2,250 × 0.125 + 400 × 0.10 + 80 × 0.50 = $0.0000275 + $0.00028125 + $0.00004 + $0.00004 = $0.00038875`, halved to \$0.000194 — about 27% *more* than real-time. The 50% discount was consumed by moving 2,050 tokens per request from the 0.1x read column to the 1.25x write column, a 12.5x rate increase on those tokens. C is wrong: caching is supported in batch, just best-effort, which is exactly why a one-hour TTL is the correct configuration there.

**V3.11 — B and E.** Switching a request between `speed: "fast"` and standard invalidates the prompt cache, so the two speeds do not share cached prefixes and the first fast request pays a full write (B). Cost-per-minute-saved improves with output length because the input premium is a fixed overhead that only saved generation time amortises: a 200,000-input, 2,000-output request works out near \$2.52 per minute saved, while a 25,000-input, 60,000-output request is about \$0.13 — a 19x swing from the same feature on the same model (E). A is backwards: the gain is on output throughput, not TTFT. C is false — Fast mode is unavailable with the Batch API. D is false: weights and behaviour are unchanged, only the inference configuration differs.

**V3.12 — B.** Equate total cost of ownership: `0.00018 × 5,000,000 + 0.05 × 5,000,000 × c = 0.00190 × 5,000,000 + 0.02 × 5,000,000 × c`, i.e. `900 + 250,000c = 9,500 + 100,000c`. Rearranging, `150,000c = 8,600`, so `c = $0.0573`. Above about 5.7 cents per error, the more expensive and more accurate model is cheaper overall. This is the central discipline: the error term carries the same volume multiplier as the token term but usually a much larger coefficient, so at five million requests a month the inference bill is frequently not the dominant line in the decision.

**V3.13 — B.** At n = 80 and accuracy near 0.92, the standard error is `sqrt(0.92 × 0.08 / 80) = sqrt(0.00092) = 0.0303`, giving a 95% half-width of about ±5.9 points on each arm. A 2.5-point observed difference sits well inside that interval, so the result is indistinguishable from noise and neither A nor C is supported by the evidence. Decide only on differences larger than your confidence interval; here you either need several hundred items or a paired design that discards agreements. D is simply false — running both effort levels over the same frozen item set is exactly the right design.

**V3.14 — D.** Streaming changes when the first token reaches the consumer; it does not change total generation time, token count or cost. A consumer that must parse a complete JSON object cannot act until the final token arrives, and that moment is unchanged, so end-to-end p99 is unchanged. Streaming is a perceived-latency lever for human readers, not a measured-latency lever for machine consumers. For backend pipelines the levers that actually move p99 are prefill reduction through caching or prompt shortening, output reduction through effort or prompting, and concurrency control on the queueing term. Streaming does retain one real engineering benefit even here: it makes a stalled long generation observable so you can abort instead of paying for tokens you discard.

**V3.15 — C and E.** Mean latency is `350 + 0.20 × 2,900 = 350 + 580 = 930 ms`, a large improvement over 2,900 ms expensive-only (C). But the escalated path runs both stages serially at `350 + 2,900 = 3,250 ms`, and since 20% of traffic takes it, every percentile above roughly the 80th is now worse than it was before the cascade existed (E). A is false because the tail gets worse, not better, and B is false for the same reason; D misstates the escalated path, which is the sum of both stages rather than the expensive stage alone. The architectural point is that a cascade can succeed on a mean-latency objective while failing a p95 or p99 SLO, so you must pick the percentile before you build.

**V3.16 — A.** Shadow spend is `sample_rate × volume × c_candidate = 0.04 × 10,000,000 × $0.00310 = $1,240` per month, against production’s `10,000,000 × $0.00021 = $2,100`. The shadow is 59% of the production bill — material, and almost entirely wasted, because reaching a few hundred paired items from ten million requests needs a sample rate on the order of 0.005%, not 4%. The correct sample rate is the smallest one that reaches your required `n` inside your decision window. Note also that a low sample rate means the shadow’s own cache mostly misses, so its per-request cost runs higher than production’s would for the same model — project production cost from token counts and your real hit rate, never from the shadow’s bill.

**V3.17 — C.** The request sits at 97,500 tokens, 2,500 below the threshold, so adding 5,000 tokens pushes it to 102,500 and reprices the entire request at 5x. With a 2,000-token output, the before cost is roughly `97,500 × 0.10/10⁶ + 2,000 × 0.50/10⁶ = $0.01075` and the after cost is roughly `102,500 × 0.50/10⁶ + 2,000 × 2.50/10⁶ = $0.0563`. The marginal cost of those 5,000 tokens is \$0.0455, an effective rate of about \$9.10 per MTok — 91 times the tier-1 input rate, and above every published input rate except Fable 5.1’s \$10. D is the seductive wrong answer: tiering is not marginal, so there is no “first 97,500 stay cheap.” On Haiku, 100,000 tokens is a hard budget line, not a soft guideline.

**V3.18 — D.** From 4.6 onward, model IDs are dateless and each maps to a single fixed snapshot; Anthropic does not update weights or configuration behind an existing ID, and new versions ship under new IDs. It is the pre-4.6 undated strings such as `claude-sonnet-4-5` that are convenience aliases floating to the latest dated snapshot for that minor version. So `claude-sonnet-4-6` is already pinned and your colleague has the relationship backwards. One caveat worth keeping: serving infrastructure such as routing and safety classifiers can change even on a fixed ID, so continue monitoring production outputs — a fixed ID guarantees stable weights, not stable observed behaviour.

**V3.19 — B and C.** Hard signals — schema-parse failures and validator or business-rule violations — are deterministic, essentially free to compute, and have no false positives, so they belong in every cascade (B). With a 20x tier gap, self-consistency over three cheap samples costs `3 × c_cheap`, still only 15% of the expensive stage, and the break-even on sampling sits at `n = 20`, so triple-sampling is comfortably affordable and typically catches more of the cheap model’s error set than a self-reported score does (C). A is poor practice because self-reported confidence is badly calibrated until you fit a threshold on held-out data. D destroys the cascade’s value: random escalation gives you the cheap model’s error rate on 80% of traffic for the same price as a calibrated gate. E abandons the strongest signals available, since input features alone cannot see the answer.

**V3.20 — B.** The monthly spread is `300 × ($1.35 − $0.14) = $363`, against an error cost of roughly €20,000 for a single miss. The ratio `monthly_spread / cost_of_one_bad_output` is about 0.018 — far below 1 — so cost optimisation cannot plausibly pay for itself and the only thing that can hurt you is a quality failure. Choose the most capable configuration your evals support and redirect the engineering effort into eval coverage, which is where your evidence is thinnest. A and C add complexity and risk for savings smaller than a few hours of engineering time; D is the wrong tool, since halving \$405 is irrelevant and a 24-hour turnaround is poor compensation for it.

**V3.21 — A.** Compare tier-2 Haiku to Sonnet 5.5 directly: input `$0.50 / $2.00 = 0.25` and output `$2.50 / $10.00 = 0.25`. The ratio is exactly 0.25 on both axes, and the read multiples work out the same way because Haiku’s tier-2 read rate of \$0.05 is 0.1x its \$0.50 input rate while Sonnet reads at 0.05x its \$2.00 rate, giving \$0.10 — again 4x. So tier-2 Haiku is always precisely 4x cheaper for identical token counts and the cliff never reverses the ordering. Haiku becomes more expensive only when it consumes more than four times the tokens, through retry loops, effort inflation, or chunking overhead — which is exactly why the cliff shrinks your retry budget from 20 attempts to 4.

**V3.22 — A and D.** Batch results are available once all requests finish or at 24 hours, and queueing routinely exceeds a few minutes, so a 5-minute TTL will mostly have expired by the time later requests are processed; the one-hour TTL is the documented recommendation for batch (A). Batch results also return in arbitrary order and `custom_id` is the only join key, so omitting meaningful ids makes reliable matching impossible — encode your primary key there, within the `^[a-zA-Z0-9_-]{1,64}$` constraint (D). B is wrong: 60,000 is well inside the 100,000-request limit. C is backwards — `params` validation is asynchronous and surfaces only after processing, which is why you should dry-run one request through the Messages API first. E is wrong: expired requests are not billed.

**V3.23 — C.** End-to-end wall time is a sum of three terms with three different levers — queueing from rate limits and retries, prefill from prompt tokens and cache state, and generation from output tokens divided by throughput — and you cannot tell which one moved without decomposing it. Recording TTFT separates queue plus prefill from generation, output tokens and OTPS isolate the generation term, and cache-hit state explains prefill swings. A, B and D each pick a lever before identifying the term: streaming would not change total latency at all, lowering effort only helps if generation dominates, and Fast mode improves output throughput rather than queueing or prefill. A 2.4x p99 regression with no code change most often turns out to be a cache hit-rate collapse or a retry storm, and both are invisible in a single wall-time number.

**V3.24 — C and D.** The 1.1x multiplier applies to every token category — input, output, cache writes and cache reads, including Haiku 5.5’s tier-2 rates — so in a read-dominated long-context workload the premium lands squarely on the largest line item and no caching strategy avoids it (C). Because `inference_geo` is a per-request parameter, you can scope it to the regulated slice of traffic rather than paying 10% across the whole workload (D). A is false for exactly the reason C is true. B is wrong and dangerous: models before 4.6 do not support the parameter and return a 400 rather than ignoring it. E is wrong — Bedrock and Google Cloud regional endpoints carry their own roughly 10% premium over global endpoints.

**V3.25 — D.** The window from 2026-09-30 to 2026-11-30 is 61 days, barely above the 60-day minimum notice commitment, and it must absorb benchmark construction, an offline paired comparison and effort sweep, a shadow run long enough to accumulate an adequate discordant-pair count, prompt and configuration work for the new model’s different effort default, a staged rollout with rollback capability, and buffer.
