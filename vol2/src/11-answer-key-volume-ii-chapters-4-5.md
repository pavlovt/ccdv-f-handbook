# Answer Key: Volume II Chapters 4–5

## Chapter 4 — Agent Engineering

**V4.1 — D.** The budget cap is enforced after a response arrives, because the cost of that response is only known from the token usage the API returns with it. The response that pushes accumulated spend past the cap has therefore already been generated and billed, so the total can exceed the cap by up to that one response’s cost. Any subagents still running when the cap trips also keep spending until they are stopped, which adds further overshoot. A is wrong because subagent spend explicitly counts toward the cap; the practical rule is to set the cap below the figure you genuinely cannot exceed.

**V4.2 — C.** Turn *n* sends `P + (n-1)·g` input tokens, so a run of `N` turns sends `N·P + g·N(N-1)/2` in total. With `P = 12,000`, `g = 2,500` and `N = 30`, that is `360,000 + 2,500 × 435 = 360,000 + 1,087,500 = 1,447,500`. Option A is the linear-only term and B is a plausible-looking round number; D roughly doubles the quadratic term. The point of the calculation is that the quadratic component — 1.09M tokens — dwarfs the 360K the prefix contributes.

**V4.3 — A.** “Be concise” is a style request, and the model satisfies it relative to what it has just read, which is why a worker that read five large files still returns thousands of tokens. A required output structure that caps total words and explicitly forbids pasting source text converts the instruction into a shape the model must fill, and shapes are obeyed far more reliably than adjectives. Lowering `maxTurns` (B) reduces the work done, not the verbosity of the report. A smaller model (C) is not reliably terser, and clearing the worker’s own context (D) changes what it can quote but not its instinct to quote.

**V4.4 — A.** Removing the tool from the orchestrator’s tool set is a guarantee; instructing it not to use the tool is a suggestion that will eventually be ignored, usually with the reasoning that this one page is worth a quick look. Once a 12,000-token page is in the orchestrator’s transcript it is re-sent on every remaining turn, so a single lapse has a cost proportional to the turns that follow it. B merely restates an instruction that is already failing, C reduces opportunity without removing capability, and D pays for the pages first and summarises them afterwards.

**V4.5 — C.** Four consecutive identical failures mean the model has no corrective action available, and every further attempt costs a full turn’s worth of accumulated context for zero progress. Opening a circuit on that tool — returning a result that says it is disabled, instructs the model not to call it again, and tells it to proceed or report the gap — preserves the remaining budget for work that can succeed. A keeps paying for the same failure, B discards everything the run has achieved, and D converts a token leak into a wall-clock leak. The counter should be per tool name and reset on any success, so an intermittent tool is not banned permanently.

**V4.6 — D.** The second call has the same arguments but a different key order, so a fingerprint built from a raw JSON dump produces a different hash and the detector sees three distinct calls. Canonicalising with sorted keys before hashing makes all three identical, which is exactly why the detector in §4.1 uses `json.dumps(call.input, sort_keys=True)`. A window larger than three would also fail to fire, but that is a tuning choice rather than the bug; B is false, since fingerprints are recorded per call regardless of batching; D’s alternative in C would prevent any loop detection from ever working, which is not the described symptom.

**V4.7 — B.** `max_turns` counts tool-use round trips, so the final text-only response that ends the loop is not a turn. In the canonical four-response example — test, read, edit-and-retest, then a text summary — three turns are counted. A turn can contain several parallel tool calls and still counts once, which rules out C. With streaming input, a message queued when a turn hits the limit starts a new turn with the count restarting, so the cap is not a session-lifetime total as D claims.

**V4.8 — A.** This is the specificity-gap case, not a genuine contradiction: A cites a named dashboard panel and a number, while B offers a general assertion sourced from marketing material. The policy prefers the specific claim and records the general one as a caveat, which costs nothing and keeps the disagreement visible. B is wrong because adjudication is reserved for two claims that are both specific and both confident; spending a worker here buys nothing. C discards a resolvable answer, and D averages confidences that are not commensurable.

**V4.9 — C.** The run has changed phase: gathering is finished and writing has begun, and the writing phase needs the distilled findings rather than the raw evidence that produced them. A handoff is the only option that resets the accumulated context entirely, and it is also the only one where you choose what survives rather than delegating that choice to a summariser or a `keep` count. A inverts the reasoning — the report needs the conclusions, not the transcripts. B is false, since a session can be resumed or forked from its `session_id`; D leaves the decision to a mechanism with no knowledge of your phase boundary.

**V4.10 — B.** Agents regress on efficiency silently: a prompt change that adds several turns to every run passes every correctness assertion while multiplying the bill. Per-case assertions on turns and cost, run over several repetitions so the stochastic spread is visible, are the only thing that turns that regression into a test failure. Forbidden-tool assertions (A) catch dangerous routes rather than expensive ones, counterfactual cases (C) catch poor refusal behaviour, and mocks versus real state (D) affects error-path coverage — all worth having, but none of them detect a 2.6x cost rise.

**V4.11 — D.** A `defer` decision ends the turn with `stop_reason` of `tool_deferred`, leaving the call pending so it can be resumed once a human has decided. That is what makes deferral the right primitive for a fleet: the run yields instead of holding a process open waiting for an approval, so throughput is bounded by work rather than by open approvals. A describes a withheld result, which is not what the mechanism does; B describes `deny`; C describes a queue that auto-executes, which would defeat the purpose of asking.

**V4.12 — B.** At 40 turns the cached run costs about \$1.49, of which cache reads of the accumulated prefix account for roughly \$0.46 — close to a third. The fraction is not constant: at 10 turns it is around a tenth, and by 80 turns it has grown to nearly half, because the prefix being re-read grows linearly while the per-turn write and output stay flat. That trajectory is the quadratic term reasserting itself through the cache-read line, which is why caching changes the constant but not the shape of the curve.

**V4.13 — C.** `CLAUDE_CODE_MAX_CONCURRENT_SUBAGENTS` caps how many subagents may run at once, and an attempt past it returns to the model as a tool result reading `Concurrent subagent limit reached` rather than as an exception. The fixes are to raise the limit or to have the orchestrator fan out in batches that fit under it. A budget trip would say `Budget limit reached` and would also stop running background subagents, and the depth limit governs nesting rather than simultaneity, so B is a different control entirely. D confuses subagent concurrency with parallel tool calls inside a single turn.

**V4.14 — A.** Compaction replaces older history with a model-written summary, and the summariser decides what mattered — so the task list and, critically, the record of approaches that already failed are exactly the content that can be paraphrased into uselessness. A fresh or compacted agent with no memory of what failed will re-attempt the broken endpoint and pay for the same dead end again. Raw early tool results (B) are expendable by design; reasoning about source reliability (C) is valuable but inherently fuzzy; system prompts and tool definitions (D) are re-sent on every request and are never at risk.

**V4.15 — B.** A run that reached 80% completion has produced most of its value, and that value is collectible only if something outside the transcript recorded it. Returning the persisted task-state brief plus the `session_id` lets the work be resumed with full context, or reconstructed by a fresh agent from the brief alone. A discards everything and pays for it again; C re-runs blindly without addressing why the cap was reached, and may hit it again; D changes cost without changing the structural problem.

**V4.16 — B and D.** The quadratic term comes from re-sending accumulated history, so only changes that stop history from accumulating in the costly context attack the exponent. Delegating a 15-turn investigation keeps that transcript inside the worker and adds just the 800-token brief to the parent, and ending the run to start fresh resets the accumulation to zero. Prompt caching (A) and truncating tool results (C) are large wins on the coefficient — caching changes the price per re-sent token, truncation halves `g` — but the growth remains quadratic. Cheaper workers (E) reduce the price of the delegated work without altering the parent’s growth.

**V4.17 — D and E.** Plan churn is defined by the absence of convergence rather than by repetition: tool calls are all distinct, nothing contradicts, and yet no task closes and no finding is added. Detecting it therefore requires your task state, not your call fingerprints — four turns with no completion, or an unchanging task-list length across six active turns, are the signals. A is identical repetition and B is cycling, both of which fingerprint checks catch. C is an oscillating write, detectable only on content hashes.

**V4.18 — C and D.** Context editing operates server-side, clearing selected content from the history before the prompt reaches the model while your client retains the full, unmodified transcript. `exclude_tools` names tools whose uses and results are never cleared, so listing the memory tool there keeps the agent’s own saved notes while the raw searches that produced them are discarded — the “clear the evidence, keep the conclusions” pattern. A reverses the required order: `clear_thinking_20251015` must be listed first when both edits are used. B is wrong because the model must deliberately save what it wants to keep, and E inverts the facts — clearing does invalidate cached prefixes, which is precisely why `clear_at_least` exists.

**V4.19 — A and C.** Both designs reduce the number of human decisions without removing the human from the consequential ones. Plan-mode approval puts one decision in front of a reviewer who sees the whole shape of the work, which is where the real errors live; consequence-gating lets reads and searches run at API speed and reserves attention for irreversible or externally visible effects. B adds human latency to every turn and reliably decays into rubber-stamping, which manufactures the appearance of oversight. D removes oversight during the run entirely, and E gates by position in the run rather than by risk, so the dangerous twentieth call runs unreviewed.

**V4.20 — A and E.** `turn_limit` and `budget_limit` look alike in a dashboard and imply opposite remedies: turns usually ran out on a tractable task that needs a higher cap, while budget usually ran out because context grew and the fix is to reduce tokens per turn. `tool_circuit_open` and `no_progress` are likewise easily conflated and differently actionable — a broken dependency versus an agent that has stopped converging. B, C and D each pair an error with a non-error or with an unrelated state, so the distinction is not the subtle one the question is about.

## Chapter 5 — Tool and MCP Design at Depth

**V5.1 — A.** The hazard of splitting a pair of tools is never the extra round trip; it is the model inventing the identifier that links them. The reliable fix is to make the first tool’s result contain the ID in exactly the form the second tool requires, prominently enough that the model uses it verbatim — a result reading `project_id: "prj_8831"` produces `prj_8831`, while one reading “Mobile App (project 8831)” eventually produces `mobile-app`. Restating the requirement in prose (B) does not supply the value. Merging (C) is defensible but gives up the intermediate result and introduces ambiguity handling; `strict: true` (D) enforces that the argument is a string, which it already was.

**V5.2 — B.** At least one tool must be non-deferred, because the model needs something callable in its initial context; a request where every tool is deferred returns a 400. The practical guidance is to keep the three to five most frequently used tools resident and defer the long tail. Both search variants support deferred tools, so A is false; `defer_loading` must never be set on the search tool itself, making C the opposite of correct; and the deferred limit is 10,000 per request, far above 240.

**V5.3 — D.** No schema can express “this tool is the wrong instrument for your question”, which is exactly the knowledge the model is missing. Stating the downsampling — at most 200 points, so a 30-day window yields roughly 3.5-hour buckets — tells the model that a 30-second spike is invisible at that resolution, and it will reach for a narrower window or a different tool. An `enum` on `window` (A) fixes the format problem, not the resolution problem. Requiring `service` (B) fixes the silent-aggregate problem, and `strict: true` (C) guarantees conformance to a schema that never encoded this constraint.

**V5.4 — D.** A `oneOf` of per-channel branches, each discriminated by a `const` on `channel` and naming only its own fields with `additionalProperties: false`, makes the invalid combination structurally impossible rather than merely documented. The per-channel body limit can live in each branch too, which prose cannot enforce. Marking all destination fields required (A) makes every call invalid; `additionalProperties: false` alone (B) rejects invented fields but still permits `email` alongside `channel: "sms"`, since both are declared; and `strict: true` (C) enforces the existing schema faithfully, including its permissiveness.

**V5.5 — B.** Strict mode constrains token sampling against your schema, so the `input` conforms — correct types, required fields present — and the tool `name` is always one you supplied. That removes the validate-and-retry cycle for malformed arguments. It says nothing about semantics: a strict schema will cheerfully accept a correctly-typed customer ID that does not exist, so A is wrong and handler-side validation with a steering error message is still required. C describes `tool_choice`, and no automatic retry layer exists, ruling out D.

**V5.6 — A.** Silent truncation is the worst available failure mode because the model cannot detect it: twenty rows with no further information read as the complete answer, and the model proceeds to reason confidently from a fifth of the data. Stating the total first, then naming what is not shown and how to get it, converts a wrong answer into a next action. Exhaustive paging (C) is a real but lesser failure, and one that announcing the paging cost largely prevents. B and D are behaviours the model rarely exhibits on an apparently successful result.

**V5.7 — A.** A good error message names what went wrong, states whether anything changed, and gives a concrete corrective action — all three are present here: the 30-second limit, the explicit statement that nothing was modified, and a specific narrowing with a one-retry bound. Whether the failed call had an effect is the single most important fact for an agent deciding whether a retry is safe. B and C give the model nothing to act on, so it retries the identical call. D is diagnostic detail for a human reading logs and offers no corrective action.

**V5.8 — C.** The 2026-07-28 revision removed protocol-level sessions and the `Mcp-Session-Id` header, so a server needing cross-call state must mint explicit handles and have clients pass them back as ordinary tool arguments. This is what makes a conforming server horizontally scalable by construction: any two requests may land on different processes, so in-memory per-connection state is a bug. A names the removed header, B names the removed handshake — every request now carries its version and capabilities in `_meta` — and D describes a notification stream, not a state mechanism.

**V5.9 — D.** A resource is addressable read-only content the host or user can pull into context by URI, and the distinction turns on who initiates and whether a decision is involved. A fixed service catalogue is content a human might reasonably pick from a list and attach, with no arguments and no effects, so it is a resource. A and C are functions the model invokes with arguments, one read-only and one with company-wide effects. B requires an ID obtained from a prior search, which makes it a decision in a sequence — a tool, not something a user would browse.

**V5.10 — D.** A denylist enables everything by default, so a tool the vendor ships after you wrote your `configs` block is live the moment it appears. That is a bet that you can enumerate every dangerous tool the vendor will ever release, and the vendor controls when you lose it. The allowlist shape — `default_config.enabled: false` plus per-tool `enabled: true` entries — is the one configuration decision worth being dogmatic about. Note also that an unknown tool name in `configs` produces a warning rather than an error, so a typo in an allowlist silently disables a tool you meant to enable.

**V5.11 — C.** Returning the original refund ID while stating explicitly that no second refund was made closes the loop: the model learns the desired state already holds and moves on. Refusing with an error (A) teaches it that something went wrong, and a model trying to fix a problem may reach the same outcome by a different route — occasionally issuing a second refund through another path. B is the failure the idempotency key exists to prevent, and an empty result (D) leaves the model unable to tell success from silence. Idempotence is as much about what the tool says as about what it does.

**V5.12 — B.** Selection accuracy degrades past roughly 30 to 50 visible tools, and 14,000 tokens of definitions are re-sent on every request, so the problem is surface size rather than description quality. Tool search with `defer_loading: true` on all but the few tools used on nearly every request typically cuts definition tokens by over 85% while keeping only a focused set in context; consistent namespacing makes the catalogue searchable. Longer descriptions (A) make the context problem worse. Forcing `tool_choice: any` (C) guarantees a call, not a correct one, and returns 400 on current models. Merging into coarse tools with mode parameters (D) trades a selection problem for a harder argument-construction problem.

**V5.13 — A.** Roots, Sampling and MCP-level Logging are deprecated in the 2026-07-28 revision: they remain functional during the deprecation window, but new implementations should pass paths as tool parameters instead of Roots, call an LLM provider API directly instead of Sampling, and log to stderr or OpenTelemetry instead of Logging. Tools, resources and prompts are the core server features and are not going anywhere, ruling out B. Streamable HTTP is the recommended transport (HTTP+SSE is the deprecated one), and `server/discover` and `_meta` are new mandatory machinery in this very revision.

**V5.14 — C.** The request is well-formed but outside the tool’s contract, which is precisely when a tool should refuse rather than improvise. The refusal needs the limit, the value received, and an explicit statement that retrying with a larger window will not help — that last clause is what stops an agent burning two or three retries against a rule that will never yield. Silently clipping (A) lets the model reason as though it saw 900 days. Clipping with a note (B) is defensible but invites a retry, and an empty result (D) discards two years of usable history.

**V5.15 — B.** The spec asks servers to return `tools/list` in a deterministic order because unstable ordering defeats client-side caching and, downstream, lowers prompt-cache hit rates — the rendered tools section changes on every call even though nothing about the tools has. This is also why list results now carry `ttlMs` and `cacheScope`. No checksum validation exists (A), the model does not select by position (C), and `ttlMs` is a freshness hint unrelated to ordering (D).

**V5.16 — B and D.** Merging is indicated when the pair is a single indivisible step in practice — always called in immediate succession, with no branching on the intermediate result — and when splitting forces the model to carry an opaque identifier across a turn, which is a reliable source of hallucinated arguments. A is the clearest signal for keeping them split, since the model needs to see the intermediate result to decide. C argues for splitting so the two halves can receive different approval treatment, and E argues for splitting because a merged schema with mutually exclusive branches is harder for the model to fill correctly.

**V5.17 — A and C.** Deferred definitions are removed from the rendered tools section before the cache key is computed, so adding to the deferred set does not invalidate an existing cache entry — which is what makes a large catalogue cheap to grow. A deferred tool cannot carry `cache_control` (the request 400s), so the breakpoint belongs on a resident tool. B is wrong because every definition must be sent on every request; the API needs them to run searches and expand references. D is explicitly prohibited, and tool search is not billed as a separate server tool, so E is false — discovered definitions count as ordinary input tokens.

**V5.18 — B and C.** Restricting the tool set controls what the server can offer, not what its text can say. A tool description is instruction-shaped content that enters the model’s context before the user says anything, so a malicious description is a prompt injection through a trusted-looking channel. And a read-only server whose results steer the model into using *your* write tools needs no write capability of its own — the confused-deputy path is unaffected by any restriction on the vendor’s surface. A, D and E are operational concerns rather than trust failures. The strongest control for both remaining risks is architectural: put the untrusted server behind a worker that has no write tools.

**V5.19 — A and D.** Natural idempotence means repetition is harmless by construction, and the two properties that deliver it are a declarative setter rather than a delta, and convergence on the same end state however many times the call runs. `set_status(id, "closed")` has both. A delta such as `increment_counter(id)` (B) compounds on every retry and is the canonical counter-example. A unique generated identifier (C) makes duplicates detectable afterwards but does nothing to prevent the second effect, and erroring on a duplicate (E) is a mitigation bolted onto a non-idempotent operation — and a poor one, since it teaches the model that something went wrong.

**V5.20 — C and E.** A schema change that is technically valid but costs two extra turns is invisible to anything that inspects the tool surface rather than the model’s behaviour against it. Only running a real model and asserting on the trajectory surfaces it, whether that happens in the server’s own behavioural tests or as turn-count assertions in an agent eval suite exercising the server. A asserts on result text and passes unchanged. B asserts that the schema is what you intended, which it is — that is the whole problem. D measures server throughput, which the change does not affect.
