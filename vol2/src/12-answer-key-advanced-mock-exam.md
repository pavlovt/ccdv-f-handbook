## Section 1 — Applications and Integration

**A1 — C.** *(Applications and Integration)* Image tokens are counted in 28 x 28 pixel patches, with each dimension rounded up independently: tokens = ceil(w / 28) x ceil(h / 28). Image one: ceil(1130/28) = 41 and ceil(845/28) = 31, giving 41 x 31 = 1,271. Image two: 700/28 = 25 and 560/28 = 20 exactly, giving 500. Image three: ceil(340/28) = 13 and ceil(250/28) = 9, giving 117. The total is 1,271 + 500 + 117 = 1,888. Option A (1,796) comes from truncating instead of rounding up, B (1,827) from rounding up only one dimension, and D (2,048) is a plausible-looking power of two with no derivation behind it.

**A2 — A.** *(Applications and Integration)* Message prefilling is incompatible with constrained JSON output on current models, and prefilling the assistant turn on Claude 4.6 and later returns 400 regardless. The documented replacement is `output_config.format` with `type: "json_schema"`, which constrains the response with a compiled grammar rather than a hand-rolled prefill-and-stop trick. B is a real parameter that does influence verbosity, but a lower effort level does not guarantee parseable JSON and does not clear the 400. C compounds the original mistake: more stop sequences do not make a rejected prefill legal. D addresses truncation, which is a different failure mode and would not produce a 400 on every request.

**A3 — B, D.** *(Applications and Integration)* Two separate rules are being broken. At least one tool must stay non-deferred — a request in which every tool carries `defer_loading: true` returns 400 — which is D, and the documented advice is to keep the three to five most-used tools loaded up front. A deferred tool also cannot carry `cache_control`, so the breakpoint must move to a non-deferred tool, which is B; deferred tools are excluded from the system-prompt prefix anyway, so caching is preserved without it. A is false: the ceiling is 10,000 deferred tools per request, and 320 is nowhere near it. C is actively wrong — the search tool must never be deferred. E is a real knob (`limit` runs from 1 to 10,000, default 5) but raising it does not clear a 400.

**A4 — D.** *(Applications and Integration)* Work the three token streams separately at batch rates. Cache reads on Sonnet 5.5 are 0.05x the \$2 base input price, so \$0.10 per MTok, halved by the batch discount to \$0.05: 2,400 x 10,000 = 24 MTok x \$0.05 = \$1.20. Unique input bills at the batch input rate of \$1 per MTok: 150 x 10,000 = 1.5 MTok = \$1.50. Output bills at the batch rate of \$5 per MTok: 200 x 10,000 = 2 MTok = \$10.00. The total is \$1.20 + \$1.50 + \$10.00 = \$12.70. Option A omits the unique input, C uses the generic 0.1x cache multiplier instead of Sonnet 5.5’s 0.05x and forgets the batch discount on reads, and B drops the batch discount from one of the three streams.

**A5 — B.** *(Applications and Integration)* Uploaded files are scoped to the workspace, not to an end user or a session, so any API key with workspace access can read any file in it. Accepting a `file_id` from the client turns that into a cross-tenant read: a caller who guesses or replays another tenant’s ID gets that tenant’s document. The documented pattern is to treat file IDs as server-side references, keep the user-to-file mapping in your own application, and give each tenant its own workspace, up to 100 per organization. A, C and D are all true statements about the Files API — 90 days is the maximum expiry, uploaded files are not downloadable, and the rate limit is around 500 file-related requests per minute — but none of them is the security hole in this design.

**A6 — A.** *(Applications and Integration)* `pause_turn` means a server-tool sampling loop reached its iteration limit, which defaults to 10. The response is a legitimate waypoint, not a failure: append the assistant’s content to `messages` and call again so Claude can continue its own loop. B misreads it as truncation, which is `max_tokens`. C confuses it with client-side tool use: a response waiting on your tools carries `stop_reason: "tool_use"`, and you must not return a `tool_result` for a server tool’s call ID. D is wrong in its premise — `stop_reason` is available when streaming, in the `message_delta` event.

**A7 — C.** *(Applications and Integration)* `anyOf` is supported, and local `$ref`, `$def` and `definitions` are supported, so a composition resolving through a local reference compiles. The one documented exception is `allOf` combined with `$ref`. A and B name constraint families that are explicitly unsupported: numeric constraints (`minimum`, `maximum`, `multipleOf`) and string length constraints (`minLength`, `maxLength`) are both out, and SDK helpers move them into field descriptions instead. D is unsupported because recursive schemas cannot be compiled into a grammar.

**A8 — A, C, E.** *(Applications and Integration)* Tool definitions are billed as input tokens (A), the tool-use system prompt overhead is added to input on every request that carries `tools` — 286 tokens on Opus 5.5, Sonnet 5.5 and Haiku 5.5 with `auto` or `none` (C) — and `tool_result` content is billed as input when you send it back (E). B is wrong: `max_tokens` is a ceiling, not a charge, and it does not even count toward the output-tokens-per-minute limit. D is the trap: thinking tokens are real and billed, but as **output** tokens, visible in `usage.output_tokens_details.thinking_tokens`. F is wrong because breakpoints themselves cost nothing.

**A9 — B.** *(Applications and Integration)* Opus 5.5 bills input at \$4 per MTok, so 18,000 uncached tokens cost 0.018 x \$4 = \$0.072 per request. A 1-hour cache write is 2x base, \$8 per MTok, costing 0.018 x \$8 = \$0.144 once. A cache read on Opus 5.5 is 0.05x base, \$0.20 per MTok, costing 0.018 x \$0.20 = \$0.0036. For N requests, caching costs \$0.144 + (N - 1) x \$0.0036 and sending uncached costs \$0.072N; solving \$0.144 + \$0.0036(N - 1) \< \$0.072N gives \$0.1404 \< \$0.0684N, so N \> 2.05 and the third request is where caching wins. Option A (2) is the break-even you would get with the generic 1.25x write multiplier instead of 2x; C and D come from using the generic 0.1x read multiplier rather than Opus 5.5’s 0.05x.

**A10 — D.** *(Applications and Integration)* `input_json_delta` carries `partial_json` fragments for a `tool_use` block, and a fragment is not valid JSON on its own. You accumulate the fragments into a buffer and parse once, at `content_block_stop`, when the block is complete. A misstates the behaviour of eager input streaming, which makes streaming finer-grained rather than atomic; current models emit one complete key/value at a time, which is exactly why the naive code appears to work sometimes. B is wrong: the final `message_delta` carries `stop_reason`, `stop_sequence` and cumulative `usage`, not tool inputs. C would reduce the number of concurrent blocks but each one still arrives as fragments, so the crash would remain.

**A11 — A.** *(Applications and Integration)* Add the fixed overhead first: 12,000 for the system prompt, 9 x 450 = 4,050 for the tool definitions, 286 for the tool-use system prompt overhead on Sonnet 5.5 with `tool_choice` at its `auto` default, and 2,400 for the user brief, which totals 18,736 tokens. That leaves 200,000 - 18,736 = 181,264 tokens for conversation history, and 181,264 / 3,100 = 58.47. Fifty-eight round trips consume 58 x 3,100 = 179,800 tokens, leaving 1,464 tokens — not enough for a 59th — so 58 is the answer. Option C (59) takes the ceiling of the division instead of the floor, which overflows the window; B (62) drops the fixed overhead and divides 181,264 by 2,900-odd, or simply divides the full 200,000 by 3,100 and rounds down; and D (60) uses 406, the overhead for a forced `tool_choice`, and then rounds up rather than down.

**A12 — B, E.** *(Applications and Integration)* `max_tokens` means generation stopped at your output ceiling, and the content may end mid-structure — the documented recovery for a truncated `tool_use` block is to retry with a higher ceiling. `model_context_window_exceeded` means the response filled the model’s context window before reaching `max_tokens`, and the response should likewise be treated as truncated. `pause_turn` (A) is a waypoint in a server-tool loop, not a cut-off. `end_turn` (C) is a natural finish, `tool_use` (D) is a complete response requesting a tool, and `refusal` (F) returns complete text that happens not to match your schema, which is a validity problem rather than a truncation one.

**A13 — C.** *(Applications and Integration)* A spend-cap 429 is distinguished from an ordinary rate-limit 429 by `error.details.error_code` being `enforced_spend_limit_reached`, and it never carries `retry-after`. Retries, including the SDK’s automatic ones, keep failing until the limit is raised by moving to a higher tier or until access resumes at 00:00 UTC on the first of the next month, so the client should stop and surface the condition. A is the correct handling for an ordinary 429 but wastes requests here. B assumes a header that is absent. D describes the limits you set yourself, which do surface as HTTP 400 `invalid_request_error` — but this response is a 429.

**A14 — B.** *(Applications and Integration)* Enabling citations together with `output_config.format` returns 400: the two features are documented as incompatible in a single request. The workable design is two calls — one that produces cited prose, one that structures it. A is wrong because the Files API no longer needs a beta header at all. C is a genuine incompatibility in the API, but between citations and `output_config.format`, not between `strict: true` and citations; strict tools and JSON outputs are independent features that can be combined. D is false: a `document` block accepts a `file_id` source and citations work with it.

**A15 — B.** *(Applications and Integration)* Cache order is tools, then system, then messages, and a change at one level invalidates that level and everything after it. Putting a timestamp at the end of the system prompt therefore invalidates the system entry on every request and takes the message-level entries with it; only the tools prefix survives. A is the appealing wrong answer, because it describes the loss you would expect if the levels were independent. C is false: matching is exact, down to every byte up to the breakpoint. D is too pessimistic — the tools prefix precedes the change and still hits.

**A16 — A.** *(Applications and Integration)* There is a stricter dimension rule for many-image requests: once a request carries more than 20 images, every image must have neither dimension above 2,000 pixels, and a violation fails with an `invalid_request_error` that mentions many-image requests. At 2,400 pixels wide these photographs breach it. B states claude.ai’s 20-images-per-message limit, not the API’s, which allows 100 images per request on 200K-context models and 600 on the others. C is the trap: automatic downscaling is real for the native-resolution limits, but it does not rescue a request from the many-image dimension rule. D invents an aggregate interpretation of the 8,000 x 8,000 per-image maximum.

**A17 — C.** *(Applications and Integration)* Add the four input streams. Tool definitions: 14 x 320 = 4,480. Tool-use system prompt overhead on Opus 5.5 with `tool_choice` at its default of `auto`: 286. System prompt: 900. User message: 400. The total is 4,480 + 286 + 900 + 400 = 6,066. Option A omits the system-prompt overhead entirely. B uses 406, the overhead for `any` or `tool`, which is wrong because `tool_choice` was left at `auto`. D uses an Opus 4.8-era figure.

**A18 — A, C, D.** *(Applications and Integration)* Changing tool definitions invalidates the tools level and everything after it, so the system prefix goes with it (A). A `speed` switch between fast and standard leaves the tools prefix valid but invalidates system and messages (C). Toggling citations or web search behaves the same way (D). The other two changes stop short of the system level: a `tool_choice` change (B) leaves tools and system valid and invalidates only messages, and adding or removing an image (E) likewise invalidates messages only. F is the no-op case: setting `output_config.effort` explicitly to the value that is already the model’s default invalidates nothing.

**A19 — B.** *(Applications and Integration)* Forced tool choice — `any` or `tool` — returns 400 on Opus 5.5, Sonnet 5.5, Fable 5.1 and Mythos 5.1. The documented substitute is `auto` with `strict: true` for schema-valid arguments, plus `output_config.format` when the final response also needs a shape. A fails because `tool` is forced too, and is rejected for the same reason as `any`. C is backwards: forced tool use is rejected under manual extended thinking as well, and in any case `thinking.type: "enabled"` itself returns 400 on 4.7 and later. D confuses an unrelated beta header with a capability switch.

**A20 — D.** *(Applications and Integration)* A breakpoint only writes a cache entry, and a read only hits an entry some earlier request already wrote at its own breakpoint. Putting the breakpoint on the incoming user message means the prefix it defines has never occurred before and never will again, so every request writes a brand-new entry and nothing is ever read — exactly the `cache_creation` non-zero, `cache_read` always zero signature observed. The breakpoint belongs on the last block that is identical across requests. A is ruled out because short prefixes produce zero on **both** counters, not a non-zero write. B describes the 20-position lookback window, which is a real limit but would not make every single request a pure write. C would produce intermittent misses, not a uniform zero.

**A21 — A.** *(Applications and Integration)* `stream: true` is rejected inside a batch request, along with `speed` and `max_tokens: 0`. Almost everything else is supported: strict tools (B), `output_config.format` (C) and context management (D) all work in batches, as do vision, server tools, multi-turn conversations and extended thinking. The trap is that batch results arrive asynchronously anyway, so a developer may carry a streaming request shape over without thinking about it.

**A22 — C.** *(Applications and Integration)* Overhead, retrieval and time-to-first-token are serial: 350 + 600 + 480 = 1,430 ms. Generation of 180 tokens at 90 tokens per second is 2.0 s, or 2,000 ms. The total is 1,430 + 2,000 = 3,430 ms, leaving 4,000 - 3,430 = 570 ms of slack. Option A is what you get by forgetting the retrieval call, B by forgetting time-to-first-token, and D inverts the sign of the correct slack — the design fits, with 570 ms to spare.

**A23 — D.** *(Applications and Integration)* Clearing rewrites the prompt prefix, which invalidates the cached prefixes, so each clear forces a fresh cache write. `clear_at_least` exists precisely to stop small clears from triggering that cost repeatedly: if the strategy cannot clear at least that many tokens, it declines to apply. A is wrong by default — only tool results are cleared, and tool calls stay visible unless you set `clear_tool_inputs: true`. B gets the default right (`keep` is 3 tool uses) but a too-small `keep` would show up as repeated work, not as a cache-rate collapse. C is wrong because a missing `context-management-2025-06-27` header would mean no clearing at all, and the symptoms show clearing is happening.

**A24 — C, E.** *(Applications and Integration)* Results become accessible when every request has completed or after 24 hours, whichever comes first (C), and they remain downloadable for 29 days counted from `created_at` rather than `ended_at` (E). A is wrong about the expiry window: batches typically finish in under an hour, but the expiry is at 24 hours, not one. B inverts the billing rule — you are not billed for `errored`, `canceled` or `expired` requests. D understates the size limit: a batch holds up to 100,000 requests or 256 MB, whichever comes first.

**A25 — B.** *(Applications and Integration)* `expires_in_seconds` accepts 3,600 (one hour) to 7,776,000 (90 days) and cannot be changed after upload, so a file written with the minimum is gone eight hours later. After `expires_at` passes, Messages requests that reference the file fail before inference, and downloads return 404. The fix is to upload with an expiry that covers the pipeline’s latency. A inverts what the 30-day metadata retention is for: metadata stays readable, but that does not make the file usable in a request. C invents a re-fetch that does not exist, since files cannot be modified or restored after upload. D gets the direction backwards.

**A26 — A.** *(Applications and Integration)* On current models other than Haiku 3.5, `cache_read_input_tokens` does not count toward the input-tokens-per-minute limit; only `input_tokens` and `cache_creation_input_tokens` do. If 85% of input is served from cache, the 15% that counts is capped at 2,000,000 tokens per minute, so total throughput is 2,000,000 / 0.15, about 13.3 million tokens per minute. Option B is the limit itself, which is the answer only if cache reads counted. C is the uncached share grossed up by the wrong factor, and D corresponds to an 85% figure applied the wrong way round (2,000,000 / 0.85 plus the cached share).

## Section 2 — Model Selection and Optimization

**A27 — B.** *(Model Selection and Optimization)* Every ticket pays the Haiku pass, and an escalated ticket pays the Opus charge on top. With escalation rate r, the blended cost is \$0.0020 + r x \$0.0400. Setting that equal to the \$0.0160 budget gives r x \$0.0400 = \$0.0140, so r = 0.35, or 35%. Option D (40%) comes from ignoring the first-pass charge and solving \$0.0160 / \$0.0400. Option C (33%) is the answer if you treat an escalated ticket as paying only the Opus charge and then blend the two prices. Option A (30%) is a round number with no derivation.

**A28 — D.** *(Model Selection and Optimization)* Opus 5.5 defaults to `medium` effort while Opus 5 defaults to `high`, so a request that omits `effort` now runs one level lower than it used to. That is also why cost fell: lower effort spends fewer output tokens. Setting `output_config.effort` to `high` restores the previous behaviour, and `xhigh` or `max` go further. A is false — both models carry a 1M-token context window. B is false twice over: effort is supported on Opus 5.5, and `thinking.budget_tokens` is what returns 400 there. C names the wrong default: `low` is a valid level but not the Opus 5.5 default.

**A29 — B, D, F.** *(Model Selection and Optimization)* Effort applies to all output tokens — text, tool calls and their arguments, and thinking when active (B). Both `max` and `xhigh` are available on Opus 5.5 (D). And setting effort explicitly to the model’s own default produces the same behaviour as omitting it, so it does not invalidate the prompt cache (F). A is backwards: `max_tokens` is a hard ceiling on total output including thinking, and effort neither raises nor replaces it — which is why the guidance is to set a large `max_tokens` at high effort. C is a category error: `adaptive` is a thinking mode, not an effort value, and passing it as one is explicitly warned against. E inverts the documented behaviour — **lower** effort combines operations and makes **fewer** tool calls.

**A30 — C.** *(Model Selection and Optimization)* All-Opus baseline: 40,000 input at \$4 per MTok is \$0.16 and 3,000 output at \$20 per MTok is \$0.06, so \$0.22 per request, or \$44,000 for 200,000 requests. After the split, 60,000 requests stay on Opus at \$0.22 = \$13,200. The 140,000 Haiku requests sit under the 100,000-token threshold, so they bill at \$0.10 and \$0.50: 0.04 x \$0.10 = \$0.004 plus 0.003 x \$0.50 = \$0.0015, giving \$0.0055 each, or \$770. The new total is \$13,970 and the saving is \$44,000 - \$13,970 = \$30,030. Option A is the new total rather than the saving — the most common slip on this item. B rounds the Haiku cost to zero, and D uses the wrong traffic split.

**A31 — A.** *(Model Selection and Optimization)* Fast mode is set with the `speed` parameter, and `speed` is one of the three parameters rejected inside a batch request, alongside `stream: true` and `max_tokens: 0`. Fast mode runs only on the synchronous Messages API, where Opus 5.5 bills at \$8 input and \$40 output per MTok — double the standard rate — with caching and residency multipliers stacking on top. B invents a beta header. C is wrong because the incompatibility is absolute, not a discount carve-out. D names the wrong models: fast mode is available on Opus 5.5, Opus 5 and Opus 4.8.

**A32 — B.** *(Model Selection and Optimization)* The cached prefix is unchanged by the effort switch, so only output moves. Sonnet 5.5 bills output at \$10 per MTok, and the saving is 2,800 - 1,700 = 1,100 tokens per request, or 0.0011 MTok x \$10 = \$0.011. Across 500,000 requests that is \$5,500. Option A halves it, as if the output price were \$5. C and D come from pricing the saved tokens at \$15 or \$25 per MTok, which are Sonnet 4.6 and Opus 5 output rates rather than Sonnet 5.5’s.

**A33 — A, D.** *(Model Selection and Optimization)* The threshold is 100,000 prompt tokens, and prompt length counts every input token — uncached input, cache writes and cache reads alike (A). Pricing is per request, so a request above the threshold pays the higher rate across the board, including on the portion that was a cache hit (D), which is what makes a long cached prefix on Haiku 5.5 expensive in a way it is not on the other models. B is the general rule for current models but Haiku 5.5 is the documented exception. C understates the tier: it raises output from \$0.50 to \$2.50 per MTok as well as input from \$0.10 to \$0.50. E is wrong — the threshold is a prompt-length threshold, so output tokens do not count toward it.

**A34 — D.** *(Model Selection and Optimization)* Three things are wrong. `temperature` and `top_p` (along with `top_k`) are deprecated on 4.7 and later and return 400. `thinking: {"type": "enabled", ...}` is not supported on 4.7 and later and returns 400 with a message beginning `"thinking.type.enabled" is not supported`. The migration is to drop the sampling parameters, drop the manual thinking block, and set reasoning depth with `output_config.effort`, relying on a JSON schema or the prompt for output consistency. A and B each catch part of the problem and miss the rest — the thinking block is deprecated-but-accepted on 4.6, not on 5.5. C is wrong on the facts and misattributes the 400.

**A35 — C.** *(Model Selection and Optimization)* Both the token count and the price change, in opposite directions. On Sonnet 4.6: 12,000 tokens at \$3 per MTok is \$0.0360. On Sonnet 5.5 the same text measures roughly 12,000 x 1.3 = 15,600 tokens at \$2 per MTok, which is \$0.0312. That is about 13% cheaper, because the two-thirds price cut more than offsets the 30% token inflation. Option A applies only the tokenizer change, D applies only the price change, and B ignores both. The practical lesson is to measure with the token-counting endpoint rather than assuming either effect dominates.

**A36 — A.** *(Model Selection and Optimization)* The prefix is 180,000 tokens, or 0.18 MTok. A 1-hour cache write on Opus 5.5 is 2x the \$4 base input price, so \$8 per MTok: 0.18 x \$8 = \$1.44 for the one write. A cache read on Opus 5.5 is 0.05x base, so \$0.20 per MTok: 0.18 x \$0.20 = \$0.036, and 399 reads cost \$14.364. The hour therefore costs \$1.44 + \$14.36 = \$15.80. Option B is the reads alone, omitting the write. C uses the generic 0.1x read multiplier instead of Opus 5.5’s 0.05x, and D uses a 5-minute (1.25x) write multiplier on a 1-hour TTL.

**A37 — C, E.** *(Model Selection and Optimization)* Lowering effort from `high` to `medium` reduces output tokens, which is where most of the spend sits on an extraction job (C), and moving to the Message Batches API applies a flat 50% discount to input and output that stacks with caching (E). A has the multiplier backwards: a 1-hour TTL costs 2x on writes against 1.25x for 5 minutes, so it raises write cost and is justified only by a much better hit rate. B is good hygiene against wasted retries but raises no cost on its own and saves nothing when responses were not being truncated. D adds a 1.1x multiplier across all token categories. F doubles the token price on Opus and is not available in batches at all.

**A38 — B.** *(Model Selection and Optimization)* The capability-first path is to implement on Opus 5.5, evaluate, and tune effort downward as the workload matures — but when evaluations still fall short at `xhigh` or `max` on demanding reasoning or long-horizon agentic work, the documented next step is Fable 5.1, which is positioned for exactly the multi-hour session and finished-deliverable profile described. A confuses output length with capability; the extended-output beta raises `max_tokens` in batches and does nothing for reasoning depth. C is wrong on both counts: Mythos 5.1 has the same capabilities as Fable 5.1, not greater ones, and it is restricted to organizations cleared through Anthropic’s verification programs. D is a legitimate cost pattern but moves work to a less capable model, which is the opposite of what a capability shortfall calls for.

**A39 — D.** *(Model Selection and Optimization)* Include the rework. Haiku: 100,000 x \$0.0015 = \$150 in inference, plus a 9% error rate on 100,000 items, which is 9,000 errors x \$4.00 = \$36,000, for \$36,150 all-in. Opus: 100,000 x \$0.0300 = \$3,000 in inference, plus a 1.5% error rate, which is 1,500 x \$4.00 = \$6,000, for \$9,000 all-in. Opus is cheaper by \$36,150 - \$9,000 = \$27,150. Option B is the inference-cost gap in the wrong direction (\$3,000 - \$150 is \$2,850, not \$30,000) and A is that same gap signed as a Haiku win — both are what you get by comparing inference alone and ignoring the downstream cost that dominates. C compares the rework columns only.

**A40 — C.** *(Model Selection and Optimization)* The minimum cacheable prompt length on Haiku 5.5 is 512 tokens, and a 460-token prefix falls short. The documented behaviour for a short prefix is that the request is processed without caching and **no error is returned**, which is exactly the silent both-counters-zero signature described. A is false: Haiku 5.5 supports caching. B invents a placement rule — the real placement guidance is to put the breakpoint on the last block that is identical across requests, which the system prompt is. D gives the 4,096-token minimum that applies to Opus 4.6, Opus 4.5 and Haiku 4.5, not to Haiku 5.5.

**A41 — A, D, E.** *(Model Selection and Optimization)* The breakpoint belongs on the last block whose prefix is byte-identical across requests, since matching is exact and a breakpoint on changing content never hits (A). Longer-TTL blocks must precede shorter-TTL blocks in the prompt (D). And the batch discount stacks on top of the cache multipliers, which is what makes a cached batch the cheapest way to run bulk work (E). B inverts the ITPM rule: cache reads do **not** count toward ITPM on current models, with Haiku 3.5 the exception. C doubles the real figure — there are at most 4 explicit breakpoints, and automatic caching consumes one of the four. F gets the clock wrong in a way that matters: the TTL starts at the **start** of the request that writes or reads the entry, so a four-minute streaming response leaves only about a minute of a 5-minute TTL.

**A42 — A.** *(Model Selection and Optimization)* The output-tokens-per-minute limit is measured against tokens actually generated, and `max_tokens` does not factor into it, so a high ceiling carries no rate-limit cost. Dividing 400,000 by the 650-token average gives about 615 requests per minute. Option B is what you would get if `max_tokens` were charged against the limit (400,000 / 64,000), which is precisely the misconception being tested. C doubles the correct figure. D is wrong because OTPM does bound request rate once you account for actual output.

**A43 — A.** *(Model Selection and Optimization)* The style guide pushes the prompt across Haiku 5.5’s 100,000-token pricing threshold, and the whole request re-prices. Before: 96,000 input at \$0.10 per MTok is \$0.0096, and 1,200 output at \$0.50 per MTok is \$0.0006, so \$0.0102 per request, or \$10.20 per 1,000. After: the prompt is 102,000 tokens, so the request bills at \$0.50 input and \$2.50 output — 0.102 x \$0.50 = \$0.051 plus 0.0012 x \$2.50 = \$0.003, giving \$0.054, or \$54.00 per 1,000. The ratio is 54.00 / 10.20 = 5.29, about 5.3x. Option B is what you get by applying the lower tier throughout, which is the mistake the question is testing. C uses the higher tier for input only, and D is the ratio of the token counts alone.

**A44 — D.** *(Model Selection and Optimization)* The prompt is 108,000 + 900 = 108,900 tokens, above Haiku 5.5’s 100,000-token threshold, so the whole request bills at the higher tier — including the cached portion, since the tier is decided per request. Cache reads at the higher tier are \$0.05 per MTok, halved by the batch discount to \$0.025: 108,000 x 20,000 = 2,160 MTok x \$0.025 = \$54.00. Unique input at the higher batch rate of \$0.25 per MTok: 900 x 20,000 = 18 MTok = \$4.50. Output at the higher batch rate of \$1.25 per MTok: 300 x 20,000 = 6 MTok = \$7.50. The total is \$54.00 + \$4.50 + \$7.50 = \$66.00. Option B is the cache stream alone. A prices the whole job at the lower tier, which is the mistake the 108,900-token prompt is there to catch, and C drops the batch discount.

## Section 3 — Agents and Workflows

**A45 — C.** *(Agents and Workflows)* `max_turns` counts tool-use turns only, so a limit of 2 stops the loop after the `Read` turn and before the `Edit` turn. When either limit is hit, the SDK returns a `ResultMessage` whose subtype is `error_max_turns`, and `result` is **not** present on that subtype — though `total_cost_usd`, `usage`, `num_turns` and `session_id` are, so the run can be resumed with a higher limit. A inverts the counting rule; the subagent-spawn controls are separate environment variables. B is wrong because hitting the limit is not a success. D invents a partial `result` on an error subtype; partial marking is a subagent `maxTurns` behaviour, surfaced in the Agent tool result, not a top-level `result` field.

**A46 — B, C, F.** *(Agents and Workflows)* At the cap, Claude Code refuses to spawn further subagents and returns `Budget limit reached` (F), stops background subagents that are still running (B), and ends the query with the `error_max_budget_usd` result subtype (C). A is the appealing wrong answer: the response that reaches the cap still completes and still counts toward `total_cost_usd`, which is why spend can pass the cap by up to one response’s cost. D is wrong because the budget total keeps accumulating across messages in the same conversation; only a `/clear` starts it over. E is invented — effort is not adjusted automatically in response to spend.

**A47 — A.** *(Agents and Workflows)* The cap is compared against spend only after a model response arrives, because the cost comes from the token usage returned with it. So the \$0.70 response completes and counts: \$4.85 + \$0.70 = \$5.55, already past the cap. Subagents still running at that moment spend before they are stopped, adding \$0.18 + \$0.11, for a reported total of \$5.84. The subtype is `error_max_budget_usd`. B describes exact enforcement, which the documented headroom behaviour explicitly does not provide. C is the figure you get by excluding the in-flight subagent spend, but subagent spend counts toward the same total. D has the right number and the wrong subtype — crossing the cap ends the query as an error, not a success.

**A48 — D.** *(Agents and Workflows)* A non-fork subagent starts with its own `AgentDefinition.prompt`, the Agent tool’s prompt string, project CLAUDE.md where `settingSources` loads it (unless `omitClaudeMd` is set), and its tool definitions — inherited or the subset named in `tools`. It does **not** receive the parent’s conversation history, the parent’s tool results, the parent’s system prompt, or preloaded skill content unless listed in `AgentDefinition.skills`. That is the whole point: intermediate work stays inside the subagent and only its final message returns. A, B and C each name something the subagent specifically does not get, which is why the Agent tool’s prompt string must carry every file path, error message and decision the subagent will need.

**A49 — B.** *(Agents and Workflows)* Three controls bound the tree. `CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH` caps nesting, defaulting to 3 layers below the main agent; `CLAUDE_CODE_MAX_CONCURRENT_SUBAGENTS` caps simultaneous subagents, defaulting to 20; and `max_budget_usd` caps spend, counting subagent requests toward the same total. The first two are environment variables, set through the `env` option, and the third is a query option. A misstates `max_turns`, which caps tool-use round trips and says nothing about how many subagents a turn may spawn. C is too blunt and factually narrow — depth, concurrency and spend limits all exist — and would disable delegation entirely. D misreads `plan` mode, which governs file edits rather than subagent spawning.

**A50 — A, E.** *(Agents and Workflows)* The default spawn depth is 3 layers of subagents below your main agent, and setting it to 1 stops your subagents from spawning any of their own; an agent at the bottom layer simply does the delegated work itself (A). At the concurrency limit, Claude Code refuses to spawn and Claude receives a `tool_result` carrying `Concurrent subagent limit reached`, and can spawn again once the running count drops below the limit (E). B inverts the spend rule — `max_budget_usd` counts subagent requests toward the total, which is exactly why it bounds fan-out. C puts the limits in the wrong place: depth and concurrency are environment variables passed through `env`, not query options. D gives the depth default where the concurrency default belongs; concurrency defaults to 20.

**A51 — C.** *(Agents and Workflows)* Two mechanisms work together. As the conversation approaches the clearing threshold Claude receives an automatic warning to preserve important information, so an agent with the memory tool can write findings to memory files before the results are cleared and retrieve them on demand later. `exclude_tools` then protects the specific tools whose results must never be cleared. A inverts the behaviour: `clear_tool_inputs: true` clears **more**, adding the call parameters to the results already being cleared. B fights the mechanism rather than using it, and a very large `keep` defeats the purpose of context editing. D makes the problem worse by clearing far more aggressively.

**A52 — A.** *(Agents and Workflows)* `dontAsk` never prompts: tools pre-approved by permission rules run, as do calls that need no approval in `default` mode, and every call that would otherwise prompt is **denied**. That is the fixed, explicit tool surface with a hard deny that the requirement describes. B is the wrong choice for exactly the reason stated in the stem — in `default` mode, a missing `canUseTool` callback is what produces the deny, which is the silent reliance the team wants to avoid. C runs allowed tools without asking, which is the opposite of a restricted surface, and it cannot run as root on Unix. D auto-approves file edits and common filesystem commands, which is broader than intended.

**A53 — D.** *(Agents and Workflows)* Inline, the 14 files add 14 x 9,000 = 126,000 tokens to the main agent’s context. Delegated, only the 1,800-token final report does. The difference is 126,000 - 1,800 = 124,200 tokens, or 0.1242 MTok, and at Opus 5.5’s \$4 per MTok input price that is about \$0.4968, so roughly \$0.50 on every subsequent main-agent request — paid again on each one, because context accumulates. Option C is the cost of the full 126,000 tokens at the wrong price point, A is off by an order of magnitude, and B is about half the correct figure. The compounding is the real point: this is why the documented advice is to delegate subtasks and keep the main context lean.

**A54 — C, D.** *(Agents and Workflows)* Omitting `tools` gives the subagent every tool available to subagents, so a prompt telling it never to modify files is the only thing standing between an auditor and `Edit` or `Write`; scoping it to `["Read", "Grep", "Glob"]` removes the tool from the session entirely, with no prompt and no error (C). With no `maxTurns`, an open-ended audit runs until Claude decides it is finished; setting a limit bounds it, and when the subagent stops at the limit its output comes back marked partial so it can be resumed (D). A is false: `inherit` is a documented `model` value that uses the main model. B is false: project CLAUDE.md is loaded into a non-fork subagent’s context via `settingSources`. E is false — `prompt` is a required field on a programmatic `AgentDefinition`. F has it backwards; subagents run in the background by default.

**A55 — B.** *(Agents and Workflows)* `result` holds the final text output and is present only on the `success` subtype, so the subtype must be checked before `result` is read. Every subtype — `success`, `error_max_turns`, `error_max_budget_usd`, `error_during_execution` and `error_max_structured_output_retries` — carries `total_cost_usd`, `usage`, `num_turns` and `session_id`. A has the availability backwards; in Python those cost fields are typed as optional and should be checked for `None`, but that is a separate guard. C is wrong on mechanism: a single-shot `query()` yields the error result **and then** raises, so the result message does arrive. D is wrong in the way that matters most operationally — `session_id` is present on error subtypes, which is precisely how a turn-limited run is resumed.

**A56 — C.** *(Agents and Workflows)* Compaction replaces older messages with a summary, so instructions given early in the conversation may not survive it. The documented fix is to move persistent rules into CLAUDE.md, loaded through `settingSources`, because that content is re-injected on every request rather than living in the compactable history. A is false: compaction is automatic when the context window approaches its limit — the `compact_boundary` message in the stream is the proof it fired. B treats the symptom and only postpones it; `autoCompactWindow` lowers a subagent’s window rather than disabling compaction, and a long enough run compacts anyway. D names a real hook, but `PreCompact` is for archiving the transcript before summarizing and is not the supported way to persist rules — and the claim that it is the only mechanism is what makes the option wrong.

**A57 — A.** *(Agents and Workflows)* Hooks run in your application process, not inside the agent’s context window, so they cost no context, and a `PreToolUse` hook that rejects a call short-circuits the loop: the tool never executes and Claude receives the rejection message as the tool result, after which it typically tries another approach. B contradicts the no-context property. C names the wrong hook — `PostToolUse` fires after the tool returns, which is too late to block anything; blocking is `PreToolUse`. D is wrong on availability: both SDKs support the core events, and the TypeScript SDK supports additional ones Python does not yet have.

**A58 — D.** *(Agents and Workflows)* The SDK runs read-only tools concurrently and state-changing tools sequentially, so the three `Read` calls can overlap while `Edit` and `Bash` are serialized to avoid conflicts. Custom tools default to sequential execution and opt into parallelism by declaring `readOnlyHint` in their annotations — the field name both SDKs take from the MCP SDK. A ignores the state-changing distinction. B invents a parameter: `disable_parallel_tool_use` is a Messages API `tool_choice` field that limits how many calls Claude requests, not how the SDK executes them. C reverses the custom-tool default.

**A59 — B.** *(Agents and Workflows)* With streaming input, a message still queued when a turn ends at the max-turns limit stays queued. Claude Code does not add it to that turn’s last model call; it starts a new turn for the message, and the max-turns count starts over for that turn. The budget total, by contrast, keeps accumulating across messages, and once spend reaches `maxBudgetUsd` later messages in the same conversation end with `error_max_budget_usd`. A describes the behaviour the design deliberately avoids. C discards a message that is in fact preserved. D is the half-right trap: the turn count does start over, but the budget total does not — only a `/clear` resets it.

**A60 — C.** *(Agents and Workflows)* The final text-only turn is not a tool-use turn and is not counted by `max_turns`, but it does consume wall-clock time, so reserve it first: 90.0 - 6.0 = 84.0 s remain. Each tool-use turn costs 5.4 + 1.9 = 7.3 s, and 84.0 / 7.3 = 11.5, so 11 turns fit and 12 would overrun (12 x 7.3 = 87.6, plus 6.0, is 93.6 s). The answer is 11. Option D takes the floor of 90 / 7.3 and forgets to reserve the final turn. A and B come from counting only the 5.4 s of model time per turn and ignoring tool execution.
