**E5.4 — A and B.** *(Applications and Integration)* A `canUseTool` callback returning `permissionDecision: "defer"` ends the turn with `stop_reason: "tool_deferred"`, which is precisely the shape an out-of-band approval needs: the application holds the pending `tool_use`, gets the reviewer’s decision, and resumes with a `tool_result`. A proposes reordering the levels, which the API fixes and the caller cannot change. C is a real improvement in isolation but a longer TTL on an entry that is invalidated rather than expired changes nothing. D moves the corpus to the messages level, which sits *after* tools in the hierarchy and is therefore invalidated by the same change.

**E5.42 — D.** *(Tools and MCPs)* Tool use injects a system prompt of 286 tokens with `tool_choice` of `auto` or `none`. So the tools-and-system contribution is 3,900 + 7,100 + 286 = **11,286**. A omits the injected overhead entirely, which is the usual error when sizing a prefix against the minimum cacheable length or a context budget. B uses the 406-token figure that applies to `any` and `tool` — forced values which in any case return 400 on current models. C counts the system prompt and the overhead but drops the tool definitions.

**E5.43 — A.** *(Tools and MCPs)* The 2026-07-28 stateless revision replaces `initialize` with `server/discover`, carries per-request state in `_meta`, and deprecates sampling and logging. That accounts for both symptoms at once: the handshake call is not the one the server answers, and the notification channel the audit console depends on no longer exists — progress has to be surfaced by the client around each request instead. B invents a re-declaration requirement. C states the real tool-naming convention, which is a permissions concern rather than a transport one. D is a true statement about connector tools set to `ask` and has nothing to do with notifications.

**E5.44 — A and B.** *(Tools and MCPs)* A marks the tool so that no allow rule can auto-approve it — `_meta["anthropic/requiresUserInteraction"]` forces the call through the approval callback even when an allow rule matches, which is exactly the property a money-movement tool needs. B puts the limit where it can actually be enforced: inside the server, against the calling identity’s own entitlements, so the constraint survives any argument the model produces. C is a description, not a control. D misreads `dontAsk`, which denies rather than prompts and never calls the callback — a safe failure, but not an approval path. E confuses shape with authority: `strict: true` guarantees the arguments parse against the schema, not that the caller is entitled to the transfer they describe.

**E5.45 — B.** *(Tools and MCPs)* The correct engineering stance is that a tool result is data from outside the trust boundary, exactly like a user-supplied document: it is validated against the expected schema in the application, and the agent’s authority is bounded by deny rules and hooks that no text in a result can widen. That makes the question of whether the model “falls for” the passage largely moot, which is the property to aim for. A changes reasoning depth, which is not a security control in either direction. C is worth doing but is prompt-level pleading on its own — it asks the model to be the boundary. D misdescribes strict tool use, which constrains the arguments the model produces, not the content a server returns.

**E5.46 — C.** *(Tools and MCPs)* A `tool_choice` change preserves the tools cache but invalidates the system and message caches, which is precisely the `system_changed` the diagnostics report. Holding `tool_choice` constant across the workflow’s phases and gating behaviour in application code — for example by ignoring tool calls during write-up rather than forbidding them — keeps the prefix alive. A is true of tool *definition* changes, which would report `tools_changed`. B is a true statement about images, which this workflow does not vary. D is a true statement about `speed`, which this workflow does not change.

**E5.47 — D.** *(Security and Safety)* Authorisation is a property of the caller and the record, and it must be decided in code against the identity store before the prompt is constructed. Two things follow, and the second is the one teams miss: the model must not be the decision point, *and* a record the caller is not entitled to see must never be placed in the prompt at all — once it is in the context, a correct refusal is the only thing standing between the caller and the data. A, B and C are all reasonable engineering practices in their own right — reliable parsing, a confirmation gate, an auditable decision record — and each would improve a system that had already made the access decision correctly. None of them repairs a design in which the model is the authority.

**E5.48 — A and B.** *(Security and Safety)* A removes the capability rather than guarding it: a bare-name deny entry takes the tool definition out of the request, so the model does not see the tool and cannot attempt it — the strongest available control, and the right one when a session’s input includes third-party content. B is the complementary measure for sessions that must retain the tool: a `PreToolUse` hook that re-derives payee and amount from the application’s own record and denies on disagreement means the model’s arguments can never be the authority for who gets paid. C is prompt-level pleading. D confuses an allow rule with an audit mechanism, and an allow rule here would make matters worse by auto-approving the call before the callback runs. E reaches for a deprecated parameter that returns 400 on current models, and determinism was never the defence anyway.

**E5.49 — A.** *(Security and Safety)* The only durable way to keep a value out of a request/response log is to keep it out of the request: a log written after the call necessarily contains whatever was sent. Deriving a stable surrogate at construction time satisfies the audit requirement — the surrogate links interaction to record and is stable across time — while the mapping stays in the system of record under its own controls. B writes the identifier first and hopes to remove it later, which fails for every read and every replica between the write and the job. C relies on access control over data that should not have been written. D misunderstands `metadata.user_id`, which is an abuse-detection field, is echoed in the request the application itself logs, and is not a protected channel.

**E5.50 — C.** *(Security and Safety)* A confirmation that lives inside the model’s turn is advisory. Nothing in the protocol prevents the closing call from being emitted in the same turn as the question, or on a later turn without one, and nothing ties the affirmative reply to the specific pending action. A real gate sits in the permission layer — `canUseTool`, a `PreToolUse` hook, or a deferral resolved out of band — where the application decides and the decision is bound to a specific `tool_use`. A improves the wording of a control that is not load-bearing. B improves detectability of the same advisory signal. D names a real session-binding concern, but it would still be a concern after the gate is moved, and the gate is the defect.

**E5.51 — B.** *(Claude Code)* Path anchoring is the trap. With a single leading slash, `Edit(/secrets/**)` anchors at the rule’s source — and for a rule passed through `disallowed_tools`, that source is the session’s working directory, so the rule guards `<cwd>/secrets`, not `/secrets` on disk. The absolute form takes a double slash: `Edit(//secrets/**)`. A is backwards: `Edit(path)` rules govern all built-in file-writing tools, including `Write` and `NotebookEdit`. C states a true and related fact — a `Write(path)` rule is never matched by the file permission checks — but naming `Write` is precisely what would *not* have helped. D is false: deny rules are evaluated before the mode check and apply even in `bypassPermissions`.

**E5.52 — D.** *(Claude Code)* The two forms differ in kind, not degree. A bare name removes the tool definition from the request, so the model never sees the tool; a scoped rule leaves the tool present and denies only the calls matching the pattern *as written*, which is why `Bash(rm *)` does not stop a call spelled `/bin/rm` — that call falls through to the permission mode like any other. A and B each collapse the two forms into one behaviour. C inverts the strength of the scoped form, which is in fact evaluated before allow rules and holds in every mode, including `bypassPermissions`.

**E5.53 — A.** *(Eval, Testing, and Debugging)* Validation of each request’s `params` in a batch happens asynchronously, so acceptance of the batch says nothing about the validity of the requests inside it; shape errors surface only when the batch ends, which here cost a night. The documented practice is to exercise the request shape against the synchronous Messages API first and use the batch for volume, not for validation. B is true about the size limits but a 2,000-request batch is perfectly adequate for a staging run — representativeness is not what failed. C is true (`errored` results are not billed) and is a reason the mistake was cheap, not a reason it happened. D states the download window correctly and then draws the wrong conclusion, since the failures are explained rather than mysterious.
