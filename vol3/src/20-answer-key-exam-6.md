# Answer Key: Exam 6

**E6.1 — B.** *(Applications and Integration)* Fast mode runs the same weights on a faster inference configuration and delivers up to 2.5x higher output tokens per second. The documentation is explicit that it does *not* improve time to first token, which is why a TTFT budget is exactly the wrong thing to spend it on. TTFT is governed by how much new input the model must process before it can emit a token, so the levers are cache hit rate, the size of the uncached suffix after the last breakpoint, and model tier. A, C and D are all true statements about fast mode — it is unavailable with batches, it has a dedicated rate limit, and switching speed invalidates the cache — and each would be a real operational concern once fast mode is in use. None of them explains why the TTFT number did not move.

**E6.2 — D.** *(Applications and Integration)* Fast mode scales output throughput, not TTFT. At the documented maximum of 2.5x, throughput goes from 60 to 150 tokens per second, so 120 tokens take 120 / 150 = 0.8 s = 800 ms. TTFT stays at 500 ms. Total **1,300 ms**, comfortably inside the 1,800 ms budget. A scales TTFT by 2.5 as well (500 / 2.5 = 200, plus 800), which is the error the question is built around. B is the standard-speed figure (500 + 2,000 = 2,500 ms), which fails the budget. C counts generation time only and omits TTFT.

**E6.3 — A.** *(Applications and Integration)* Haiku 5.5 is \$0.10 input / \$0.50 output per MTok, with cache reads at 0.1x = \$0.01/MTok; at 1,020 total prompt tokens the long-context tier is nowhere in play. Reads: 40,000,000 × 900 = 36,000,000,000 tokens × \$0.01/MTok = \$360.00. Uncached input: 40,000,000 × 120 = 4,800,000,000 × \$0.10/MTok = \$480.00. Output: 40,000,000 × 40 = 1,600,000,000 × \$0.50/MTok = \$800.00. Total **\$1,640.00**. B prices the whole 1,020-token prompt as uncached input (\$4,080 + \$800). C omits the cache reads entirely. D applies the 5x long-context multiplier, which a 1,020-token prompt does not trigger.

**E6.4 — C.** *(Applications and Integration)* The minimum cacheable length on current models is 512 tokens. A 300-token prefix falls below it, so the prompt is processed without caching — and crucially no error is returned, which is why the deployment looks successful and the bill does not move. The documented check is to read `cache_creation_input_tokens` and `cache_read_input_tokens`; both 0 means nothing was cached. A misapplies the lookback window, which concerns discovering entries rather than placing a breakpoint. B states the real four-breakpoint rule but a fifth breakpoint returns 400 rather than failing silently. D would reduce the hit rate at low arrival rates but could not produce a complete absence of caching, and in any case the 5-minute TTL is refreshed at no cost on each read.

**E6.5 — B.** *(Applications and Integration)* OTPM is evaluated in real time against tokens actually produced; `max_tokens` does not factor into it, so setting a higher value carries no rate-limit penalty and setting a lower one buys no headroom. The clamp therefore does nothing for throttling and everything for truncation — the worst of both. Real OTPM headroom comes from producing fewer tokens: lower effort, shorter formats, a smaller model for the short-answer majority. A is true of ITPM, which is estimated at request start and adjusted during the request, and is the wrong limit here. C is a true fact about header granularity. D is true and worth checking — the `tokens-*` headers report the most restrictive limit in effect, which may not be the one the team assumed — but it describes how to diagnose, not why the clamp failed.

**E6.6 — A, B and C.** *(Applications and Integration)* A attacks TTFT directly: the uncached suffix is what the model must process before it can emit a token, and cache reads are both cheaper and faster than reprocessing. B is the structural latency win on any generative interface — the user’s perceived latency becomes TTFT plus a few tokens rather than the whole generation. C is the standard high-QPS shape: serve the majority on the fastest tier and escalate on a signal the application computes, not one the model requests. D is a trap built on a true fact — raising `max_tokens` carries no OTPM penalty — but it does not make anything faster. E is a 1.1x price modifier and a data-residency control, not a latency control. F reaches for a parameter that is deprecated on 4.7 and later and returns 400.

**E6.7 — D.** *(Applications and Integration)* Compiled grammars are cached for 24 hours *from last use*. A schema used once every 30 hours has always fallen out of that cache by the time it is next used, so **every** long-tail request pays the compilation cost. The arithmetic is the point: the cache’s TTL has to be compared against the inter-arrival time of each schema, not against the endpoint’s overall rate. The fix is consolidation — one schema with optional fields, or a small number of schemas each used often enough to stay warm. A and B treat compilation as a one-off amortised across the schema’s lifetime, which is true only for schemas used more often than daily. C asserts indefinite persistence, which the 24-hour window contradicts.

**E6.8 — A.** *(Applications and Integration)* Changing `output_config.effort` between requests restarts the prompt cache. A client that varies effort per request inside one thread therefore invalidates the prefix on every switch, which on a mobile conversation is most turns. The `mid-conversation-output-config-2026-07-01` beta exists precisely to preserve the cache across such a change; without it, fix effort for the life of a thread and route differently-shaped work to different threads. B names the correct Sonnet 5.5 default but the stem does not state the model, and the default is not what invalidates. C is true and is the useful corollary — an explicit value equal to the model’s default costs nothing — but here both values are being set and at least one differs. D is false: a misplaced reasoning parameter is rejected, not ignored.

**E6.9 — C.** *(Applications and Integration)* ITPM counts `input_tokens` plus `cache_creation_input_tokens`; cache reads do not count on current models. Each request therefore charges 1,200 + 800 = 2,000 tokens, and 1,500 requests per minute consume 3,000,000 of the 4,000,000 limit. Headroom is 1,000,000 / 2,000 = **about 500 more requests per minute**. This is the whole reason a 250,000-token cached prefix is viable at consumer QPS: the read is billed at the cache-read rate and consumes no ITPM. A counts the reads (252,000 × 1,500 = 378,000,000). B counts the reads by another route. D drops the cache writes, which do count.

**E6.10 — B.** *(Applications and Integration)* The Messages API has no idempotency key. A request that completed server-side after the client gave up has already been billed and will be billed again on retry, and because generation is not deterministic the two responses can differ — which is exactly the pair of symptoms described. Deduplication has to be keyed in the application: record a request key before the call, and reconcile rather than repeat. A is a true distinction between 429 and 529 that does not bear on timeouts. C concerns rate-limit retries, not client timeouts. D is true of SDK defaults and would add attempts, but the defect is the absence of deduplication, not the number of tries.

**E6.11 — D.** *(Applications and Integration)* Synchronous cost: input 3,000,000 × 1,500 = 4,500,000,000 × \$2/MTok = \$9,000; output 3,000,000 × 250 = 750,000,000 × \$10/MTok = \$7,500; total \$16,500. Batch is 50% of that, \$8,250, so the saving is **\$8,250** — and the two constraints that decide whether it is usable are that results can arrive in any order, with `custom_id` as the only join key, and that a batch expires if it does not complete within 24 hours. A has the right number and the wrong ordering guarantee, which is the most dangerous combination in this question because a positional loader will appear to work in testing. B treats the saving as the whole cost. C applies a 25% discount that does not exist.

**E6.12 — A.** *(Applications and Integration)* Requests at different speeds do not share cached prefixes: switching between fast and standard invalidates the cache. On a long mobile session the fallback turn therefore reprocesses the entire prefix at write prices, and every later turn is working against a prefix that was rebuilt under the other speed — which is why both the fallback turn *and* the turns after it degrade. Pinning one speed per session, and deciding it before the first turn, avoids the whole class of problem. B is true and is how the client should anticipate the 429, but reading a header does not explain the spike. C is a true and important caveat about `max_retries=0`, which also disables retries for transient 5xx. D is true and is good instrumentation, not a cause.

**E6.13 — A and B.** *(Applications and Integration)* `usage.speed` reports `"fast"` or `"standard"` and is the authoritative statement of what actually served the request — worth checking, since a request can be accepted at one speed and served at another. `anthropic-fast-output-tokens-remaining` is one of the `anthropic-fast-*` headers that expose the dedicated fast-mode limit, with matching `-limit` and `-reset` values and an input-token pair. C reports the standard rate limit, which is a different budget. D is emitted only under a Priority Tier commitment, which is in any case unavailable with fast mode. E reports the inference geography, not the speed.

**E6.14 — C.** *(Applications and Integration)* Image tokens are `ceil(w/28) × ceil(h/28)`. Native: `ceil(3024/28) = 108` and `ceil(4032/28) = 144`, so 108 × 144 = 15,552 tokens. Downscaled: `ceil(1008/28) = 36` and `ceil(1344/28) = 48`, so 36 × 48 = 1,728 tokens. The reduction is 15,552 / 1,728 = **9x**, because halving each dimension three times over quarters the token count each time — the formula is quadratic in linear dimension, which is the insight the question tests. A and D get the arithmetic partly right and the factor wrong. B scales the dimensions rather than the areas.

**E6.15 — D.** *(Applications and Integration)* On 4.6 and later models an interrupted generation is resumed with a user-message continuation carrying what was already delivered — the prefill-style resumption belongs to 4.5 and earlier and returns 400 here. The caveat matters on a flaky link: tool-use and thinking blocks are not partially recoverable, so a break inside one of them forces a restart from the last complete block rather than mid-block. A is the 4.5-and-earlier form and will fail. B treats a connection failure as a budget problem. C is the worst option for a mobile client: non-streaming removes the progressive rendering that makes a long answer tolerable, and a non-streaming request is subject to a 10-minute ceiling besides.

**E6.16 — B.** *(Applications and Integration)* A prompt may carry at most four `cache_control` breakpoints; the fifth returns 400, which is why the endpoint works for a few turns and then fails. The intended pattern is a small fixed set of breakpoints — typically tools, system, and one or two at stable points in the history — with the 20-block lookback finding the most recent entry that still matches. A states the lookback window correctly but a lookback miss is a cache miss, not a 400. C is a true ordering rule for mixed TTLs that the stem does not engage. D is true about cache writes counting toward ITPM and would show up as 429, not 400.

**E6.17 — A.** *(Applications and Integration)* Mixed-TTL billing resolves to three positions: read everything up to A, write the A-to-B span at the 1-hour rate, and write the B-to-C span at the 5-minute rate. On Sonnet 5.5 the read is 0.05x = \$0.10/MTok, the 1-hour write is 2x = \$4/MTok, and the 5-minute write is 1.25x = \$2.50/MTok. Read: 150,000 × \$0.10/MTok = \$0.015. One-hour write: (170,000 − 150,000) = 20,000 × \$4/MTok = \$0.080. Five-minute write: (182,000 − 170,000) = 12,000 × \$2.50/MTok = \$0.030. Total **\$0.125**. B prices all 182,000 tokens as a 5-minute write. C prices everything as a read. D swaps the two write rates between the segments.

**E6.18 — A, B and C.** *(Applications and Integration)* A is the dominant lever on Haiku 5.5 specifically: it is the only current model priced by prompt length, and crossing 100,000 total tokens — cache reads and writes included — multiplies input *and* output by five on that request. B is the general shape of a cacheable prefix: content above the last breakpoint bills at 0.1x of base on Haiku rather than at the input rate. C stacks a further 50% off on whatever share of traffic can tolerate a 24-hour window. D is wrong twice: fast mode is Opus-only, and it raises the price rather than lowering it. E is a 1.1x price modifier, so it increases the bill. F is built on a true fact — `max_tokens` carries no OTPM penalty — but raising it reduces nothing.

**E6.19 — C.** *(Model Selection and Optimization)* The escalated 5% pay for *both* models, because the Opus run repeats work the Haiku run already did. Haiku per request: 2,000 × \$0.10/MTok = \$0.0002 input, 150 × \$0.50/MTok = \$0.000075 output, total \$0.000275. Opus per request: 2,000 × \$4/MTok = \$0.008 input, 150 × \$20/MTok = \$0.003 output, total \$0.011. Blended: \$0.000275 + 0.05 × \$0.011 = \$0.000275 + \$0.00055 = **\$0.000825**. B, at \$0.000811, is the near-miss worth understanding: it is the weighted average 0.95 × \$0.000275 + 0.05 × \$0.011, which quietly assumes the escalated requests never ran on Haiku at all. A is the Haiku-only cost. D is the all-Opus cost, useful as the comparison the routing is justified against — the routed design is about 13x cheaper.

**E6.20 — A.** *(Model Selection and Optimization)* Three facts converge against the proposal: Fable 5.1 is the slowest of the four current tiers, its default effort is `high` so it generates more reasoning output than the others before answering, and at \$10/\$50 per MTok it is the most expensive — with fast mode, the one lever that raises throughput, available only on Opus models. A reply-suggestion endpoint at tens of millions of requests per day with a 600 ms budget is the archetypal Haiku 5.5 workload, with Sonnet 5.5 as the escalation. B is true and is exactly the irrelevance a “strongest model” argument leans on. C is true and contributes to the latency problem but is not by itself the review finding. D is true and would help, but lowering a slow model’s effort to approach a fast model’s default is not a sound way to reach 600 ms at this volume.

**E6.21 — D.** *(Model Selection and Optimization)* Sonnet 5.5 defaults to `high` effort; Opus 5.5 defaults to `medium`. A migration that changes only the model string therefore silently raises reasoning depth, and reasoning tokens are billed as output and take time to generate — which accounts for the higher p99 *and* for the bill falling by less than the headline price ratio predicted. Setting effort explicitly is the fix, and the lesson is that a model swap is never only a price change. A is true (both are 0.05x) and is therefore not a differentiator. B is true and is the kind of fact that makes a migration look like a drop-in. C is true — fast mode is Opus-only — and would be the answer if the endpoint had been using fast mode, which the stem does not say.

**E6.22 — A and B.** *(Model Selection and Optimization)* Fast mode draws on a dedicated rate limit, separate from standard Opus limits and reported through `anthropic-fast-*` headers, which is what makes capacity planning for it a separate exercise. It is also unavailable with the Message Batches API and with a Priority Tier commitment. C inverts the central fact: the gain is up to 2.5x in output tokens per second, and TTFT is explicitly unaffected. D is wrong — fast mode is available on Opus 5.5, Opus 5 and Opus 4.8, not on Haiku. E is wrong: caching and data-residency multipliers stack on top of fast-mode pricing.

**E6.23 — B.** *(Model Selection and Optimization)* Standard: 3,000 × \$4/MTok = \$0.012 input, 2,500 × \$20/MTok = \$0.050 output, total \$0.062. Fast: 3,000 × \$8/MTok = \$0.024 input, 2,500 × \$40/MTok = \$0.100 output, total \$0.124. The ratio is exactly **2.0x**, because fast mode doubles both the input and the output price on Opus 5.5 (\$4/\$20 to \$8/\$40). What it buys is up to 2.5x output tokens per second, with model weights and behaviour unchanged and TTFT unchanged. A and C quote multipliers the arithmetic does not produce. D has the correct 2.0x and attaches a TTFT improvement that fast mode explicitly does not provide — the single most common misconception about the feature.

**E6.24 — C.** *(Model Selection and Optimization)* Haiku 5.5 is priced by prompt length, and the threshold is 100,000 tokens counted across the whole prompt, cache reads and writes included. A 40% rise in token volume that straddles the threshold produces a far larger rise in cost, and only on the requests that cross — which is exactly the “far more, and only on some requests” pattern described. Above the line both input and output pay 5x, and the tier is decided per request. A is true about ITPM and explains why no rate-limit alarm fired, not why the bill rose. B is a reasonable remedy — trimming history server-side would hold the prompt under the threshold — but it answers “what next”, not “what happened”. D is true and is the assumption that let the change ship.

**E6.25 — A, B and C.** *(Model Selection and Optimization)* The cache-read multiplier is not uniform: 0.05x of base on Opus 5.5 and Sonnet 5.5, a deeper 0.025x on Fable 5.1, and the general 0.1x elsewhere including Haiku 5.5. At volume this changes model comparisons materially, because a model with a higher base price can have a cheaper effective read. D is the flat assumption A and B contradict. E is wrong — the caching multipliers stack with the 50% batch discount, which is what makes a cached batch so cheap. F is wrong: cache reads do not count toward ITPM on current models, which is the rate-limit half of the same argument.

**E6.26 — A.** *(Model Selection and Optimization)* Opus 5.5 is \$4/\$20 and Haiku 5.5 is \$0.10/\$0.50, a 40x gap on both input and output, and Haiku is the fastest of the four tiers while Opus is moderate. Once an eval establishes parity on the actual task, there is no remaining argument for the larger model on a latency-critical path, and the only operational caution is Haiku’s 100,000-token prompt threshold — which the stem rules out. B is a reasonable intuition about robustness but is a hypothesis the eval has already addressed, and “degrades gracefully” is not a measured property here. C is arithmetically wrong: `low` effort reduces output tokens, not the 40x per-token gap. D is factually wrong — fast mode is Opus-only.

**E6.27 — D.** *(Model Selection and Optimization)* Dateless model IDs on 4.6 and later are fixed snapshots, not moving aliases. The comment therefore describes behaviour the ID does not have, and the practical consequence is that nobody has planned the migration this configuration will eventually need — with the minimum 60-day deprecation notice as the outer bound on reaction time. A, B and C are all true and all useful: reading the Models API `line` field rather than parsing the ID, monitoring the deprecations page, and relying on the 60-day minimum. Each is a piece of good migration hygiene. None of them corrects the false belief in the comment, which is what the review has to do first.

**E6.28 — B.** *(Agents and Workflows)* Default subagent concurrency is 20, so 200 children do not run in parallel — 20 run and the rest queue, which is why the wall-clock improvement falls far short of the projection. The second half of the answer is the one teams miss at consumer scale: every subagent is a full model request with its own prompt, so a 200-way fan-out multiplies the ITPM consumed per *user* request by up to 200, and the service hits its input-token limit long before it hits its request limit. A names the depth default (3), which bounds nesting rather than breadth. C and D are true statements about inheritance and turn counting that would produce different symptoms.

**E6.29 — C.** *(Agents and Workflows)* Per turn on Opus 5.5: cache read 16,000 × \$0.20/MTok (0.05x of \$4) = \$0.0032; uncached input 2,000 × \$4/MTok = \$0.0080; output 900 × \$20/MTok = \$0.0180. Total \$0.0292 per turn. Cumulative after 17 turns is 17 × \$0.0292 = \$0.4964, still under the cap; after the 18th it is \$0.5256. Because `max_budget_usd` is checked *after* a response arrives, the run completes turn 18 and only then stops — **overshooting to \$0.5256**. A stops at the last turn that stayed under, which is what a pre-request cap would do. B asserts that pre-request behaviour, which is the misconception the question targets. D invents an absorption that does not occur: the overshoot is real spend.

**E6.30 — A.** *(Agents and Workflows)* Clearing tool results invalidates the cached prefix: the prompt changes, so the next request pays a cache write across a prefix that by then is very large. That write is both a cost and a latency event, and because clearing is triggered by accumulated context it recurs periodically — matching the described pattern exactly. `clear_at_least` is the documented control for it: require each clearing to recover enough tokens to be worth the write, and raise the trigger so clearings are fewer and larger. B is a plausible tuning concern that would show as repeated tool calls, not latency spikes. C and D are true facts about `applied_edits` and the token-counting endpoint, both useful for observability and neither a cause.

**E6.31 — A and B.** *(Agents and Workflows)* `dontAsk` is the non-blocking mode by construction: any call that would prompt is denied outright and `canUseTool` is never invoked, so the agent has a fixed tool surface and no path that waits on a human. B is the coverage caveat that makes such a design trustworthy — a bare `allowedTools` entry auto-approves before the callback is reached, so a check that must run on every call belongs in a `PreToolUse` hook, which runs before every other step. C is precisely backwards: `defer` exists to wait for a human. D overstates `auto` mode, where a classifier reviews actions and blocks the ones it rejects. E is the documented trap: `allowed_tools` does not constrain `bypassPermissions`.

**E6.32 — D.** *(Agents and Workflows)* A deferral ends the turn. The application holds the message history and resumes later with a `tool_result` for the deferred `tool_use` — so the gap between the two requests is however long a human takes, which is unbounded and has nothing to do with the model. That makes deferral structurally incompatible with a p99 budget on the originating request: the right shape is to end the user-facing request, hand the pending action to an asynchronous flow, and notify when it resolves. A is wrong about the mechanism — nothing stays open server-side. B would resolve the call by removing the gate. C asserts a bound that does not exist.

**E6.33 — A.** *(Agents and Workflows)* Each tool-use turn is a full model round trip. Without `max_turns`, nothing bounds how many of them a single user-visible request can make, so the median reflects the common two- or three-turn case while the tail reflects whatever the agent decides to do — which is exactly the shape described. Capping `max_turns`, remembering that it counts tool-use turns only and not the final text turn, converts an unbounded tail into a bounded one with a defined degraded answer. B bounds cost and does so only after a response arrives, which makes it a poor latency control. C names a real default that bounds breadth, not depth. D describes a blocking behaviour the stem does not exhibit.

**E6.34 — C.** *(Agents and Workflows)* Each tool-use turn costs TTFT plus generation plus tool execution: 400 + (120 / 150 × 1,000) + 150 = 400 + 800 + 150 = 1,350 ms. The closing text-only turn costs 400 + (200 / 150 × 1,000) = 400 + 1,333 = 1,733 ms. The closing turn alone already consumes 1,733 ms of the 2,000 ms budget, so **zero** tool-use turns fit: adding one brings the total to 3,083 ms. The design conclusion is the useful part — at this budget the agent shape has to change (fewer output tokens, a cheaper closing turn, or tool work moved off the user-visible request), not just be tuned. A, B and D all omit the closing turn’s TTFT, its generation time, or both.

**E6.35 — A.** *(Agents and Workflows)* Hooks are the first step in the permission evaluation flow and they run on every tool call, so a network call inside a `PreToolUse` hook is added to the critical path of every turn. An agent that makes four tool calls per request pays the policy service’s latency four times, which is why p99 rises by more than one round trip. The remedies are to cache the decision locally for the life of the session and to scope the hook to the tools that actually need authorising. B misstates the flow — a hook `allow` does not skip the deny and ask rules, but that is a correctness property, not a doubled evaluation. C is true and is a reason to use hooks, not a latency mechanism. D invents a subprocess cost.

**E6.36 — D.** *(Prompt and Context Engineering)* ITPM counts `input_tokens` plus cache writes, and in steady state the prefix is read rather than written. With the breakpoint at the end of the system prompt, tools (500) and system (2,000) are cached and the entire 40-turn history is the uncached suffix: 40 × 300 = **12,000** ITPM-counted tokens per request. Moving the breakpoint to the end of turn 38 brings 38 × 300 = 11,400 of the history inside the prefix, leaving two turns: 2 × 300 = **600**. That is a 20x reduction in ITPM consumption and in the work done before the first token. A adds the already-cached 2,500 to the “before” figure. B leaves the cached prefix in the “after” figure. C reports the new cached prefix size rather than the new suffix.

**E6.37 — A and B.** *(Prompt and Context Engineering)* Both answers do the same thing from opposite ends: A moves the boundary forward so that stable history is inside the cached prefix, and B keeps volatile values from poisoning that prefix — a timestamp or device string inside the cached region changes it on every request and guarantees a miss. Together they are the whole technique for a chat endpoint. C would exceed the four-breakpoint limit and return 400. D is a data-residency control and a 1.1x price modifier, with no caching behaviour. E is built on a true fact about `max_tokens` and OTPM but does not change the prompt at all.

**E6.38 — B.** *(Prompt and Context Engineering)* Toggling web search or citations preserves the tools cache but invalidates the system and message caches, because the hierarchy runs tools → system → messages and a change at one level takes every level after it. The 50,000-token corpus lives in the system level, so it is invalidated by a toggle it has nothing to do with — which is why the corpus “never changing” is no protection. The remedy is to make the toggle a property of the thread rather than of the request. A gets the direction wrong: it is specifically the tools cache that survives. C misapplies the lookback window. D invents a mechanism — search results arrive as content, not as prefix edits.

**E6.39 — C.** *(Prompt and Context Engineering)* On the Claude API, a consecutive run of `tool_use` blocks counts as a single lookback position, and so does a consecutive run of `tool_result` blocks. So the 6 tool-use blocks count 1, the 6 tool-result blocks count 1, and the 14 text blocks count 14: **16 positions**, inside the 20-block window, so the breakpoint’s entry is still discoverable. This collapsing rule is what makes the window workable for tool-heavy agents, where a naive count runs out almost immediately. A is that naive count (6 + 6 + 14 = 26). B and D are arithmetic that no rule produces.

**E6.40 — A.** *(Prompt and Context Engineering)* Changing `output_config.format` invalidates the prompt cache for that conversation thread. Assigning a variant per *request* therefore guarantees a cache write on roughly half the turns of every conversation, which is a large cost on a long thread and buys nothing experimentally — the same comparison is available from disjoint traffic with sticky per-conversation assignment. B is true and is why grammar compilation is not the cost here. C is true and adds a small constant to every request under either design. D is a true output-ordering rule with no bearing on cost.

**E6.41 — D.** *(Prompt and Context Engineering)* On Fable 5.1, Opus 5.5, Sonnet 5.5 and Haiku 5.5, server-side context management never invalidates thinking blocks, and `clear_thinking_20251015` defaults to keeping all turns on those models — so thinking clearing is not where the churn comes from. Tool-result clearing is: it rewrites the prompt and invalidates the cached prefix each time it fires, which is exactly what `clear_at_least` is for. A gets the attribution backwards. B is wrong about scope — `clear_at_least` belongs to the tool-use clearing strategy. C treats the two strategies as symmetric, which on current models they are not.

**E6.42 — B.** *(Tools and MCPs)* Tool use injects a 286-token system prompt with `tool_choice: "auto"`, and that overhead sits inside the cached prefix along with the definitions. Before: (9,600 + 286) = 9,886 tokens × 40,000,000 = 395,440,000,000 tokens × \$0.01/MTok (0.1x of Haiku’s \$0.10) = **\$3,954.40** per day. After: (3,100 + 286) = 3,386 × 40,000,000 = 135,440,000,000 × \$0.01/MTok = **\$1,354.40**, a saving of **\$2,600.00** per day. A omits the 286-token overhead from both figures. C prices the reads at the base input rate instead of 0.1x. D has both figures right and subtracts carelessly, reporting the “before” value as the saving.

**E6.43 — A and B.** *(Tools and MCPs)* In the 2026-07-28 stateless revision, `server/discover` replaces `initialize` and per-request `_meta` carries what used to be session state. For a high-QPS client both facts point the same way: there is no handshake to amortise and no session to keep warm, so each request stands alone and the client’s connection strategy is a transport concern rather than a protocol one. C and D describe sampling and logging, both deprecated in that revision — and a client that depends on either for a round-trip saving or for progress reporting will find neither available. E is the opposite of stateless.

**E6.44 — C.** *(Tools and MCPs)* Forced `tool_choice` — `{"type": "any"}` and `{"type": "tool", ...}` alike — returns 400 on current models, so the optimisation fails outright rather than producing the saved round trip. Where the goal is a guaranteed machine-readable shape, `output_config.format` is the supported mechanism, and it is compatible with streaming so the latency path is preserved. A quotes the real token figures (286 for `auto` or `none`, 406 for the forced values) and would be a cost observation, not a 400. B is a true cache fact. D is a true statement about strict tool use — it validates arguments, not whether a tool is called — and is the closest distractor, because it correctly identifies what `strict` does *not* solve without naming what does.

**E6.45 — D.** *(Tools and MCPs)* A tool result is not a transient: it enters the conversation on the next turn, lands after the last breakpoint, and is therefore billed at the full input rate and reprocessed on every subsequent turn of the session. Forty full documents thus cost once in retrieval and then again, as input tokens and as TTFT, on every turn that follows — which is why both curves climb steadily rather than spiking. The fix is at the tool’s contract: return identifiers and short snippets, and fetch full text only for the two documents the agent actually needs. A is a real mitigation that fires only after the trigger is reached and costs a cache write when it does. B is a true lookback rule and does not bear on cost. C is true and is the assumption that allowed the design.

**E6.46 — A.** *(Tools and MCPs)* Allow rules accept tool-name globs only after a literal `mcp__<server>__` prefix, and the server segment must be glob-free so the rule names a server actually configured. `mcp__search__*` is therefore valid and does exactly what the team wants; an unanchored entry such as `mcp__*` or `*` is ignored with a startup warning and auto-approves nothing — a silent no-op rather than an error, which is the dangerous part. B asserts that `mcp__*` works and then proposes narrowing it, compounding the error. C denies glob support entirely. D asserts that `allowed_tools=["*"]` is effective, which it is not.

**E6.47 — B.** *(Security and Safety)* `metadata.user_id` is supplied by the caller for abuse detection. It carries no authentication whatsoever, so a backend that scopes access by reading it is trusting a value the client chose — the authorisation decision has to come from the server-side session instead. The second half matters independently: even as a label, the field should carry an opaque stable surrogate rather than an email address, so a personal identifier is not spread across request logs. A is true (512 characters) and essentially never binding for an email. C is true and is the cost-reporting consequence, not the security one. D misdescribes the field’s handling and would be the least of the problems here.

**E6.48 — C.** *(Security and Safety)* A key shipped inside an app binary is extractable, and once extracted it spends against the organization’s limits and quota with no attribution and no revocation short of rotating the key for every user. That is not an 80 ms trade; it is a credential disclosure with a cost ceiling set by the spend cap. The key stays server-side, and the perceived-latency gap is closed by streaming, which makes the hop invisible after the first token. A is false — streaming works from any client. B is true in the narrow sense that a fleet shares one organization’s limits, but it frames a security failure as a capacity one. D is a minor attribution consequence of a much larger problem.

**E6.49 — A and B.** *(Security and Safety)* A fetched page is content from outside the trust boundary, and the durable defence is that the agent’s authority does not depend on what the page says: code-level deny rules and a tool surface scoped to summarisation mean that no text in a page can widen what the agent can do. B closes the output side — structured output is validated against an application-side allow-list before anything acts on it. C is worth including but is prompt-level pleading on its own: it asks the model to be the boundary. D treats reasoning depth as a security control, which it is not in either direction. E increases exposure rather than reducing it, and logs page content the user may not expect to be retained.

**E6.50 — D.** *(Security and Safety)* A 429 raised by the monthly spend cap is typed `rate_limit_error` like any other, but carries `error.details.error_code == "enforced_spend_limit_reached"`, has no `retry-after`, and never succeeds on retry until access resumes. At 20,000 requests per minute a retry layer that does not distinguish it turns a billing event into a self-inflicted load event against an endpoint that cannot serve any of it. The correct behaviour is to branch on the code, fail over to a degraded non-model path immediately, and alert. A assumes a continuously replenishing limit that this is not. B misclassifies the error and sheds load that will never be served. C makes the amplification worse.

**E6.51 — A.** *(Claude Code)* `allowed_tools` pre-approves the tools it lists; it does not restrict the ones it omits. Unlisted tools match no allow rule, fall through to the permission mode step, and `bypassPermissions` approves them there — so the combination in the stem approves every tool, `Bash` and `Write` included. To block a tool in that mode, name it in `disallowed_tools`, where a bare name removes the definition from the request entirely. (The TypeScript SDK warns about a related shadowing case with the code `CLAUDE_SDK_CAN_USE_TOOL_SHADOWED`.) B is false — bare names are valid allow entries. C states a real restriction that applies to running as root outside a recognised sandbox, which a CI container typically is. D is false: hooks still execute in `bypassPermissions` and their denies still hold, which is why a hook is the right guard here.

**E6.52 — B.** *(Claude Code)* Switching to a model that auto mode does not support changes the session to `default` mode, and the SDK reports it with a `system` message of subtype `status` carrying `permissionMode: "default"`. The change is not reversed by switching the model back: the application must call `setPermissionMode("auto")` again once a supported model is active, and attempting it while the unsupported model is current fails with an explicit message. The practical lesson is to treat that status message as a signal to act on rather than noise. A is false. C invents a rule reset. D misattributes the behaviour to a classifier failure rather than the documented mode change.

**E6.53 — C.** *(Eval, Testing, and Debugging)* Two defects compound. A mean is the wrong statistic when the budget is written at p99 — a change can lower the mean while worsening the tail. And an end-to-end number collapses two quantities that move independently: time to first token and output tokens per second. Fast mode raises throughput and leaves TTFT alone; a better cache hit rate lowers TTFT; lower effort shortens generation. A single number cannot attribute a regression across those, and in this case a throughput win masked a TTFT regression that users felt immediately. A is wrong on the facts — 10,000 requests is ample for a p99. B is a real attribution difficulty that applies to any end-to-end measurement and is not what failed. D is a genuine hygiene point about mixing populations, and a sound secondary finding, but the eval would still be misleading with a single speed.
