## Section 1 — Applications and Integration

**E7.1 — C.** *(Applications and Integration)* Image tokens are counted in 28 x 28 pixel patches with each dimension rounded up independently: tokens = ceil(w / 28) x ceil(h / 28). First image: ceil(1450/28) = 52 and ceil(1090/28) = 39, giving 2,028. Second: 980/28 = 35 and 784/28 = 28 exactly, giving 980. Third: ceil(330/28) = 12 and ceil(220/28) = 8, giving 96. The total is 2,028 + 980 + 96 = 3,104. Option A (2,995) truncates instead of rounding up on every dimension, B (3,040) rounds up the width but truncates the height, and D (3,296) has no derivation behind it.

**E7.2 — A.** *(Applications and Integration)* Message prefilling returns 400 on Claude 4.6 and later, and prefilling was never compatible with constrained JSON output in any case. The documented replacement is `output_config.format` with `type: "json_schema"`, which constrains the response with a compiled grammar instead of a hand-rolled prefill-and-stop trick. B is wrong on its premise: the system prompt is not a prefill channel and moving the brace there would not produce JSON. C compounds the original mistake, since more stop sequences do not make a rejected prefill legal. D addresses truncation, which is a different failure that would surface as `stop_reason: "max_tokens"` rather than a 400 on every request.

**E7.3 — A, B.** *(Applications and Integration)* Two documented batch rules are broken. `stream: true` is an explicitly rejected parameter on the Batches API, alongside `speed` and `max_tokens: 0`, which is A. Batch results come back in arbitrary order and `custom_id` is the only join key, so joining by file position will silently mis-assign descriptions, which is B. C is false: the per-batch ceiling is 100,000 requests or 256 MB, and 80,000 is inside it. D is false in the direction stated — `custom_id` must be unique *within* a batch, not across batches, so reuse tomorrow is fine. E is false and inverted: `params` are validated asynchronously, and validation errors surface only after the batch has finished processing, which is precisely why the docs advise testing one request shape on the Messages API first.

**E7.4 — C.** *(Applications and Integration)* Work the three token streams separately at batch rates. Cache reads on Sonnet 5.5 are 0.05x the \$2 base input price, so \$0.10 per MTok, halved by the batch discount to \$0.05: 3,200 x 60,000 = 192 MTok x \$0.05 = \$9.60. Unique input bills at the batch input rate of \$1 per MTok: 400 x 60,000 = 24 MTok = \$24.00. Output bills at the batch rate of \$5 per MTok: 350 x 60,000 = 21 MTok = \$105.00. The total is \$9.60 + \$24.00 + \$105.00 = \$138.60. Option A (\$129.00) omits the cached tokens entirely, B (\$133.80) uses Fable 5.1’s 0.025x read multiplier rather than Sonnet 5.5’s 0.05x, and D (\$277.20) drops the batch discount from all three streams.

**E7.5 — D.** *(Applications and Integration)* Enabling citations together with `output_config.format` returns a 400; the two features are documented as incompatible. The design therefore has to give one up, and the usual resolution is to run a separate uncited structured pass for the fields and keep citations on a free-text pass, or to drop structured output and validate the JSON yourself. A misreads a 400 as a length problem. B invents behaviour: effort changes reasoning depth and has nothing to do with citation emission. C is wrong twice over, since `output_format` is deprecated and does not lift the citations restriction.

**E7.6 — B.** *(Applications and Integration)* Opus 5.5 bills input at \$4 per MTok, so 24,000 uncached tokens cost 0.024 x \$4 = \$0.096 each time. A 1-hour cache write is 2x base, \$8 per MTok, costing 0.024 x \$8 = \$0.192 once. A cache read on Opus 5.5 is 0.05x base, \$0.20 per MTok, costing 0.024 x \$0.20 = \$0.0048. At two requests caching costs \$0.192 + \$0.0048 = \$0.1968 against \$0.192 uncached, so caching still loses; at three it costs \$0.192 + \$0.0096 = \$0.2016 against \$0.288, so caching wins. Option A is the break-even you get with the 1.25x five-minute write multiplier instead of 2x, and C and D come from using the generic 0.1x read multiplier rather than Opus 5.5’s 0.05x.

**E7.7 — C.** *(Applications and Integration)* `metadata.user_id` is an abuse-detection signal. It is not a grouping dimension in the Usage or Cost APIs, so no amount of populating it will produce per-merchant spend. Attribution at that granularity comes from the structures the billing surfaces actually group by — separate API keys, or separate workspaces per merchant tier. A states a true fact, that the field is capped at 512 characters, but draws the wrong conclusion from it; B invents a Batches-only grouping rule; D invents a cache interaction, since request metadata is not part of the cached prefix.

**E7.8 — C.** *(Applications and Integration)* Haiku 5.5 is the only tiered model: a request whose input exceeds 100,000 tokens pays the 5x tier, and the threshold counts cache reads and writes as well as fresh input. Here 94,000 + 9,000 = 103,000, so the whole request prices at the tier: input \$0.50 per MTok, output \$2.50 per MTok, and cache reads at the standard 0.1x of the tiered input price, \$0.05 per MTok. Reads: 94,000 x \$0.05 / 1,000,000 = \$0.0047. Fresh input: 9,000 x \$0.50 / 1,000,000 = \$0.0045. Output: 600 x \$2.50 / 1,000,000 = \$0.0015. The total is \$0.0107. Option A prices everything at the base tier by excluding cache reads from the threshold, B applies the tier to fresh input and output but prices reads off the base rate, and D bills all 103,000 tokens as uncached tiered input.

**E7.9 — A, B, E.** *(Applications and Integration)* Tool definitions are billed as input tokens (A); the tool-use system prompt overhead — 286 tokens with `tool_choice` at `auto` or `none` — is added to input on every request that carries `tools` (B); and `tool_result` content is billed as input when your application sends it back (E). C is the trap: thinking tokens are real and billed, but as **output** tokens. D is wrong because `max_tokens` is a ceiling rather than a charge; you are billed for the tokens actually produced. F is wrong because breakpoints are markers and cost nothing in themselves — what costs is the cache write they trigger.

**E7.10 — A.** *(Applications and Integration)* The Messages API has no idempotency key. An `Idempotency-Key` header is simply not part of the contract, so a retry after a 500 may well produce a second completed generation, and the caller has to own deduplication — typically by writing a SKU-plus-attempt key to its own store before issuing the request and checking it on retry, or by moving the work onto the Batches API where `custom_id` gives a stable join key. B, C and D all presuppose that the key exists and merely has limits, which is the wrong starting point.

**E7.11 — B.** *(Applications and Integration)* Add the fixed parts: 14,000 for the system prompt, 11 x 520 = 5,720 for the tool definitions, 286 for the tool-use overhead at the default `tool_choice`, and 3,400 for the brief, which is 23,406. Adding the 32,000-token output reserve gives 55,406, leaving 1,000,000 − 55,406 = 944,594 tokens. Dividing by 1,850 gives 510.59, and only whole reviews count, so 510. Option C (511) takes the ceiling and overflows the window; A (504) reserves 44,000 for output instead of 32,000; and D (540) divides the full 1M window by 1,850, ignoring both the fixed overhead and the output reserve.

**E7.12 — D.** *(Applications and Integration)* The minimum cacheable prompt length on current models is 512 tokens, and a 380-token block is below it. Shorter prompts are processed without caching and **no error is returned**, which is exactly the silent-failure signature described. The fix is to let the breakpoint cover a larger stable prefix — brand voice plus taxonomy plus instructions — rather than the brand-voice block alone. A is false: system blocks are cacheable, and the tools-then-system-then-messages ordering exists precisely because all three levels cache. B is a real risk in general but the stem says the block is fixed. C is false; up to four breakpoints coexist, and a later one does not cancel an earlier one.

**E7.13 — A.** *(Applications and Integration)* Cache writes count toward the input-tokens-per-minute limit even though cache reads generally do not, so each request charges 60,000 + 2,000 = 62,000 tokens against the limit. 400,000 / 62,000 = 6.45, and you cannot run a fraction of a request, so the pool sustains 6 per minute. Option B rounds up and would exceed the limit. C comes from a decimal slip, dividing by 6,000 rather than 62,000. D counts only the 2,000 uncached tokens, which is the mistake the question is built to catch: the whole point is that writes are not free against the limit. The deeper fix, of course, is to stop flipping effort so the prefix is read rather than rewritten.

**E7.14 — B.** *(Applications and Integration)* `temperature`, `top_p` and `top_k` are deprecated on Claude 4.7 and later, and sending a non-default value returns 400. Determinism in an extraction pipeline comes from constraining the output rather than from sampling knobs: `output_config.format` fixes the shape of the answer, and `output_config.effort` governs how much reasoning goes into it. A fails because `top_k` is deprecated on the same models. C invents a relocation of the parameter. D is the most tempting distractor because `temperature: 0` sounds like the safest possible value, but the deprecation is of the parameter, not of particular values above zero.

**E7.15 — D.** *(Applications and Integration)* 1,120 / 28 = 40 exactly in both dimensions, so each image is 40 x 40 = 1,600 tokens, and 24 images give 38,400 tokens. At Sonnet 5.5’s \$2 per MTok input rate that is 38,400 x 2 / 1,000,000 = \$0.0768. The over-20-images rule in the stem is satisfied, since no dimension exceeds 2,000 pixels, so nothing is downscaled. Option A prices a single image. B halves one dimension’s patch count. C caps the count at 20 images, misreading the over-20 rule as a hard limit of 20 rather than as a constraint on dimensions once you pass 20.

**E7.16 — A, C.** *(Applications and Integration)* Prefixes cache in the order tools, then system, then messages, and a change at one level invalidates that level and every level after it. Adding a tool is a change at the first level, so all three prefixes go, which is A. Changing `output_config.effort` always invalidates the message cache and on some models the tool and system caches too, so C is correct as stated, with “at least” doing the necessary work. B contradicts the invalidation hierarchy. D is the plausible-sounding error the question targets: effort shapes output but is part of the request configuration the cache keys on. E is backwards — adding or removing an image invalidates only the message cache. F is also backwards: a system change leaves the tool prefix intact.

**E7.17 — A.** *(Applications and Integration)* A 429 carrying `error.details.error_code` of `enforced_spend_limit_reached` is a spend-cap rejection, not a throughput rejection. It carries no `retry-after` and is never retryable: retrying cannot succeed until a human raises the cap, so the correct behaviour is to classify the error code, stop the job and alert. B is the generic rate-limit playbook, which is right for ordinary 429s and wrong for this one. C is false — workspace spend limits apply to batch usage too, although a batch may slightly exceed the limit. D is false because the cap is on the workspace, not the key.

**E7.18 — D.** *(Applications and Integration)* Price each stage per SKU. Haiku 5.5, below the tier threshold: 2,400 x \$0.10 / 1,000,000 = \$0.00024 input and 500 x \$0.50 / 1,000,000 = \$0.00025 output, so \$0.00049. Sonnet 5.5: 1,800 x \$2 / 1,000,000 = \$0.0036 input and 900 x \$10 / 1,000,000 = \$0.009 output, so \$0.0126. Per SKU that is \$0.01309, and 150,000 SKUs cost \$1,963.50. Option A (\$1,423.50) drops stage two’s input tokens, B (\$1,890.00) drops stage one entirely on the assumption that Haiku is negligible, and C (\$1,926.00) drops stage one’s output. The lesson behind the arithmetic is that the cheap stage really is close to negligible here — but “close to” is not “equal to”, and the exam asks for the figure.

## Section 2 — Model Selection and Optimization

**E7.19 — B.** *(Model Selection and Optimization)* Haiku 5.5 per SKU: 3,000 x \$0.10 / 1,000,000 = \$0.0003 input plus 400 x \$0.50 / 1,000,000 = \$0.0002 output, so \$0.0005. Across 100,000 SKUs that is \$50.00. The 6% that fail are 6,000 SKUs re-run on Sonnet 5.5 at 3,000 x \$2 / 1,000,000 = \$0.006 plus 400 x \$10 / 1,000,000 = \$0.004, so \$0.01 each, or \$60.00. The all-in total for design one is \$110.00. Option A stops at the Haiku pass and ignores the rework, which is the specific error the question tests. C uses a 10% failure rate. D is design two’s total — \$1,000 of Sonnet plus \$400 of human review — and is there to be chosen by anyone who reads the wrong column.

**E7.20 — D.** *(Model Selection and Optimization)* The documentation names Claude Opus 5.5 as the recommended default for most workloads, and positions Claude Fable 5.1 for demanding reasoning and long-horizon agentic work, or for the case where Opus 5.5 at a higher effort setting still falls short on your own evals. A and B both name the wrong default. C inverts the documented path: starting at the top and stepping down until something breaks burns money establishing a ceiling you may never need, whereas the documented approach is to start at the recommended default and escalate on evidence from evals.

**E7.21 — C.** *(Model Selection and Optimization)* Priority Tier is closed to new purchase and excludes all of the current models, so it cannot appear in a capacity plan built on Fable 5.1, Opus 5.5, Sonnet 5.5 or Haiku 5.5. Peak headroom has to be engineered instead: move deferrable work to the Batches API, cache the stable catalogue prefix, and push the bulk extraction down the model ladder. A, B and D each concede the premise that the tier could be bought and then argue about its properties, which is the trap — the objection is availability, not fit.

**E7.22 — A, C.** *(Model Selection and Optimization)* Effort is configured through `output_config.effort` and takes `low`, `medium`, `high`, `xhigh` or `max`, which is A. Opus 5.5 and Haiku 5.5 default to `medium` while the other current models default to `high`, which is C. B names the wrong location and is a common migration error: effort is a sibling of the thinking configuration, not a field inside it, and `thinking` with `budget_tokens` returns 400 on 4.7 and later. D invents a `low` default for Sonnet 5.5. E is false and expensive to believe — changing effort between requests restarts the prompt cache, which is the whole subject of E7.23.

**E7.23 — C.** *(Model Selection and Optimization)* A five-minute cache write on Sonnet 5.5 is 1.25x the \$2 base, so \$2.50 per MTok: 80,000 tokens cost 0.08 x \$2.50 = \$0.20 per write. A read is 0.05x base, \$0.10 per MTok, so 0.08 x \$0.10 = \$0.008. Flipping effort on every request forces a write every time: 500 x \$0.20 = \$100.00. Holding effort constant pays one write and 499 reads: \$0.20 + 499 x \$0.008 = \$0.20 + \$3.992 = \$4.192. The difference is \$100.00 − \$4.192 = \$95.81. Option A is the 499 reads alone, B is the stable run’s total rather than the difference, and D is the flipping run’s total rather than the difference.

**E7.24 — B.** *(Model Selection and Optimization)* From Claude 4.6 onward, a model ID without a date is a fixed snapshot rather than a floating alias. `claude-sonnet-5-5` will keep resolving to the same weights; a newer Sonnet arrives under a new ID and has to be adopted deliberately. What the team does get is notice: a minimum of 60 days before a model is retired. A, C and D all accept the alias premise and then argue about the details of floating, which is the error the question is built around — there is no floating to qualify.

**E7.25 — B.** *(Model Selection and Optimization)* Haiku 5.5’s tier threshold is 100,000 input tokens and it re-prices the whole request, so a single 120,000-token request bills at \$0.50 per MTok: 120,000 x \$0.50 / 1,000,000 = \$0.0600. Two requests of 62,000 tokens each sit below the threshold and bill at the base \$0.10 per MTok: 62,000 x \$0.10 / 1,000,000 = \$0.0062 each, or \$0.0124 for the pair. The saving is \$0.0600 − \$0.0124 = \$0.0476, and it survives the 4,000 tokens of duplicated instructions comfortably. Option A is the split design’s cost, C is the single request’s cost, and D adds the two figures instead of subtracting.

**E7.26 — A, B, C.** *(Model Selection and Optimization)* All four current models offer a 1M-token context window and up to 128K output tokens (A); Fable 5.1 is \$10 per MTok input and \$50 per MTok output (B); and Haiku 5.5 is the only current model with tiered input pricing, the 5x step above 100,000 input tokens (C). D is wrong because Opus 5.5 reads cached tokens at 0.05x, not the generic 0.1x. E names the wrong default: that is Opus 5.5. F attributes Fable 5.1’s 0.025x read multiplier to Haiku 5.5, which uses the standard 0.1x.

**E7.27 — A.** *(Model Selection and Optimization)* This is a high-volume, tightly specified normalisation with a 0.3-point quality gap between the cheapest and the most expensive model, and the price difference is two orders of magnitude at the input rate. The efficiency-first path says to run it on the cheapest model that clears the quality bar, and Fable 5.1’s documented positioning is demanding reasoning and long-horizon agentic work, which this is not. B, C and D are all factually wrong: Fable 5.1 is supported on the Batches API, supports `output_config.format`, and has the same 1M context window as the rest of the line-up. They are tempting because each would be a decisive objection if true, and none of them is.

## Section 3 — Agents and Workflows

**E7.28 — A.** *(Agents and Workflows)* `max_budget_usd` is checked **after** a response arrives, not before one is requested, so the cap can be overshot by exactly one response. With \$1.94 spent after seven responses, the eighth is issued because the budget still had headroom, and its \$0.31 brings the total to \$2.25 before the check fires and ends the run with `error_max_budget_usd`. B assumes a pre-flight check and an unbilled cancellation, neither of which happens. C assumes clamping, which would require the cap to be enforced mid-response. D names a real subtype but the wrong one: the run ended on the budget, and the budget outcome has its own subtype.

**E7.29 — D.** *(Agents and Workflows)* `max_turns` counts tool-use turns only. A run can therefore contain many assistant and user messages while consuming very little of the budget, because only the turns in which the agent actually calls a tool are counted. A inverts the rule exactly. B is false: the limit is enforced by the SDK. C is false — a subagent’s turns are counted against the subagent, not against the parent, which is why subagent depth and concurrency have their own separate caps.

**E7.30 — C.** *(Agents and Workflows)* Two separate defaults produce the two symptoms. Subagent concurrency defaults to 20, so of the 60 spawned subagents only 20 execute at a time and throughput plateaus at that ceiling rather than scaling with the fan-out. Subagent depth defaults to 3, so a fourth generation is refused, which is why the deepest level never runs. A, B and D each get one of the two numbers wrong, and D in particular invents a spend-cap explanation for a limit that depth already accounts for.

**E7.31 — A, C.** *(Agents and Workflows)* The valid `ResultMessage.subtype` values are `success`, `error_max_turns`, `error_max_budget_usd`, `error_during_execution` and `error_max_structured_output_retries`. A and C are on that list. B, D and E are invented: a rate-limit failure or a denied tool surfaces as `error_during_execution`, and context overflow is handled by compaction and context editing rather than by terminating the run with a dedicated subtype. The useful discipline here is remembering that the subtype enumerates *how the run ended*, which is why every member is either success or one of the four named limits.

**E7.32 — A.** *(Agents and Workflows)* The fault is that 320 tool definitions are in context for every single decision, which both costs 48,000 input tokens per request and gives the model a selection problem it cannot do well. The documented remedy is twofold: keep the handful of frequently used tools loaded and defer the rest behind tool search, and split the work across subagents whose tool sets are scoped to their task. B raises effort, which makes each decision slower and more expensive without shrinking the decision space. C describes caching, which lowers the cost of the definitions but leaves selection accuracy exactly where it was — a true statement about caching that does not address the stated problem. D is simply false: moving definitions into the system prompt would break tool use altogether.

**E7.33 — C.** *(Agents and Workflows)* `clear_tool_uses_20250919` defaults to a trigger of 100,000 input tokens and keeps the 3 most recent tool use and result pairs. Input grows as 22,000 + 12,000k, where k is the number of accumulated tool results. Setting 22,000 + 12,000k at or above 100,000 gives 12,000k at or above 78,000, so k is at least 6.5, and since k is a whole number the threshold is first crossed at k = 7. Clearing therefore fires at the 7th tool call. Option B takes the floor of 6.5 rather than the ceiling, which leaves input at 94,000 and below the trigger. Option A divides the 100,000 trigger by 12,000 to get 8 and then subtracts the 3 kept pairs, which misreads `keep` as part of the trigger condition rather than as what survives the clear. D adds a call by treating the crossing as happening on the request after the one that exceeds the trigger; by the 8th call input is already 118,000.

**E7.34 — D.** *(Agents and Workflows)* When both context-editing strategies are enabled, `clear_thinking_20251015` must come first in the `edits` array; the ordering is a documented requirement rather than a stylistic preference, and reversing it does not behave as described. A is false, since the two are explicitly designed to be combined. B is false: both ship under the same `context-management-2025-06-27` beta header. C invents a dependency — `clear_at_least` is an optional guard that stops a clear from firing unless it frees a worthwhile number of tokens, and it is good practice with caching, but it is not required by the presence of thinking clearing.

**E7.35 — B.** *(Agents and Workflows)* Three of the four sub-tasks are independent and one depends on them, which is the textbook case for parallelisation feeding a chained step: fan out extraction, category assignment and the compliance flag concurrently, join their results, then run copy generation once on the joined output. A collapses the structure into a single agent, which serialises work that need not be serialised and puts all four jobs’ instructions in one context. C serialises everything for a caching benefit that a shared cached prefix across the parallel calls would give anyway. D is wrong on the facts of the stem, since copy generation genuinely depends on the other three and cannot be reconciled after the fact.

## Section 4 — Prompt and Context Engineering

**E7.36 — A.** *(Prompt and Context Engineering)* A cached prefix must be byte-identical across requests, and putting the per-request SKU payload first guarantees that nothing after it ever matches. Reordering so that the style guide, taxonomy and instructions come first and the SKU payload comes last makes the 42,000 tokens of stable content a genuine prefix that the breakpoint can cover. B moves the breakpoint further into territory that changes every request, which makes the miss worse rather than better. C is a true statement about TTLs that is irrelevant: a one-hour cache of a prefix that differs on every request still never hits. D splits a prefix that is already invalidated at its first block.

**E7.37 — C.** *(Prompt and Context Engineering)* Structured output may return an enum value that differs from the schema only in capitalisation, with no error and no special `stop_reason`. The documented handling is to compare case-insensitively downstream and to avoid designing enums whose members differ only by case, since those become genuinely ambiguous. A is the wrong direction: adding lowercase variants creates exactly the case-only collision the documentation warns against. B misdiagnoses a silent casing difference as a compilation failure, which would have returned a 400 at request time. D confuses an object-level constraint with enum value matching.

**E7.38 — D.** *(Prompt and Context Engineering)* Asking for step-by-step reasoning inside a constrained structured output can produce a reasoning-extraction refusal, which arrives as `stop_reason: "refusal"` with a 200 status and is billed, and whose output may not match the schema. The documented remedy is to ask for a short explanation rather than extended reasoning. A misreads a refusal as truncation, which would be `stop_reason: "max_tokens"`. B is wrong because `additionalProperties: false` is required on objects and is unrelated to refusals. C overstates the constraint: auditability is perfectly achievable within structured output, just not in the form of long chains of reasoning.

**E7.39 — A, B, C.** *(Prompt and Context Engineering)* String length constraints (A) and numeric constraints (B) are both outside the supported schema subset, as are recursive schemas (C), which cannot be compiled into a grammar. SDK helpers fold unsupported constraints into field descriptions rather than enforcing them, which is worth knowing because it means the constraint quietly becomes advice. D, E and F are all supported: `anyOf` works, internal `$ref` works, and `enum` over scalar values works. The one `$ref` subtlety to remember is that `allOf` combined with `$ref` is the documented exception.

**E7.40 — B.** *(Prompt and Context Engineering)* A breakpoint looks back at most 20 block positions, counting itself as the first. A prefix boundary 26 positions back is beyond that window, so no cached prefix is found. The arithmetic is worth doing carefully, because consecutive `tool_use` blocks collapse to one position and so do consecutive `tool_result` blocks — which means a conversation that looks like 26 blocks may be fewer positions than it appears, or more. A is false: four breakpoints is the ceiling, not an overrun. C is false, since tool results cache normally. D invents an evaluation order.

**E7.41 — A.** *(Prompt and Context Engineering)* The schema already enforces the types; what varies is the convention for which unit to normalise into, and a prose description of a convention is weaker than a demonstration of it. Two or three worked examples that span the cases — one input stated in grams, one in kilograms — give the model the mapping directly. B fails because numeric constraints are unsupported and would return 400. C raises effort, which is a real knob and will not teach a convention the prompt never shows. D is the subtle one: field descriptions do travel with the schema and do influence the model, but they are not enforced by the compiled grammar, so the claim as stated is wrong.

## Section 5 — Tools and MCPs

**E7.42 — D.** *(Tools and MCPs)* Forced `tool_choice`, in both the `any` and the named-`tool` forms, returns 400 on current models. The guarantee the team wants is a guarantee about the *shape of the response*, and that is now expressed through `output_config.format`: constrain the response to the attribute schema and the model must return that object, with `tool_choice` left at its default. A is wrong because `any` is forced too and fails identically. B is a real parameter with a real effect on parallel calls, but it does not force a call to happen. C invents a beta header that re-enables a removed behaviour.

**E7.43 — B.** *(Tools and MCPs)* Sum the parts: 6,000 for the system prompt, 14 x 410 = 5,740 for the tool definitions, 2,000 for the user brief, and 286 for the tool-use system prompt overhead at the default `auto` setting of `tool_choice`. The total is 6,000 + 5,740 + 2,000 + 286 = 14,026. Option A omits both the brief and the overhead. C uses 406, which is the overhead for a forced `tool_choice` of `any` or `tool` — and which could not apply here anyway, since forced choice returns 400 on current models. D adds both overhead figures together.

**E7.44 — A, B.** *(Tools and MCPs)* The stateless 2026-07-28 revision replaces `initialize` with `server/discover` for capability negotiation (A) and moves per-request context into a `_meta` field on each request, so the server holds no session state between calls (B). C is the opposite of the revision’s intent: removing the session is the point, so there is no identifier to echo. D is backwards — sampling and logging are deprecated, not promoted. E is invented; tools remain part of the protocol.

**E7.45 — C.** *(Tools and MCPs)* Sampling is deprecated in the stateless revision, so a server-initiated callback into the client’s model is no longer a design the server can rely on. The stateless-friendly shape is to make ambiguity part of the tool’s return value: hand the candidate SKUs back as the tool result and let the agent’s next turn choose, which keeps the decision in the agent loop where the model and its context already are. A conflates a deprecated capability with a long-running one. B is a real pattern but a heavier one, since it puts model credentials, cost and latency inside the MCP server. D is wrong because the client negotiates the revision, not the server, and pinning backwards is not something the server can unilaterally do.

**E7.46 — B.** *(Tools and MCPs)* The model selects tools from their definitions, so when two neighbouring tools each carry one line of description there is nothing in context that distinguishes them. The reliable fix is to make each description state its purpose, its boundaries and when the sibling tool is the right choice, naming that sibling. A is superstition: array order is not a selection mechanism. C constrains how many tools can be called at once, not which one is chosen. D is true about what `strict: true` does — it validates names and inputs with grammar-constrained sampling — but validating the arguments of the wrong tool does not make it the right tool.

## Section 6 — Security and Safety

**E7.47 — A.** *(Security and Safety)* The structural fault is that one agent both reads untrusted third-party text and holds a write-capable tool, so any instruction smuggled into a review has a direct path to a price change. The fix has two halves and both matter: mark review text explicitly as data to be summarised rather than instructions to be followed, and take the mutation capability away from the component that reads untrusted input, moving price changes behind a separate human-approved path. B is the single most common wrong answer in this area: an instruction to ignore instructions is itself just text in the prompt and does not change what the agent is *able* to do. C invents a robustness property of effort. D is worth doing as hygiene but does not touch text-only injections.

**E7.48 — A, B.** *(Security and Safety)* Both correct options constrain what an injected instruction can actually cause. Giving the agent read-only tools and routing every mutation through a human-approved service means a successful injection produces a bad suggestion rather than a bad write (A), and validating proposed actions against an allow-list of operations and value ranges catches the ones that slip through (B). C and F are prompt-level instructions and delimiters: useful defence in depth, but they operate inside the channel the attacker already controls and cannot be relied on. D is false — susceptibility to injection is not a capability ladder. E is detection after the fact, which is valuable for response but does nothing to reduce blast radius.

**E7.49 — D.** *(Security and Safety)* Untrusted supplier content belongs in a user-turn content block, explicitly labelled as input to be processed, with the instructions kept in the system prompt where the trust boundary is clear — and the extracted attributes validated against both the schema and the business rules before anything is written to the catalogue. A puts untrusted text in the most authoritative channel, which is exactly backwards. B removes the separation that lets the model tell instructions from data. C asks for something the model does not do and would be a serious flaw if it did.

**E7.50 — C.** *(Security and Safety)* Two distinct leaks are described. The logs retain customer names and order references that the extraction task does not need, which is a data-minimisation failure; and `metadata.user_id` is populated with an email address, when that field is an abuse-detection signal that should carry an opaque, non-reversible identifier rather than directly identifying data. A is a true-sounding irrelevance about batch retention. B states a real property of the field, the 512-character cap, but draws a trivial operational conclusion from it rather than the privacy one. D invents a cache interaction, since request metadata is not part of the cached prefix.

## Section 7 — Claude Code

**E7.51 — D.** *(Claude Code)* In Claude Code’s permission model, deny takes precedence over allow, and an allow rule cannot carve an exception out of a deny rule however narrowly it is written. The only way to permit the feature-branch push is to narrow the deny rule itself so that it no longer matches. A overstates settings precedence, which does matter but is not what decides this case — even a project-level allow would lose to a project-level deny. B invents a pattern-syntax requirement. C invents file-order evaluation, which would make the outcome depend on rule position rather than on rule type.

**E7.52 — A.** *(Claude Code)* `CLAUDE.md` at the project root is Claude Code’s project memory: it is loaded automatically for sessions in that repository, which is exactly the “every session knows this without anyone pasting it” requirement. B is wrong on two counts, since custom slash commands are merged into skills and are invoked rather than loaded automatically. C would apply the conventions to every repository the developer opens, including ones where they are wrong. D is both more fragile than the declarative mechanism and based on a false premise that no project memory exists.

## Section 8 — Eval, Testing, and Debugging

**E7.53 — B.** *(Eval, Testing, and Debugging)* A uniform random sample of SKUs produces a field population dominated by the attributes that appear on almost everything — brand, colour, basic dimensions — which are also the easiest to extract. A single averaged accuracy figure is therefore mostly a measurement of the easy majority, and it can stay high while the rare, high-value attributes that merchandisers actually care about perform badly. The fix is to stratify by attribute and report per-attribute precision and recall, weighting the commercially important attributes explicitly. A treats a structural bias as a sample-size problem, and a larger uniform sample reproduces the same bias with tighter error bars. C substitutes a cost metric for a quality metric. D names a real discipline — evaluate on the production snapshot — that would not produce this particular pattern of complaint.
