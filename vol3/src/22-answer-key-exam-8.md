## Section 4 — Prompt and Context Engineering

**E8.37 — C.** *(Prompt and Context Engineering)* Structured output may return an enum value differing from the schema in capitalisation only, with no error and no distinguishing `stop_reason`. The documented handling is to compare case-insensitively downstream and to avoid enums whose members differ only by case, since those become genuinely ambiguous. A is the wrong direction, creating exactly the case-only collision the documentation warns against. B misdiagnoses a silent casing difference as a compilation failure, which would have returned 400 at request time. D confuses an object-level constraint with enum matching.

**E8.38 — A, B, C.** *(Prompt and Context Engineering)* String length constraints (A), numeric constraints (B) and recursive schemas (C) are all outside the supported subset and return 400. **E8.39 — D.** *(Prompt and Context Engineering)* Requesting step-by-step reasoning inside a constrained structured output can produce a reasoning-extraction refusal, which arrives as `stop_reason: "refusal"` with a 200 status, is billed, and may not match the schema. **E8.40 — D.** *(Prompt and Context Engineering)* A breakpoint looks back at most 20 block positions, counting itself as the first, so a boundary 27 positions back cannot be reached and no cached prefix is found. **E8.41 — A.** *(Prompt and Context Engineering)* The schema already pins the type to an integer; what varies is the convention for what that integer means and how to derive it, and a prose statement of a convention is weaker than a demonstration of it. D is the subtle distractor: field descriptions do travel with the schema and do influence the model, but the compiled grammar enforces structure and type, not the semantics written in a description.

## Section 6 — Security and Safety

**E8.47 — D.** *(Security and Safety)* The structural fault is that a single component both reads untrusted submitted text and holds the capability to publish, so an instruction smuggled into a description has a direct route to a release. Both halves of the fix matter: label submitted text explicitly as content to assess rather than instructions to follow, and take the publishing capability away from the component that reads untrusted input, so that releasing an asset runs through a separate authorised path. A is the most common wrong answer in this area: an instruction to ignore instructions is itself just text in the same channel the attacker controls, and it does not change what the agent is able to do. B invents a robustness property of effort. C is reasonable hygiene and useless against a text-only injection.

**E8.48 — C.** *(Security and Safety)* The stem reports two failures at once — 82% of escalations are cleared, so precision at the current threshold is poor, and the auto-cleared stream is leaking cases, so recall is poor too — and no single cut point fixes both, because moving it trades one against the other. The engineering answer is to characterise the classifier across its score range on a labelled set and then operate two thresholds: auto-clear below the lower, auto-escalate above the upper, and route only the uncertain band to humans, with the band’s width set by what review capacity can absorb. A optimises precision alone and widens the leak the spot checks already found. B optimises recall alone and buries the reviewers the stem says are already overwhelmed. D removes the calibrated score, which is the only thing that makes a banded policy possible.

**E8.49 — A, B.** *(Security and Safety)* Both correct options constrain what an injected instruction can cause rather than trying to prevent it being read. Read-only tools plus an authorised path for state changes means a successful injection yields a bad suggestion instead of a bad action (A), and validating proposed actions against an allow-list of operations and value ranges catches what gets through (B).
