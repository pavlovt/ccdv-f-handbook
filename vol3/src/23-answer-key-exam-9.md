**E9.1 — C.** *(Applications and Integration)* The cache write is 120,000 × \$2/MTok × 1.25 = \$0.30. **E9.2 — B.** *(Applications and Integration)* A cache breakpoint caches everything *before* it. Placing the breakpoint after per-user retrieved chunks means the cached prefix contains material unique to one user and one question, so no two requests share it and every request is a write. The fix is to put the breakpoint immediately after the stable corpus and leave retrieval and the question outside it. **A** is a real control — the 1-hour TTL does last longer — but a prefix that is unique per request will miss at any TTL. **C** correctly states the 20-block lookback, and **D** correctly states that writes count toward ITPM, but neither explains a hit rate of zero across all users.

**E9.3 — D.** *(Applications and Integration)* Total input is 95,000 + 8,000 = 103,000 tokens, which crosses Haiku 5.5’s 100,000-token threshold; cache reads count toward that threshold, and the 5× surcharge is applied per request to the whole request. Untiered, one request is (95,000 × \$0.10/MTok × 0.1) + (8,000 × \$0.10/MTok) + (1,200 × \$0.50/MTok) = \$0.00095 + \$0.00080 + \$0.00060 = \$0.00235. Multiplying by 5 gives \$0.01175, and 1,000 requests cost \$11.75. **A (\$2.35)** omits the surcharge entirely — the trap is assuming the 8,000 uncached tokens are what the threshold measures. **B (\$9.38)** uses a 0.05× read multiplier; Haiku 5.5 reads at 0.1×. **C (\$7.95)** applies the surcharge only to the uncached and output tokens rather than to the request as a whole.

**E9.4 — A.** *(Applications and Integration)* `temperature`, `top_p` and `top_k` are deprecated on Claude 4.7 and later and return 400. **E9.5 — B and D.** *(Applications and Integration)* A request may carry at most four cache breakpoints, which is exactly enough for the tools, handbook and corpus layers with one spare (**B**), and cache lookup walks back at most 20 content blocks from a breakpoint, so a prefix fragmented into many small blocks can fail to match even when its text is unchanged (**D**). **A** is false: breakpoints may be set on tool definitions and on message content as well as the system prompt. **E** is the minimum-size rule with the wrong number — the minimum on current models is 512 tokens, not 5,000. **C** inverts the invalidation hierarchy, which runs tools → system → messages: a tool change invalidates everything below it, including the handbook and corpus.

**E9.7 — A.** *(Applications and Integration)* Structured output via `output_config.format` is incompatible with citations and the combination returns 400. **E9.8 — D.** *(Applications and Integration)* Input is 4,000 × 3,200 × \$2/MTok = \$25.60 and output is 4,000 × 400 × \$10/MTok = \$16.00, giving \$41.60 at full price. **E9.10 — C.** *(Applications and Integration)* Staleness is a property of the corpus, and the model can only reason about what reaches its context. **E9.51 — C.** *(Claude Code)* `CLAUDE.md` at the repository root is loaded as project memory for every Claude Code session in that project, which makes it the right home for conventions that should apply to everyone without anyone having to remember them — and being in the repository, it is reviewed and versioned with the code it describes. **A** depends on each engineer remembering. **B** makes the conventions opt-in at exactly the moment they are most likely to be forgotten. **D** scopes them to one engineer across all their projects, which is both too narrow and too broad.

**E9.52 — B.** *(Claude Code)* In Claude Code’s permission model, deny takes precedence over allow, and an allow rule cannot carve an exception out of a deny. The only way to permit the wiki host is to narrow the deny pattern itself so it no longer matches those invocations. **A** applies a specificity rule the model does not use. **C** describes a prompt-on-conflict behaviour that does not occur — the deny simply wins. **D** states the settings precedence backwards for this case and, more importantly, misses that precedence between files is a separate question from deny beating allow within the resolved set.

------------------------------------------------------------------------

**E9.53 — D.** *(Eval, Testing, and Debugging)* The suite has two structural blind spots. It samples only questions that already work, so it is a regression net with no coverage of the failure modes this system actually has; and it scores against the same corpus the assistant retrieves from, which makes a confidently cited stale document look like a pass. An eval that could catch the production complaints needs unanswerable questions with “I don’t know” as the expected output, deliberately stale documents with a known correct behaviour, and per-entitlement cases asserting that a scoped user’s retrieval does not return out-of-scope material. **A** and **C** are reasonable improvements that would not have caught anything here. **B** overcorrects: LLM judging is workable for grounded answers, and swapping the judge does nothing about a case set that never poses the hard question.
