## Section 1 — Applications and Integration

**E11.1 — C.** *(Applications and Integration)* Work the four components separately, then halve. The single cache write is 12,000 × \$0.125/MTok (the 5-minute write multiplier of 1.25× applied to Haiku 5.5’s \$0.10 input rate) = \$0.0015. The 39,999 cache reads are 39,999 × 12,000 = 479,988,000 tokens at \$0.01/MTok (0.1× of \$0.10) = \$4.79988. Fresh input is 40,000 × 800 = 32,000,000 tokens at \$0.10/MTok = \$3.20, and output is 40,000 × 200 = 8,000,000 tokens at \$0.50/MTok = \$4.00. The synchronous total is \$11.99998, and the Batches API 50% discount — which stacks with caching — halves it to **\$6.00**. B is that same total with the batch discount forgotten; D prices the cache reads at the full input rate (\$47.9988 + \$3.20 + \$4.00 = \$55.20, halved to \$27.60); A treats cache reads as free (\$3.20 + \$4.00 + \$0.0015, halved). Note also that per-request input here is 12,800 tokens, comfortably below Haiku 5.5’s 100,000-token tiering threshold, so no multiplier applies.

**E11.2 — A.** *(Applications and Integration)* Per-request input is 120,000 + 20,000 = 140,000 tokens, above the 100,000-token threshold, and the threshold counts cache reads as well as fresh input — this is the step most candidates miss. So all input rates for the request are multiplied by 5. Cache read: 120,000 × \$0.01 × 5 / 1,000,000 = \$0.006. Fresh input: 20,000 × \$0.10 × 5 / 1,000,000 = \$0.010. Output: 3,000 × \$0.50 / 1,000,000 = \$0.0015, unmultiplied. Per request \$0.0175; 2,000 requests = **\$35.00**. B (\$9.40) assumes the tier never fires; C (\$25.40) applies the multiplier only to the fresh input, as if cache reads sat outside the tiered rate; D (\$47.00) wrongly multiplies the output tokens too.

**E11.3 — B and C.** *(Applications and Integration)* Batch results come back in arbitrary order, and `custom_id` is the only reliable join key, so positional matching will silently mis-assign results across 60,000 rows — the worst kind of defect because the job still “succeeds.” Separately, `max_tokens: 0` is rejected, along with `stream` and `speed`, so the token-count-only subset cannot be expressed this way. A is wrong because 60,000 is under the 100,000-request limit. D confuses the 24-hour *expiry* for an in-flight batch with the 29-day *retention* of results. E is false: batching and caching stack. F is wrong about what expiry means and, in any case, polling is the documented way to learn a batch’s state.

**E11.4 — B.** *(Applications and Integration)* A request may define at most four cache breakpoints; this one defines six, so it is rejected outright. The reasoning behind the design is not silly — finer granularity really would let partial corpus changes preserve more prefix — but it collides with a hard limit, and the fix is to consolidate the three corpus blocks behind one or two breakpoints. A is false (tool definitions are the canonical first cacheable segment). C is false; a breakpoint on the final turn is legitimate. D inverts the documented ordering, which puts stable material first.

**E11.5 — B.** *(Applications and Integration)* Opus 5.5’s cache read multiplier is 0.05×, not the generic 0.1× — \$4 × 0.05 = \$0.20/MTok. Write: 180,000 × \$5/MTok (1.25× of \$4) = \$0.90. Reads: 400 × 180,000 = 72,000,000 tokens × \$0.20/MTok = \$14.40. Fresh input: 400 × 500 = 200,000 × \$4/MTok = \$0.80. Output: 400 × 1,200 = 480,000 × \$20/MTok = \$9.60. Total **\$25.70**. C (\$40.10) uses the generic 0.1× read rate; A (\$24.80) drops the cache write; D (\$298.40) is the no-caching baseline, useful as a sanity check — caching here saves about 91%.

**E11.6 — D.** *(Applications and Integration)* A 429 carrying `error.details.error_code == "enforced_spend_limit_reached"` is a spend-cap rejection, not a rate-limit rejection. It carries no `retry-after` and is never retryable: no amount of waiting raises the cap. The worker must classify 429s by error code and fail fast on this one, surfacing it so a human can raise the limit. A is wrong because there is no `retry-after` to honour. B invents a clearing cycle that does not exist. C is wrong: spend limits apply to batch traffic too.

**E11.7 — D.** *(Applications and Integration)* Apply the ceiling on each axis independently. For 1,130 × 870: ceil(1130/28) = ceil(40.36) = 41 and ceil(870/28) = ceil(31.07) = 32, giving 41 × 32 = 1,312 tokens; six panels = 7,872. For 910 × 1,405: ceil(910/28) = ceil(32.5) = 33 and ceil(1405/28) = ceil(50.18) = 51, giving 33 × 51 = 1,683; two panels = 3,366. Total **11,238**. B (10,640) floors both axes instead of ceiling them; C (10,740) rounds each axis to the nearest integer; A (10,786) computes area ÷ 784 and rounds once at the end, which is the same formula only when both dimensions divide evenly by 28.

**E11.8 — C.** *(Applications and Integration)* Maximum output is 128K tokens, so `max_tokens: 200000` is not a valid request regardless of the context window; the extraction has to be decomposed, typically by section with a stable cached prefix. A invents a streaming-specific cap. B invents a Batches API requirement. D is the most tempting distractor because it is almost a real concern — input and output do share the window in the sense that both are accounted for — but it is not what blocks this request. The blocking fact is the flat output ceiling.

**E11.9 — D.** *(Applications and Integration)* The Messages API has no idempotency key. A header containing a UUID is simply an unrecognised header, so the retry is an ordinary second request: billed, executed, and producing a second row. De-duplication must live in the job runner — persist a request fingerprint before dispatch and check it before re-submitting. A is wrong because `custom_id` is a Batches API join key, not a de-duplication token. B and C invent semantics that do not exist.

**E11.10 — B.** *(Applications and Integration)* Two caps apply and the smaller one binds. By count: 100,000 requests per batch. By size: 256,000,000 ÷ 4,000 bytes = 64,000 requests per batch. 64,000 is the real cap, so the job needs ceil(260,000 ÷ 64,000) = ceil(4.0625) = **5 batches, bound by the payload limit**. A applies only the request-count cap and gets 3. D gets the right count by arithmetic coincidence of guessing but attributes it to the wrong limit — and attributing it correctly matters, because the fix (trim per-request payload) differs from the fix for a count limit. C misreads the 24-hour expiry as a batching constraint.

**E11.11 — A.** *(Applications and Integration)* `clear_tool_uses_20250919` defaults to a 100,000-token trigger and keeps the 3 most recent tool uses. B invents size-based selection. C inverts recency — keeping the oldest results would discard exactly the context the agent is currently working with. D confuses the context trigger with `max_tokens`, which governs output length and has nothing to do with clearing.

**E11.12 — A and C.** *(Applications and Integration)* `output_config.format` is the first-class structured-output field, and the older `output_format` is deprecated in favour of it; and `output_config.format` is incompatible with citations, so combining the two in one request returns a 400. The team must choose: structured output, or citations with the attribution guarantees they bring. B inverts the deprecation direction. D invents a Batches-only restriction. E is wrong in the most dangerous way — the request fails loudly, it does not silently drop citations. F is wrong twice over, since forced `tool_choice` values are themselves rejected on current models.

**E11.13 — B.** *(Applications and Integration)* Cache writes count toward ITPM; cache reads generally do not. Fresh input: 40 × 6,000 = 240,000. Cache writes: 3 × 180,000 = 540,000. Total counted = **780,000**. A counts only the fresh input and forgets that writes are charged against the limit — the error that produces surprise throttling after a prompt change invalidates a prefix. C counts the 7,200,000 tokens of cache reads and nothing else; D counts everything, which is the worst over-estimate and would lead the team to buy capacity they do not need.

**E11.14 — C.** *(Applications and Integration)* 1,180,000 + 40,000 = 1,220,000 input tokens against a 1M context window. The request will not fit, and no output budget changes that. A inverts the relationship in a way that sounds plausible but gets the magnitude wrong — 20,000 tokens is not what breaks this. B is false; system prompt tokens count. D is simply wrong about units. The real fix is staged synthesis: summarise in tranches, then synthesise the summaries.

**E11.15 — A.** *(Applications and Integration)* On Opus 5.5 the derived rates are: 1-hour write \$4 × 2 = \$8/MTok, 5-minute write \$4 × 1.25 = \$5/MTok, cache read \$4 × 0.05 = \$0.20/MTok. With the 1-hour TTL: one write of 250,000 × \$8/MTok = \$2.00, plus 19 reads at 250,000 × \$0.20/MTok = 19 × \$0.05 = \$0.95, giving \$2.95. With the 5-minute TTL every query is a fresh write, because the gaps exceed the TTL: 20 × 250,000 × \$5/MTok = 20 × \$1.25 = \$25.00. Saving = \$25.00 − \$2.95 = **\$22.05**. B (\$23.00) compares the 20 writes against the single 1-hour write while ignoring the 19 reads; C (\$22.80) prices the 1-hour write at the 5-minute 1.25× multiplier; D (\$12.50) is a guess that the 1-hour option simply halves the cost.

**E11.16 — D.** *(Applications and Integration)* Batch results are retained for 29 days. A six-week archival cycle loses them, so archival must run inside the retention window. B confuses retention with the 24-hour processing expiry, which is about how long an in-flight batch may take, not how long results live. C garbles the same two figures. A invents a one-download restriction.

**E11.17 — A, B and D.** *(Applications and Integration)* The 50% batch discount stacks with prompt caching; a batch is capped at 100,000 requests and 256 MB; and results come back in arbitrary order with `custom_id` the only dependable join key. C is false — `stream` is rejected inside a batch, along with `speed` and `max_tokens: 0`. E is false: spend limits still apply. F directly contradicts A and is the single most expensive misconception in this list, because it leads teams to drop caching from batch jobs on the theory that it would be wasted.

**E11.18 — A.** *(Applications and Integration)* Changing the effort level restarts the cache, so the alternating run never gets a read: all 60 requests are writes at 400,000 × \$2.50/MTok = \$1.00 each, giving \$60.00. Grouped, each of the two effort levels pays one write and 29 reads: 2 × \$1.00 = \$2.00 plus 58 × 400,000 × \$0.10/MTok = 58 × \$0.04 = \$2.32, giving \$4.32. Saving = \$60.00 − \$4.32 = **\$55.68**. B (\$58.00) assumes the grouped run costs only its two writes, dropping the 58 reads. C (\$56.68) counts one write instead of two in the grouped run. D is the misconception the question exists to kill: effort is part of what the cache keys on, which is also why interleaved A/B dual-running is so much more expensive than it looks.

## Section 2 — Model Selection and Optimization

**E11.19 — C.** *(Model Selection and Optimization)* Fable 5.1 cache reads are 0.025 × \$10 = \$0.25/MTok; Opus 5.5 cache reads are 0.05 × \$4 = \$0.20/MTok — the larger discount *factor* does not make Fable the cheaper read. Fable: reads 150 × 300,000 = 45,000,000 × \$0.25/MTok = \$11.25; fresh 300,000 × \$10/MTok = \$3.00; output 750,000 × \$50/MTok = \$37.50; total \$51.75. Opus 5.5: reads 45,000,000 × \$0.20/MTok = \$9.00; fresh 300,000 × \$4/MTok = \$1.20; output 750,000 × \$20/MTok = \$15.00; total \$25.20. Difference **\$26.55**. A (\$22.50) compares output only; B (\$24.30) ignores cache reads entirely; D (\$51.30) applies the generic 0.1× read multiplier to both models.

**E11.20 — B.** *(Model Selection and Optimization)* Opus 5.5 is the documented recommended default, and the documented workflow is to establish quality there first and then test whether a cheaper model holds the bar. A inverts that order: starting cheap means you never learn what the achievable ceiling was, so you cannot tell a model limitation from a prompt limitation. C is a reasonable-sounding heuristic but is not the documented default and is expensive at \$10/\$50. D asserts a “mid-tier is default” rule that does not exist.

**E11.21 — B.** *(Model Selection and Optimization)* Split by tier. Large requests: 3,000 × 160,000 = 480,000,000 input tokens at the tiered rate \$0.10 × 5 = \$0.50/MTok = \$240.00. Small requests: 7,000 × 40,000 = 280,000,000 tokens at \$0.10/MTok = \$28.00. Output across all 10,000 requests: 20,000,000 tokens at \$0.50/MTok = \$10.00, unmultiplied. Total **\$278.00**. A (\$86.00) ignores the tier. C (\$290.00) wrongly applies the 5× to the large requests’ output as well. D (\$390.00) applies the tier to every request rather than per request, which is the failure mode of billing the tier at the job level instead of the request level.

**E11.22 — D.** *(Model Selection and Optimization)* Priority Tier is closed to new purchase and excludes all current models, so the plan’s foundation does not exist; peak-season throughput has to be managed through batching, caching, and rate-limit headroom instead. A, B and C each describe a plausible-sounding limitation of a capacity product, and each would be a reasonable guess if you had not read the current state of the tier — which is exactly what the question tests.

**E11.23 — A and C.** *(Model Selection and Optimization)* Effort lives at `output_config.effort`, not inside `thinking`, and takes `low`, `medium`, `high`, `xhigh`, `max`; the defaults are `medium` on Opus 5.5 and Haiku 5.5 and `high` on the others. B puts effort in the wrong place, which is the single commonest migration error. D asserts a uniform default. E is wrong and dangerous: `thinking` with `budget_tokens` returns a 400 on 4.7+, it does not downgrade silently. F is wrong — effort levels are recalibrated across models, which is precisely why a sweep is required.

**E11.24 — B.** *(Model Selection and Optimization)* There are 3 effort levels × 2 model configurations = 6 cache-distinct combinations. Each pays one write and 119 reads. Writes: 6 × 500,000 × \$2.50/MTok = 6 × \$1.25 = \$7.50. Reads: 6 × 119 = 714 reads × 500,000 × \$0.10/MTok = 714 × \$0.05 = \$35.70. Total **\$43.20**. A (\$37.20) assumes a single cache entry survives model and effort changes. C (\$78.90) uses the generic 0.1× read multiplier instead of Sonnet 5.5’s 0.05×. D (\$900.00) assumes no reuse at all within a combination.

**E11.25 — B.** *(Model Selection and Optimization)* Reliable knowledge extends to June 2026. Anything later — including an internal wiki, which was never in training at all — must be supplied in context. The endpoint supplies none, so the model answers from its priors and describes stale material as current. A asserts continuous training. C mistakes a knowledge gap for a reasoning gap; no amount of effort recovers information the model does not have. D invents a policy distinction that does not explain the symptom.

**E11.26 — C.** *(Model Selection and Optimization)* Compute the absolute per-MTok read price, not the multiplier. Fable 5.1: 0.025 × \$10 = \$0.25/MTok. Opus 5.5: 0.05 × \$4 = \$0.20/MTok. Sonnet 5.5: 0.05 × \$2 = \$0.10/MTok. Over 400,000 × 1,000 = 400,000,000 tokens that is \$100.00, \$80.00 and **\$40.00** respectively, so Sonnet 5.5 at \$40.00. A applies the 0.025 multiplier to a price that was already a read price. D applies Fable’s 0.025 multiplier to Sonnet 5.5. B is the right arithmetic on the wrong model.

**E11.27 — A.** *(Model Selection and Optimization)* The cache is keyed per model, so a three-way router maintains three separate copies of the prefix and every route switch is a write rather than a read. With a 300,000-token prefix that is expensive enough to erase the routing saving entirely; the fix is to route at a coarser granularity — batch requests by model, or keep the cached corpus on one model and route only the cheap leaf steps. B invents a prefix-length cap. C inverts the ITPM relationship (reads generally do *not* count) and confuses rate limiting with eviction. D is false: cache reuse of a stable prefix across varying user turns is the entire point of caching.

## Section 3 — Agents and Workflows

**E11.28 — D.** *(Agents and Workflows)* `max_turns` counts tool-use turns only. A conversation that looks like twenty-one exchanges may contain only a handful of tool calls, so the limit is never reached. This matters in both directions: a team that sets `max_turns` expecting it to bound conversational length will find it ineffective, and a team debugging an `error_max_turns` result should count tool calls, not messages. A, B and C each describe a plausible alternative semantics, and each would lead to a different and wrong tuning decision.

**E11.29 — B.** *(Agents and Workflows)* The budget is checked *after* a response arrives, so the run can overshoot by exactly one response. After five responses the spend is \$1.75, still under \$2.00, so a sixth is issued; cumulative spend becomes \$2.10, the check fires, and the run ends with `error_max_budget_usd`. The answer is **\$2.10 with `error_max_budget_usd`**. A reports the last value below the cap, which is what you would get if the check ran before dispatch. C assumes the cap is a hard stop and that the run ends cleanly. D names a real subtype but the wrong one — `error_during_execution` signals a failure inside the run, not a budget stop.

**E11.30 — A and B.** *(Agents and Workflows)* The defined subtypes are `success`, `error_max_turns`, `error_max_budget_usd`, `error_during_execution`, and `error_max_structured_output_retries`. C, D, E and F are all plausible-sounding names for conditions that really can occur, but they are not subtypes — a context-window overflow or a rate-limit failure surfaces as `error_during_execution`, and depth and timeout conditions do likewise. Branching on an invented subtype string means the branch never fires and the real error falls through to a default handler.

**E11.31 — C.** *(Agents and Workflows)* Default subagent nesting depth is 3. Orchestrator → triage → per-journal → per-paper is already at the limit; the per-figure spawn would be a fourth level and fails. A names the right default for the wrong dimension — concurrency is 20, and nothing in the scenario says 20 were in flight. B is false; subagents may spawn subagents, up to the depth limit. D confuses turn budget with depth.

**E11.32 — A.** *(Agents and Workflows)* When an agent can reach the right answer by an illegitimate route, outcome-only scoring measures nothing useful: the harness and the reviewers disagree because the harness is blind to *how*. Asserting on the trajectory — which tools were called, in what order, with what arguments — turns the shortcut into a test failure. B treats a correctness-definition problem as a capability problem. C changes the grader but still grades only the output, so the shortcut still scores well. D makes coincidence less likely but does nothing about a systematic shortcut, which is not coincidence at all.

**E11.33 — B.** *(Agents and Workflows)* Default subagent concurrency is 20, so 90 tasks run in ceil(90 ÷ 20) = 5 waves, and 5 × 40 s = **200 seconds**. A (180 s) floors 4.5 to 4 waves, which would require the final 10 tasks to run for free. C (120 s) assumes a concurrency of 30. D (3,600 s) is the fully serial time, 90 × 40 s, useful mainly as the upper bound that shows what the concurrency default buys.

**E11.34 — D.** *(Agents and Workflows)* `compaction_control` was removed from the Python SDK in v1.0. There is no rename and no beta header that restores it; the long-context strategy has to be rebuilt on context editing and, where durable state is needed, the memory tool. A, B and C each offer a cheap fix, and each would send the team hunting for a migration path that does not exist — the recurring hazard when an SDK removes rather than deprecates.

**E11.35 — A and C.** *(Agents and Workflows)* Pinning the exact snapshot ID and effort level removes the two largest sources of behavioural drift — and note that both are also cache keys, so pinning them stabilises cost as well as behaviour. Recording and replaying the full trajectory gives the auditability the reviewer actually wants, which is not bit-identical output but the ability to see and compare what the agent did. B and E are the trap: `temperature` and `top_k` are deprecated on 4.7+ and removed from the Python SDK v1.0, so setting them raises a `TypeError` before a request leaves the process — and even on older models they would not have delivered determinism. D invents a sampling difference in the Batches API. F confuses effort with variance; higher effort is not more deterministic.

## Section 4 — Prompt and Context Engineering

**E11.36 — A.** *(Prompt and Context Engineering)* Documents first, question last is the documented ordering, with the docs’ own long-context tests reporting quality gains of up to roughly 30%. It also happens to be the cache-friendly ordering, since the stable documents form a reusable prefix and only the trailing question varies. B is the intuitive ordering and the one most teams ship first. C multiplies cost and discards cross-document synthesis. D puts a short instruction block in front of the cacheable bulk for no benefit.

**E11.37 — C.** *(Prompt and Context Engineering)* When thinking clearing and tool-result clearing are combined, `clear_thinking_20251015` runs first. A is false — the two are designed to be combined. B states the opposite order; the intuition that tool results dominate is often true but does not determine the sequence. D invents threshold-driven ordering.

**E11.38 — A.** *(Prompt and Context Engineering)* The default `keep` is 3, so 18 − 3 = **15 results are cleared**, reclaiming roughly 15 × 8,000 = **120,000 tokens**. B clears everything, ignoring `keep` entirely. C inverts kept and cleared. D assumes a `keep` default of 6. Note that the 100,000-token default trigger has clearly been passed here — 18 × 8,000 = 144,000 tokens of tool results alone — which is why clearing fires at all.

**E11.39 — B.** *(Prompt and Context Engineering)* The memory tool, `memory_20250818`, is the mechanism for durable state that outlives a context window and a session. A names a parameter that was removed from the Python SDK in v1.0 and never had that semantics. C confuses a cost optimisation with persistence — a cache TTL is not storage, and the entry is gone on invalidation. D keeps more context within a session but carries nothing across sessions.

**E11.40 — A and D.** *(Prompt and Context Engineering)* Invalidation flows tools → system → messages: a change at any level invalidates everything after it, which is why editing a tool definition destroys the whole cached prefix. Lookback considers at most 20 blocks. B reverses the direction — changing the last user turn is the *normal* case and invalidates nothing before it. C gets the system-prompt case right but is the weaker of the two true-sounding options and is not among the pair being asked for; it is also incomplete, since it omits the tools level that explains the team’s symptom. E conflates the 20-block lookback with the 4-breakpoint maximum. F is false and is a common cause of mysterious cache misses, since tool definitions are matched as serialised content, not by name.

**E11.41 — D.** *(Prompt and Context Engineering)* One change fixes both symptoms, because both have the same cause: the stable bulk is at the end and the varying text is at the front. Moving the corpus to the front with a breakpoint after it makes the prefix reusable across the session’s related questions, and putting the question last matches the documented long-context ordering. A trades away two-thirds of the corpus to buy something reordering gives for free. B improves hygiene without touching either symptom. C caches the one part of the prompt guaranteed to change on every request.

## Section 5 — Tools and MCPs

**E11.42 — C.** *(Tools and MCPs)* The 2026-07-28 revision is stateless: `server/discover` replaces the `initialize` handshake, so there is no session to establish or resume. A and D both assume the protocol moved toward more session state, which is the opposite of what happened. B states the change backwards. Note that published connector documentation may still describe the older handshake; where the two disagree, the revision date is what tells you which spec a server implements.

**E11.43 — A.** *(Tools and MCPs)* Per-request metadata belongs in the request’s `_meta` field. This follows directly from statelessness: with no session, there is nowhere to negotiate metadata once and reuse it, so anything per-request must travel with the request. B and C both assume a session-scoped negotiation the revision removed. D is wrong because the protocol does define a metadata field, and relying on transport headers would make metadata invisible to the protocol layer.

**E11.44 — A and B.** *(Tools and MCPs)* Sampling and logging are deprecated in the 2026-07-28 revision. C, D, E and F are core protocol surface that remains. Sampling is the one teams most often depend on without noticing, because it is what lets a server ask the client to run a completion — a server written around it needs restructuring, not a flag.

**E11.45 — A.** *(Tools and MCPs)* The 406-token figure applies to forced `tool_choice` (`any` or `tool`), and forced `tool_choice` returns a 400 on current models — so that path is unavailable and the design is budgeting for a request shape it cannot send. With `auto`, overhead is 286 tokens: 286 × 50,000 = 14,300,000 tokens at \$2/MTok = **\$28.60**. B accepts the design’s premise and only adds the arithmetic. C lands on the right number through a wrong story — `any` is not “cheaper”, it is rejected — and a right number with a wrong mechanism will not survive the next design decision. D is false; the overhead is real input, and whether it is cached depends on breakpoint placement.

**E11.46 — D.** *(Tools and MCPs)* Forced tool use is gone on current models; the replacement is `tool_choice: {"type": "auto"}` with strict tool definitions, plus a prompt that states when the tool must be called. Because the model may still answer without calling the tool, the client should validate. A invents a beta header. B invents a naming rule. C is the trap: `any` is a forced value too and fails for the same reason as `tool`.

## Section 6 — Security and Safety

**E11.47 — C.** *(Security and Safety)* The structural fix is to treat retrieved text as untrusted data rather than as instructions, and to put an authorisation boundary in front of state-changing tools so that a hijacked turn cannot send mail or overwrite a report on its own authority. A is worth doing but is a prompt-level control against a prompt-level attack, and it fails the moment an injection is more persuasive than the instruction. B does not change the attack surface. D is brittle filtering that both over-blocks legitimate scientific text and under-blocks any injection phrased as a statement.

**E11.48 — A and B.** *(Security and Safety)* Least-privilege tools and human approval for irreversible or outbound actions both reduce blast radius regardless of whether the injection succeeds — that is what makes them structural rather than probabilistic. C relies on a positional heuristic that does not hold. D is unsupported and would degrade the agent’s actual work. E increases exposure rather than reducing it. F makes the model the security boundary, which is exactly the thing an injection is designed to defeat.

**E11.49 — B.** *(Security and Safety)* A filename emitted as free-form model output is an unverified claim about provenance, and attribution errors in a research product are a correctness failure, not a formatting one. The citations mechanism binds a quoted span to the document block it was drawn from, so the link is produced by the system rather than asserted by the model. A changes the data type of an unverified field. C destroys the product. D adds a second unverified step and compounds the problem.

**E11.50 — D.** *(Security and Safety)* A `refusal` stop reason is a decision, not a transport failure; an identical retry produces the same outcome while costing three times as much and delaying the user. The client should classify the refusal from its stop details and route to a non-automated path. A misreads refusal as truncation. B treats refusal as noise and encourages model-shopping around a safety decision. C is both ineffective and likely to break the request in other ways.

## Section 8 — Eval, Testing, and Debugging

**E11.53 — D.** *(Eval, Testing, and Debugging)* When expert disagreement is stable, it is signal about the task, not noise in the labels, and a single accuracy number against one expert measures agreement with that expert rather than correctness. Establishing inter-rater agreement first tells you the ceiling any model could reach; scoring against consensus where one exists and reporting the contested subset separately keeps the two questions apart. A discards the information that the task is contested and fixes the number at one rater’s idiosyncrasies. B throws away the only grounded judgements available and substitutes a grader with its own unmeasured bias. C removes the human reference entirely, leaving a metric that can rise while quality falls.
