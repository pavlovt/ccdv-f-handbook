# Answer Key: Exam 12

Domain labels below name the **section the question sits in**, not the subject matter it happens to touch. A caching question inside the Agents section is still an Agents question for scoring purposes — which matters more in this exam than any other, because a capstone migration paper deliberately mixes domains inside each section.

## Section 1 — Applications and Integration

**E12.1 — B.** *(Applications and Integration)* Count from 30 September 2026 to 30 November 2026: 30 September to 30 October is 30 days, and 30 October to 30 November is 31 days, giving **61 days**. The documented commitment is at least 60 days’ notice before retirement for publicly released models, so this clears the bar by one day — which is the practically useful observation, because it tells Halyard that the documented minimum is the planning assumption, not a generous floor. A (59 days) undercounts by stopping at 28 November. C (62 days) counts both endpoints inclusively, which double-counts a day. D states the right day count against an invented 90-day minimum; a team using that figure would wrongly conclude the notice was defective and plan around an escalation that will not come.

**E12.2 — D.** *(Applications and Integration)* The missed breaking change is the deprecation of `temperature`, `top_p` and `top_k` on 4.7+ models, compounded by the Python SDK removing them outright in v1.0. Because the SDK no longer accepts the keyword argument, passing `temperature=0.2` raises a `TypeError` in the client process, so CI fails before a request is built — which is why the failure appears local rather than as an API error. A describes what would happen on the raw HTTP API with an older SDK: a 400 at response time. B is the most dangerous distractor, because silent clamping would let a behavioural change ship unnoticed; nothing is clamped. C invents a beta header that does not exist for these parameters.

**E12.3 — A.** *(Applications and Integration)* The shadow sample is 20% of 500,000 = 100,000 requests per day. Input: 100,000 × 12,000 = 1,200,000,000 tokens at \$4/MTok = \$4,800. Output: 100,000 × 1,500 = 150,000,000 tokens at \$20/MTok = \$3,000. Synchronous total \$7,800, and the Batches API 50% discount halves it to **\$3,900**. B is the same total with the batch discount forgotten — the commonest shadow-budget error, because teams model the discount once and then forget it when re-scoping the sample. C (\$19,500) shadows 100% of traffic rather than the 20% sample. D (\$1,950) applies the 50% discount twice.

**E12.4 — C.** *(Applications and Integration)* The missed breaking change is that prefilling a trailing assistant turn returns a 400 on 4.6+; the conversation must end with a user message. The replacement for output shaping is `output_config.format`, the first-class structured-output field. A treats a 400 about message structure as a JSON-escaping problem. B invents a system-prompt prefill, which has never existed — system content is not an assistant turn. D is tempting because structured outputs really are the replacement, but the beta header enables structured outputs, it does not re-enable prefill; a team that believes it does will add the header, still get a 400, and lose a day.

**E12.5 — B.** *(Applications and Integration)* The relevant change is the cache minimum dropping to 512 tokens on current models from 4,096 on Opus 4.6/4.5 and Haiku 4.5, so an 1,800-token prefix that could never be cached now can be. Derived rates on Opus 5.5: write \$4 × 1.25 = \$5/MTok, read \$4 × 0.05 = \$0.20/MTok. Writes: 720 × 1,800 = 1,296,000 tokens × \$5/MTok = \$6.48. Reads: (2,000,000 − 720) × 1,800 = 3,598,704,000 tokens × \$0.20/MTok = \$719.74. Total **\$726.22**, against \$14,400 uncached. A omits the writes; C (\$1,445.96) uses the generic 0.1× read multiplier instead of Opus 5.5’s 0.05×; D is the pre-migration baseline and is the number worth quoting to the migration board, since the caching change alone pays for a large share of the work.

**E12.6 — A and C.** *(Applications and Integration)* `output_format` is deprecated in favour of the first-class `output_config.format`, so the rename direction is right — but `output_config.format` is incompatible with citations and the combination returns a 400, so “change nothing else” is exactly the missed breaking change. Halyard must either keep citations and shape output another way, or accept structured output and rebuild traceability. B inverts the deprecation. D is the plan’s own assumption and is what the 400 disproves. E imports a forced `tool_choice` value that is itself rejected on current models. F invents a Batches-only restriction.

**E12.7 — A.** *(Applications and Integration)* From 18 October to 31 October is 13 days, and November contributes 30, giving **43 days** to the 30 November retirement. B (42) excludes one endpoint too many, typically by counting to 29 November. C (44) counts both endpoints inclusively. D (13) counts only the remainder of October, the error that comes from reading the retirement date as the end of the current month. The practical point is that 43 days must cover dual-running, adjudication of regressions, and rollback capacity — not just the code change.

**E12.8 — D.** *(Applications and Integration)* Amazon Bedrock and Google Cloud set their own retirement schedules; the dates published for the Claude API, the Claude Platform on AWS and Microsoft Foundry do not govern them. The Bedrock date must be confirmed independently, and planning must allow for it falling either side of the Claude API date. A is false — Bedrock carries deprecated models on its own timeline. B is the plan’s implicit assumption stated outright, and it is unsafe precisely because it assumes a direction. C invents a contractual step. A migration programme that tracks one schedule for two platforms will eventually miss a retirement on the platform it was not watching.

**E12.9 — C.** *(Applications and Integration)* Two caps apply and the tighter one binds. By size: 256,000,000 ÷ 2,000 bytes = 128,000 requests per batch. By count: 100,000. So 100,000 binds, and the job needs ceil(1,400,000 ÷ 100,000) = **14 batches, bound by the request-count limit**. A applies only the size cap and gets ceil(1,400,000 ÷ 128,000) = 11. B gets the right count but attributes it to the wrong limit, which matters because the remedies differ — trimming payload would not help here, whereas it is the only fix when size binds. D misreads the 24-hour expiry, which bounds how long an in-flight batch may take, not how many may run per day.

**E12.10 — B.** *(Applications and Integration)* The missed breaking change runs the other way from most: `inference_geo` returns a 400 on pre-4.6 models, so adding it unconditionally breaks the legacy route rather than the new one. It can only be introduced into the shared request path once the pre-4.6 routes are gone, or it must be set conditionally on the target model. A invents a Console-only setting. C invents a conflict with caching. D invents a Batches API requirement. The general lesson is that a staged cutover has two request shapes alive at once, and a shared builder must be conditional on the target model, not on the migration’s end state.

**E12.11 — D.** *(Applications and Integration)* The same text tokenises to roughly 30% more tokens on the replacement, so the real average is 40,000 × 1.3 = 52,000 tokens. Daily: 300,000 × 52,000 = 15,600,000,000 tokens at \$2/MTok = **\$31,200**. A (\$24,000) is the budgeted figure at the old token count, which is what the capacity model predicted and what makes the overrun a surprise. B (\$18,461) divides by 1.3 instead of multiplying, treating the change as a reduction. C (\$7,200) is the increase alone, not the total — a real number, but not the answer to the question asked.

**E12.12 — A.** *(Applications and Integration)* From 4.6 onward a dateless model ID is a **fixed snapshot**, not an alias; it is the pre-4.6 undated strings that floated. So `claude-sonnet-5-5` will not roll forward, and the document’s stated benefit — continuous improvement without further PRs — does not exist. This cuts both ways and is worth stating plainly to a change board: the pin is safer than they think, and the maintenance saving they were counting on is imaginary. B is false; dateless IDs are the normal form on the Claude API. C concedes the aliasing premise and argues about scope. D invents resolution at account-creation time.

**E12.13 — C.** *(Applications and Integration)* Cache writes count toward ITPM; cache reads generally do not. Production: 200 × 30,000 = 6,000,000. Shadow fresh input: 200 × 5,000 = 1,000,000. Shadow cache writes: 4 × 25,000 = 100,000. The 196 × 25,000 = 4,900,000 tokens of cache reads are not counted. Total **7,100,000**. A counts production only and ignores the shadow arm entirely. B forgets the cache writes — the error that produces unexplained throttling right after a prefix change invalidates the cache and turns reads into writes. D counts the cache reads too, giving 12,000,000 and leading Halyard to request capacity it does not need.

**E12.14 — A, B and C.** *(Applications and Integration)* Three breaking changes apply on this hop. Non-default `temperature`, `top_p` and `top_k` must go (400 on 4.7+, and a `TypeError` in Python SDK v1.0). `thinking` with `budget_tokens` must go, replaced by `output_config.effort` — which lives in `output_config`, not inside `thinking`. Forced `tool_choice` values `any` and `tool` must become `auto`, with strict tools to keep the output shape. D is invented: `custom_id` is a Batches API join key with no relationship to model identity. E is false; the context window is 1M on current models. F inverts the cache change — the minimum fell to 512 tokens, so more prompts cache, not fewer.

**E12.15 — B.** *(Applications and Integration)* A 20% sample costs 0.20 × \$19,500 = \$3,900 per day and a 50% sample costs \$9,750 per day. First phase: 14 × \$3,900 = \$54,600. Second phase: 29 × \$9,750 = \$282,750. Total **\$337,350**. A (\$167,700) holds the 20% rate for all 43 days. C (\$419,250) applies the 50% rate throughout. D (\$838,500) shadows all traffic for the whole window and is the figure that usually kills a dual-run proposal before anyone checks whether a sample would do.

**E12.16 — A.** *(Applications and Integration)* `claude-opus-4-1-20250805` retired on 5 August 2026. A quarterly job that last ran in July 2026 has not run since retirement, so its next run will fail — and may already have failed unnoticed. This is an incident and a monitoring gap, not a migration item: requests to retired models fail outright. B describes `claude-mythos-preview`, whose retirement is to be announced, not this model. C transplants the Sonnet 4.5 snapshot’s 30 November date onto an Opus model that retired three months earlier. D invents an exemption. The generalisable lesson is that low-frequency jobs are the ones a deprecation sweep misses, because they generate no traffic to show up in a usage export between runs.

**E12.17 — D.** *(Applications and Integration)* Under the old caps, each image was downscaled to a 1,568-pixel long edge and then capped at 1,568 visual tokens, so the old cost was 1,568 tokens per image. At full size, ceil(2000/28) = ceil(71.43) = 72 and ceil(1500/28) = ceil(53.57) = 54, giving 72 × 54 = 3,888 tokens, which is within the new 4,784-token cap. The increase is 3,888 − 1,568 = 2,320 tokens per image; 50,000 × 2,320 = 116,000,000 tokens at \$2/MTok = **\$232.00 per day**. B (\$153.60) uses the uncapped downscaled count of 56 × 42 = 2,352 as the old value, forgetting that the old cap bound. C (\$388.80) prices the full new count as if the old cost were zero. A ignores that the token caps changed at all.

**E12.18 — C.** *(Applications and Integration)* The cache is keyed per model, so a 50/50 split maintains two separate copies of the prefix, and under alternating traffic each path repeatedly finds its own entry expired or superseded — turning what should be reads into writes on both arms. The fix is to batch traffic by model rather than interleave it, or to accept and budget the duplicated write cost for the rollout window. A invents hit-rate-driven eviction. B invents a code-path dependency; the cache keys on serialised content, not on where it was constructed. D inverts the ITPM relationship, since reads generally do not count toward it.

## Section 2 — Model Selection and Optimization

**E12.19 — B.** *(Model Selection and Optimization)* Every request has 130,000 input tokens, above Haiku 5.5’s 100,000-token threshold, so its input rate becomes \$0.10 × 5 = \$0.50/MTok; output is unaffected at \$0.50/MTok. Haiku: 400,000 × 130,000 = 52,000,000,000 tokens × \$0.50/MTok = \$26,000, plus 800,000,000 output tokens × \$0.50/MTok = \$400, total \$26,400. Sonnet 5.5: 52,000,000,000 × \$2/MTok = \$104,000, plus 800,000,000 × \$10/MTok = \$8,000, total \$112,000. Haiku is cheaper by **\$85,600**. A (\$106,400) ignores the tier. C (\$78,000) compares input only. D is the subtlest trap: it multiplies 5× onto \$0.50 rather than \$0.10, producing an imagined \$2.50/MTok that would make Haiku the dearer option — the right concern applied to the wrong base rate.

**E12.20 — A.** *(Model Selection and Optimization)* The documented recommended replacement for `claude-sonnet-4-5-20250929` is **`claude-sonnet-5-5`**. B elevates the recommended default into a universal replacement rule; Opus 5.5 is the documented default for new work, which is a different question from what replaces a specific retiring snapshot. C invents a minor-version-stepping policy and would land Halyard on a model that will itself need migrating sooner. D inverts the documented approach of establishing quality first and testing downgrades afterwards.

**E12.21 — C.** *(Model Selection and Optimization)* Priority Tier is closed to new purchase and excludes all current models, so there is no capacity to buy for Sonnet 5.5 and the line item has to come out of the plan. Throughput protection during the dual run has to come from elsewhere: route shadow traffic through the Batches API, schedule it off-peak, and keep rate-limit headroom on the production arm. A, B and D each describe a plausible restriction on a capacity product and would each be a sensible guess from first principles — which is the point. The candidate either knows the tier’s current status or does not.

**E12.22 — D.** *(Model Selection and Optimization)* Changing effort restarts the cache, so each of the three levels pays its own write plus 499 reads. Derived rates on Opus 5.5: write \$4 × 1.25 = \$5/MTok, read \$4 × 0.05 = \$0.20/MTok. Writes: 3 × 60,000 × \$5/MTok = 3 × \$0.30 = \$0.90. Reads: 3 × 499 = 1,497 reads × 60,000 = 89,820,000 tokens × \$0.20/MTok = \$17.964. Total **\$18.86**. A (\$18.29) assumes one cache entry survives effort changes. B (\$17.96) omits the writes. C (\$36.83) uses the generic 0.1× read multiplier. The design consequence matters more than the figure: sweep one effort level to completion before changing it, never interleave.

**E12.23 — A and C.** *(Model Selection and Optimization)* Effort is set at `output_config.effort` with values `low`, `medium`, `high`, `xhigh`, `max`, and the defaults are `medium` on Opus 5.5 and Haiku 5.5, `high` on the others. B is the single commonest migration error — putting effort inside `thinking`, where `budget_tokens` used to live — and it is what produces a 400 that teams then misdiagnose as a thinking problem. D asserts a uniform `low` default. E is what makes teams skip the sweep: there is no fixed mapping from a token budget to an effort level, and levels are recalibrated across models. F invents a per-conversation restriction.

**E12.24 — A.** *(Model Selection and Optimization)* Per-request input is 95,000 + 8,000 = 103,000 tokens, above the 100,000 threshold — and the threshold counts cache reads, which is the step that makes this a surprise. All input rates are therefore multiplied by 5. Cache reads: 60,000 × 95,000 = 5,700,000,000 tokens at \$0.01 × 5 = \$0.05/MTok = \$285.00. Fresh input: 60,000 × 8,000 = 480,000,000 tokens at \$0.10 × 5 = \$0.50/MTok = \$240.00. Output: 72,000,000 tokens at \$0.50/MTok = \$36.00. Total **\$561.00**. B (\$141.00) assumes no tier, which is what the budget was built on. C (\$705.00) wrongly multiplies output too. D (\$333.00) applies the multiplier only to the fresh input, as though cache reads counted toward the threshold but were billed outside it.

**E12.25 — B.** *(Model Selection and Optimization)* The overrun comes from crossing the 100,000-token threshold by 3,000 tokens, not from Haiku’s base rate: below the threshold the same job would cost \$141.00. Trimming or splitting the prefix to get under 100,000 recovers almost the entire overrun at Haiku pricing. A would work but is a large and unnecessary step up in unit cost for a job whose only problem is 3,000 tokens of margin. C technically removes the tier but throws away the caching discount, which costs far more than it saves. D invents a batch exemption from tiering; batching gives 50% off, which helps, but it does not change how the threshold is computed.

**E12.26 — D.** *(Model Selection and Optimization)* Sonnet 5.5 reads are 0.05 × \$2 = \$0.10/MTok; across 250,000 × 80,000 = 20,000,000,000 tokens that is **\$2,000**. Haiku 5.5 reads are 0.1 × \$0.10 = \$0.01/MTok, but the 250,000-token prefix puts every request over the threshold, so the rate becomes \$0.05/MTok and the cost is **\$1,000** — still cheaper, but only half as cheap as the headline multiplier suggests. A (\$200 on Haiku) forgets the tier entirely and overstates Haiku’s advantage fivefold. B applies a 0.025× multiplier to Sonnet 5.5, which belongs to Fable 5.1. C applies the generic 0.1× to Sonnet 5.5, giving \$4,000.

**E12.27 — C.** *(Model Selection and Optimization)* `claude-mythos-preview` was deprecated on 9 June 2026 with retirement **to be announced**. No date exists to plan against, so the only safe posture is to migrate now and treat the documented 60-day minimum as the warning the team will eventually get at an unpredictable moment. A invents a 60-day auto-retirement that would already have passed. B borrows the Sonnet 4.5 snapshot’s date. D is false and is the belief that leaves preview-model features stranded: deprecated models are also documented as likely to be less reliable than active ones, so staying is a quality risk as well as a schedule risk.

## Section 3 — Agents and Workflows

**E12.28 — D.** *(Agents and Workflows)* `compaction_control` was **removed** from the Python SDK in v1.0 — removed, not renamed or gated — so there is no drop-in replacement and the long-context strategy must be rebuilt on context editing (`clear_tool_uses_20250919`, `clear_thinking_20251015`) with the memory tool (`memory_20250818`) where state must outlive the context window. A, B and C each offer a cheap fix and each sends the team hunting for a migration path that does not exist, which is the characteristic hazard of a removal as opposed to a deprecation: there is no warning period and no compatibility shim.

**E12.29 — B.** *(Agents and Workflows)* `max_budget_usd` is checked **after** a response arrives, so a run can overshoot by exactly one response. After five responses the canary has spent 5 × \$0.90 = \$4.50, under the \$5.00 cap, so a sixth is issued; cumulative spend reaches \$5.40, the check fires, and the run ends with **`error_max_budget_usd`**. A (\$4.50) is what you would get if the check ran before dispatch. C treats the cap as a hard ceiling and the run as clean. D pairs the right figure with a subtype that signals a different termination condition entirely, which would send the dashboard’s triage down the wrong path.

**E12.30 — A and B.** *(Agents and Workflows)* The defined subtypes are `success`, `error_max_turns`, `error_max_budget_usd`, `error_during_execution`, and `error_max_structured_output_retries`. C, D, E and F name conditions that are real and migration-relevant — a retired model, a cache miss, a deprecated parameter — but none is a subtype; a request to a retired model or a rejected deprecated parameter surfaces as `error_during_execution`. A dashboard branching on invented strings will show zero of everything while real failures fall through to a default bucket, which is the worst possible instrumentation during a cutover.

**E12.31 — A.** *(Agents and Workflows)* `max_turns` counts **tool-use turns only**, so a run with many conversational exchanges and few tool calls never approaches the limit. During migration testing this matters in both directions: a limit set to bound run length will not bound it, and an `error_max_turns` result should be debugged by counting tool calls rather than messages. B invents a reset on model change. C restricts the parameter to subagents. D invents a per-minute window.

**E12.32 — C.** *(Agents and Workflows)* Output equality is the wrong instrument because it is simultaneously too strict and too loose: it flags harmless wording changes as regressions and passes a run that skipped a validation tool. Comparing trajectories as well as outputs makes the skipped validation a detected regression and the wording change a non-event. A fixes only the too-strict half and still cannot see the skipped step. B assumes matches are safe, which is precisely the assumption the reviewer disproved. D is a more elaborate string comparison and inherits every weakness of the simple one.

**E12.33 — B.** *(Agents and Workflows)* Default subagent concurrency is 20, so 150 tasks run in ceil(150 ÷ 20) = 8 waves, and 8 × 25 s = **200 seconds**. A (175 s) floors 7.5 to 7 waves, which would leave the last 10 subagents unaccounted for. C (125 s) assumes a concurrency of 30. D (3,750 s) is the fully serial time and is useful only as the upper bound that shows what the default buys. Note the related default the question does not turn on: subagent nesting depth is 3, which a flat fan-out never reaches.

**E12.34 — A.** *(Agents and Workflows)* `error_max_structured_output_retries` is the subtype for exhausting retries on structured output, and it is a migration-typical failure because output shaping moved from assistant prefill to `output_config.format` — a schema that the old prefill approach tolerated loosely may now fail validation strictly. B is the catch-all and would hide the specific cause. C is not a subtype. D names a different termination condition. Mapping this subtype to a distinct alert is worth doing before cutover, since it points straight at the schema rather than at the model.

**E12.35 — A and C.** *(Agents and Workflows)* Pinning the exact model ID and effort level on both arms removes the two largest sources of drift, and both are cache keys, so pinning stabilises cost as well as behaviour. Persisting the full trajectory gives what reproducibility actually means here: the ability to replay and diff a run, not bit-identical output. B and D are the trap, and a capstone-level one — `temperature` and `top_k` are deprecated on 4.7+ and removed from the Python SDK v1.0, so setting them raises a `TypeError` before a request is built; they were never going to deliver determinism either. E invents a sampling difference in the Batches API. F confuses effort with variance.

## Section 4 — Prompt and Context Engineering

**E12.36 — D.** *(Prompt and Context Engineering)* Prefill is rejected on 4.6+, and the replacement is not a single substitution but a decomposition by purpose: output format moves to `output_config.format`, preambles move to the system prompt, and continuations and reminders become user-turn content. A preserves the text but not the mechanism — an assistant preamble pasted into a user turn reads as something the user said, which changes behaviour. B invents a system-prompt prefill. C gives up too early; every one of the three uses has a documented replacement, which is exactly what makes this a migration task rather than a loss.

**E12.37 — A.** *(Prompt and Context Engineering)* Documents first with the question last is the documented long-context ordering, associated in the docs’ own tests with quality gains of up to roughly 30%, and it has a second payoff during migration: the 300 source records become a stable cacheable prefix while only the trailing question varies. B is the intuitive ordering and the one most systems ship with. C puts a short rules block ahead of the cacheable bulk for no benefit and pushes the question into the middle. D multiplies cost and destroys cross-record synthesis.

**E12.38 — C.** *(Prompt and Context Engineering)* The default `keep` is 3, so 26 − 3 = **23 results are cleared**, reclaiming roughly 23 × 5,000 = **115,000 tokens**. The default 100,000-token trigger has clearly been passed, since 26 × 5,000 = 130,000 tokens of tool results alone. A assumes a `keep` of 6. B clears everything and ignores `keep`, which would discard the context the agent is actively using. D inverts kept and cleared.

**E12.39 — B.** *(Prompt and Context Engineering)* When both clearing strategies are enabled, `clear_thinking_20251015` runs first. A and D both assert an exclusivity that does not exist — the two are designed to be combined, which is the normal configuration for a long-running migrated agent. C states the opposite order; the intuition that tool results dominate the context is often true but does not determine the sequence.

**E12.40 — A and C.** *(Prompt and Context Engineering)* Invalidation flows tools → system → messages, so adding one tool definition invalidates everything cached after it — for every request, including those that never call the new tool. That is the whole explanation for a fleet-wide hit-rate collapse from a one-line change, and it is why tool definitions should be changed in deliberate, batched releases during a migration. Cache lookback considers at most 20 blocks, which bounds how far a match can be found. B reverses the direction. D conflates the 20-block lookback with the 4-breakpoint maximum. E is false and is a frequent source of mysterious misses: tool definitions are matched as serialised content, not by name. F is wrong because invalidation is immediate, not deferred to TTL expiry.

**E12.41 — D.** *(Prompt and Context Engineering)* The missed change is a default, not a parameter: on the replacement model a request with no `thinking` field runs with thinking on, where previously it ran without. Since `max_tokens` covers thinking plus text and thinking tokens bill as output, a 4,096-token budget tuned for text alone now has to accommodate both, and the visible answer is truncated. The fix is to raise `max_tokens`, or to lower effort, or to use `thinking: {"type": "between_tools"}` where up-front thinking is not wanted. A invents a lower ceiling; the output maximum is 128K. B has the tokenizer change backwards — the same text produces about 30% *more* tokens — and then draws a conclusion that would not follow anyway. C invents an output-token cost for citations.

## Section 5 — Tools and MCPs

**E12.42 — B.** *(Tools and MCPs)* Both `any` and `tool` are forced values and both return a 400 on current models, so the proposal swaps one rejected value for another. The replacement is `tool_choice: {"type": "auto"}` with strict tool definitions, a prompt that states when the tool must be called, and code-side validation — because with `auto` the model may legitimately answer without calling the tool. A accepts the proposal. C is wrong on the facts and would also leave the team believing a rejected request shape is merely expensive. D invents a one-tool rule.

**E12.43 — A.** *(Tools and MCPs)* The 406-token figure applies to forced `tool_choice`, which is rejected on current models, so the capacity model is budgeting for a request shape Keel cannot send; the applicable overhead is the 286-token `auto`/`none` figure. Daily: 286 × 900,000 = 257,400,000 tokens at \$2/MTok = **\$514.80**. B accepts the premise and merely completes the arithmetic, giving \$730.80 — an over-budget of \$216 a day, which is less damaging than the design error it conceals. C reaches the right number through a wrong story: `any` is not cheaper, it is rejected, and that distinction decides whether the next design review repeats the mistake. D invents free cached overhead.

**E12.44 — C.** *(Tools and MCPs)* The 2026-07-28 revision is **stateless**, with `server/discover` replacing the `initialize` handshake, so the updated server establishes no session at all. A and D both assume the protocol moved toward more session state, which is the opposite of the change. B states the relationship backwards. Note that connector documentation written against the older spec may still describe the handshake; the revision date, not the prose, tells you which contract a server implements.

**E12.45 — A and B.** *(Tools and MCPs)* Sampling and logging are deprecated under the 2026-07-28 revision. Sampling is the harder of the two to lose, because it is what lets a server ask the client to run a completion — a server built around it needs restructuring rather than a configuration change. C, E and F are core surface that remains. D is the trap: per-request `_meta` is not deprecated, it is the mechanism the stateless revision introduces to carry what a session used to hold.

**E12.46 — B.** *(Tools and MCPs)* With no session, there is nowhere to negotiate a trace identifier once and reuse it, so it must travel with each request in `_meta` — which is exactly what that field exists for. A fights the protocol by re-establishing a session per request, adding latency to simulate state the revision deliberately removed. C abuses the tool schema and would make the identifier part of the model’s input, visible to the model and liable to be omitted or altered. D is wrong because the protocol does define a metadata field, and confining tracing to transport headers hides it from the protocol layer where the server reads requests.

## Section 6 — Security and Safety

**E12.47 — C.** *(Security and Safety)* A 429 carrying `error.details.error_code == "enforced_spend_limit_reached"` is a spend-cap rejection, not a rate-limit rejection: it carries no `retry-after` and is never retryable, because no amount of waiting raises a cap. Classifying by error code and failing fast would have turned a silent hour-long stall into an immediate, actionable signal — which on cutover night is the difference between pausing the dual run deliberately and discovering the queue is empty. A invents a slower clearing cycle. B is impossible, since there is no `retry-after` to honour. D is false: spend limits apply to batch traffic too.

**E12.48 — A and B.** *(Security and Safety)* A staged split with an automated rollback bound to a measured signal removes the dependency on someone noticing in time, and gating state-changing actions that are new to the candidate path keeps the dual run from doing irreversible things twice or differently. Both are structural; both hold whether or not the model behaves. C treats effort as a safety control. D removes the evidence needed to adjudicate regressions and is a false economy — the answer is to protect the logs, not to delete them. E widens the window for an agent to act. F makes the model the safety boundary, which is never the right place for it during a change.

**E12.49 — A and B.** *(Security and Safety)* Replaying archived customer free text through a candidate configuration with a different tool surface can activate injection payloads that were inert before — the attack did not change, the capability did. And copying both arms’ outputs into a widely readable comparison database spreads customer content into a system that was never scoped for it, so it needs the source system’s controls. C is wrong on the facts and on the relevance: there is no idempotency key, but replay does not require one. D misreads batch ordering, which is solved by `custom_id`. E is a cost observation dressed as a security one. F overstates a real constraint — thinking-block portability is limited across model families, but archived *requests* replay fine.

**E12.50 — A.** *(Security and Safety)* `refusal` is a decision, not a transport failure, so an identical retry returns the same thing three times at three times the cost while the user waits. The client should classify the refusal from its stop details and route those requests to a non-automated path, and the migration team should treat the shift as a genuine behavioural difference to characterise rather than an error rate to suppress. B misreads refusal as truncation. C is the worst option on the page: it routes traffic back onto a model that retires within weeks, hard-coding an incident into the cutover plan. D is both ineffective and likely to break the request in other ways.

## Section 7 — Claude Code

**E12.51 — B.** *(Claude Code)* `CLAUDE.md` at the repository root is Claude Code’s project memory and is where standing conventions belong, so every session in the Keel repository starts with the migration rules in context. A confuses permissions with conventions — the deny list governs which commands may run, not which parameters may appear in source. C puts repository conventions behind a network dependency and in a place sessions will not read as project context. D surfaces the rules only after the code is already written.

**E12.52 — C.** *(Claude Code)* Deny takes precedence over allow, and an allow entry cannot carve an exception out of a deny rule, regardless of which settings file it lives in. The dry run stays blocked, and the correct fix is to narrow the deny pattern itself so it does not match the dry-run invocation. A applies file-precedence reasoning that is real for merging settings generally but does not override deny-wins. B invents a conflict resolution that does not exist. D invents a session scope. During a freeze this is the behaviour you want: the exception has to be made explicit in the rule, not bolted on beside it.

## Section 8 — Eval, Testing, and Debugging

**E12.53 — D.** *(Eval, Testing, and Debugging)* Agreement with the outgoing model is not correctness, and a 94% match number conflates three different things: cases where both are right, cases where both are wrong in the same way, and cases where the candidate differs because it is better. Using it as a gate therefore penalises improvement and rewards shared error. The defensible procedure is to adjudicate the 6% disagreement against a reference standard, spot-check a sample of the agreeing cases to bound shared error, and report regressions and improvements separately. A accepts the metric and argues only about the threshold, which is the most seductive wrong answer because it sounds rigorous. B overstates the tokenizer difference into an impossibility. C raises a real sampling concern but a secondary one — a perfectly representative sample of the wrong metric is still the wrong metric.
